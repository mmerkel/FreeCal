# FreeCal v1

Status: ready-for-agent

## Problem Statement

I keep my calendars in several places: Google, one or more CalDAV servers (Nextcloud, Fastmail, iCloud…), and things that live only on my machine. On Linux there's no desktop calendar app that brings them together with the ergonomics of Google Calendar, works properly offline, and that I can trust not to quietly damage my calendars when sync goes wrong. Today I use a browser tab for Google, other tools for the rest, and I have no safety net if a sync tool deletes or mangles Events on a server.

## Solution

FreeCal is a desktop calendar app for one local user, mainly for Linux. It shows Calendars from many Accounts (Local, CalDAV and Google) in one Google-Calendar-like view with day, week and month views, drag-to-create, drag-to-move/resize and keyboard shortcuts. It is offline-first: every synced Calendar is held locally, can be viewed and edited without a network, and syncs two ways when a connection is available. When a local and a remote change can't both be kept, FreeCal takes the server's version, keeps the user's, and shows what it decided until the user has looked. Every change to a Calendar, made in FreeCal or pulled from a server, is recorded in its Calendar History and can be undone. A Mass-Change Guard asks before FreeCal sends an unusually large change to a server. Daily Backups are the last resort. FreeCal runs in the background where a system tray exists, shows reminder notifications, and reports Conflicts and Sync Errors through a tray icon.

The domain vocabulary is defined in the glossary; architecture decisions are in ADRs 0001–0004 (Tauri + Svelte 5 + FullCalendar behind `CalendarGrid`, Google via REST, GPLv3, SQLite).

## User Stories

### Accounts and Calendars

- **US-1** As a user, I want a Local Account to exist from the first launch, so that I can start using FreeCal without connecting anything.
- **US-2** As a user, I want the Local Account to be impossible to remove, so that my local-only Calendars always have a home.
- **US-3** As a user, I want to create, rename, recolour and delete Calendars in the Local Account, so that I can organise Events that live only on this computer.
- **US-145** As a new user, I want FreeCal to start with a shown "Work" and a hidden "Home" Calendar, a hint when the Local Account has no Calendars, and a tooltip on each Calendar saying whether it is shown, so that I learn the sidebar without reading anything.
- **US-4** As a user, I want to add a CalDAV Account by entering a server URL, username and password, so that I can use my Nextcloud, Fastmail, iCloud or other CalDAV calendars.
- **US-5** As a user, I want FreeCal to discover all Calendars of a CalDAV Account automatically and let me choose which of them to add, so that I don't have to enter each Calendar's URL and only see the ones I want.
- **US-6** As a user, I want to add a Google Account by logging in through my browser and choose which of its Calendars to add, so that I never type my Google password into FreeCal and only see the Calendars I want.
- **US-7** As a user of the public 1.0, I want a guided "bring your own client" setup for Google, so that I can connect Google even though FreeCal's shared client isn't verified yet.
- **US-8** As a developer or tester, I want to use FreeCal's shared (unverified) Google client, so that I can connect Google without creating my own client.
- **US-9** As a user, I want to connect several Accounts of each Provider, so that work and personal calendars appear side by side.
- **US-10** As a user, I want my passwords and tokens kept in the system keyring, so that they are protected by my desktop login.
- **US-11** As a user without a working system keyring, I want a clear error explaining why I can't add a server Account, so that I know what to fix.
- **US-12** As a user, I want to remove a Google or CalDAV Account, so that its Calendars disappear from FreeCal and its credentials are deleted from the keyring.
- **US-13** As a user, I want each Calendar to have a colour, so that I can tell Events apart at a glance.
- **US-14** As a user, I want to show and hide individual Calendars from a sidebar, so that I can focus on what matters right now.
- **US-15** As a user, I want Calendars grouped by Account in the sidebar, with each server Account's line letting me fetch the server's current list of Calendars and add or remove them, so that I can see where each Calendar comes from and pick up Calendars created on the server later.
- **US-152** As a user adding server Calendars, I want each one to appear in the sidebar at once and fill in when it has loaded, with its progress on its line, so that I can go on working while a large Calendar loads and never see a half-loaded one.
- **US-16** As a user, I want Calendars the server doesn't let me change to be marked read-only when I add them, so that FreeCal doesn't start edits that will fail.
- **US-17** As a user, I want to mark any Calendar as read-only in FreeCal, so that I can protect a Calendar from accidental edits.
- **US-18** (dropped 2026-11-21: newly added Calendars are marked read-only only when their server doesn't allow changes, before 1.0 too.)
- **US-19** As a user, I want to switch a Calendar from read-only to writable myself, once its server allows changes, so that I decide when FreeCal may change it.
- **US-154** As a user, when the server stops accepting changes to a Calendar, I want my changes to wait as when I'm offline, and to decide myself when to give them up and mark the Calendar read-only, so that a short loss of access costs nothing.

## Implementation Decisions

- **Platforms**: v1 targets Linux, but Windows and macOS stay possible. The core stays platform-neutral, and desktop-specific pieces (tray detection, D-Bus, autostart, the file hand-off) sit behind shell interfaces so that they can be ported.
- **Architecture** (ADR 0001): a Rust core library that holds all domain logic, a Tauri shell exposing the core to the frontend as commands, and a Svelte 5 frontend (runes only, plain Vite, no SvelteKit). Vite is used only for development and the build; the shipped binary embeds the compiled frontend.
- **Core application interface**: the core exposes one application-level interface, which is also the main test seam. Its operations cover:
  - Accounts: add, remove, re-authenticate
  - Calendars: list, create, rename, recolour, delete, show or hide, show only one, set or remove the read-only mark (removing asks the server first), stop waiting where writes are refused; for a server Account, list the server's current Calendars, add Available Calendars (each is stored at once, empty, and its First Sync runs as its first Incoming Sync) and remove Calendars from FreeCal
  - Occurrences: get those in a date range, already converted to the Display Time Zone, each with whether it has unsent local changes and since when
  - Events: create, edit, move or delete, including the recurrence scope (this / this and following / all) and moves across Accounts
  - Sync: sync now (per Account, or for all); get the current sync status of every Account and Calendar
  - Conflicts: list the open ones, for all Calendars or for one, each with its User's Version, Server Version and Last Agreed Version, and resolve them, one or all of a Calendar's together, by keeping the server's version or restoring the user's
  - Sync Errors: read through the Sync Status; send what a paused Calendar holds back
  - Calendar History: list the Snapshots of all Calendars, or of one, or only the user's own; undo one Snapshot, with or without the later changes standing in its way; the undo and redo of Ctrl+Z and Ctrl+Shift+Z; read an Event's History
  - Import/export: add files waiting to be imported, list them, dismiss one, preview an import, run it, export
  - Backups: take, list, restore
  - App state and settings: last-used view, sidebar shown or hidden and its width; the settings background mode, autostart, appearance (system, light or dark), the overrides for Display Time Zone and format region (each `system` by default), the first day of week (`monday`, `saturday` or `sunday`, default `monday`) and the clock (`24` or `12`, default `24`). Settings are written as partial updates: only the fields given change
  The frontend talks only to this interface.
- **Signals (core → frontend)**: besides answering requests, the core pushes Signals: messages saying that something changed. The Tauri shell forwards them to the frontend as Tauri events. In code and docs they are always called Signals, never "events" (that word means calendar Events) or "notifications" (those are desktop notifications). There are two kinds:
  - A **status Signal** carries the new state itself, because it is small and the state is the whole message.
  - A **change Signal** only names what changed. The frontend re-reads through the core interface, so the Local Store stays the single source of truth.

  The v1 Signals are:
  - **Sync status changed** (status): the new Sync Status of an Account or Calendar, with the time and outcome of the last finished sync, and for a Calendar whether it has unsent changes, how many Conflicts it has, and how far a sync that takes long has come (what is counted depends on the Provider).
  - **Occurrences changed** (change): the Events of one or more Calendars changed, for any reason (an Incoming Sync, the user's change, import, undo, redo, Backup restore, Conflict resolution). It carries the affected Calendar IDs.
  - **Calendars changed** (change): Accounts or Calendars were added, removed, renamed, recoloured, shown or hidden, or their writability changed (for example the user adding a server Calendar, or a server permission change).
  - **Conflicts changed** (change): a Calendar got a Conflict, its Conflicts changed, or they ended. Sync Errors come with "Sync status changed". The tray and the notifications follow both and query the core for details; they run in the shell next to the core.
  - **Display Time Zone changed** (status): the system time zone changed, for example after travelling, or the user changed the Display Time Zone override. It carries the new zone. The frontend redraws the visible range and the time zone label. An open editor keeps its draft, including the draft's own time zone.
  - **Waiting imports changed** (change): files waiting to be imported were added or one was dismissed or imported. The frontend re-reads the list and opens the preview for the first one when no modal dialog is showing.
  - **Date changed** (status): the local date changed, at midnight or on waking up on a new day. It carries the new date. The frontend moves the today highlight, and jumps to the new today if it is tracking today (see View state). The core sends it because it already detects waking from sleep and owns the clock that tests control.

  There are no Signals for reminders, which are desktop notifications only, or for the progress of long operations (import, export, Backup restore). While such a command runs, the window shows a modal "Working…" dialog that blocks it until the command finishes, so edits can't interleave with an import or restore. A non-blocking version can come later if large imports turn out to be slow.

  Account-level states (Offline, an expired login, a locked keyring) and Calendar-level states (paused by the Mass-Change Guard, writes refused) each live where they happen. "Sync status changed" is sent separately for Accounts and for Calendars, and the sidebar shows an Account-level state once on the Account row, not repeated on every Calendar. The Local Account and its Calendars have no Sync Status and never send "Sync status changed".

  Signals are batched: an Incoming Sync sends at most one "Occurrences changed" per Calendar, when its Database Transaction is committed. A First Sync is an Incoming Sync like any other (ADR 0018): adding a Calendar sends "Calendars changed" at once, and its First Sync one "Occurrences changed" when it finishes. Signals are fire-and-forget: with no window to receive them, they are dropped. Running in the background hides the window rather than destroying it (ADR 0016), so a hidden window still receives them and is current when it shows again. When the frontend starts, it subscribes first and then reads the current state, so nothing falls in the gap. The tray and the background desktop notifications use the same Signals inside the shell, so the window and the tray never disagree.
- **Provider interface** (internal, not a test seam): one implementation per Provider: Local, CalDAV and Google (REST, ADR 0002). It covers discovering Calendars, incremental fetching (CalDAV `sync-collection`/ETags, Google sync tokens with 410 handling), and conditional create, update and delete. The interface must allow Microsoft Graph and ICS feeds to be added later without changing the sync engine.
- **Local Store** (ADR 0004): one SQLite database in the XDG data directory. For each Event it holds the fields FreeCal manages and its Unimplemented Fields: what the server holds about the Event beyond them, in a canonical form, so that every write sends them back (ADR 0017). The server's original text is not kept. It also holds the Calendar History (every Event Version, with the Snapshots it began and ended with, and the Snapshots, ADR 0018), the server's Current-Version Marks, where each Server Object is and its ETag, the Resolutions of Conflicts, Sync Errors, settings and app state. It holds no queue of changes to send and no copies of versions for Conflicts: both are read from the Calendar History (ADR 0019). Backups are compressed `.ics` files in the same directory. Only one running FreeCal opens a Local Store at a time (ADR 0005). A new Local Store is created with the Local Account, which the schema allows only once, and two Local Calendars: "Work" (shown) and "Home" (hidden). An existing Local Store never gets them again, so deleted ones don't come back. Their names are stored in English while v1 ships English only; once FreeCal is translated, the core picks them from the system locale when it creates the Local Store.
- **One running FreeCal** (ADR 0005): one FreeCal runs per user session, whatever its data directory. The core holds an exclusive file lock on the Local Store for its lifetime and refuses a locked one with `LocalStoreInUse`. The shell does the hand-off over D-Bus: a second launch hands its arguments and activation token to the running FreeCal, which comes to the front, and exits. In prose, say "second launch" or "another running FreeCal", never a bare "instance", which the glossary reserves against Occurrences.
- **Startup failures**: when the core can't open (a newer Local Store, `LocalStoreInUse`, a damaged Local Store), the window still opens and shows an error screen, translated from an error code through the i18n layer. Closing it quits FreeCal. The frontend holds its own defaults for every setting (`system` for each override) and draws the error screen with them. The window is created hidden and shown once the core has sent the settings or a startup failure is known, so that it never flashes the wrong theme.
- **Untrusted content**: every stored field is treated as hostile, whatever its origin: Event fields, Account and Calendar names, server error text and the names of files waiting to be imported. A Local Calendar can hold imported Events and a Backup restore can bring back anything, so the rule never depends on where data came from. The aim is that no such text can run code, change a file or request, or carry markup into the window, a notification or the tray.
  - **Descriptions are plain text** in v1. The core turns a description into structured content: paragraphs made of text pieces and link pieces. HTML (Google descriptions, `.ics` imports) is converted in the core: `<br>` and `<p>` become line breaks, `<a href=u>x</a>` becomes a link piece, every other tag is dropped and its text kept. `X-ALT-DESC` is never read. The frontend only draws the pieces and never parses or renders HTML. The editor edits the plain-text form, which the core also provides. An untouched description keeps the text it arrived with; an edited one is written back as plain text, so formatting from Google is lost on that Event. Bold, italics and lists can be added later as new kinds of piece, without changing the safety model, because the text is kept as it arrived.
  - **Links**: in the description and the location, the core turns `http(s)://` and `mailto:` URLs into link pieces and drops links with any other scheme. Clicking one opens it in the system browser through the shell, which checks the scheme again on the Rust side. When a link's text differs from its URL, FreeCal first asks "Open <full URL> in your browser?". The window itself never navigates away from FreeCal.
  - **The window**: no `{@html}` and no `innerHTML`; FullCalendar's custom-content hooks build DOM nodes, not HTML strings. A file name in a message is set apart as a bidi isolate (U+2068…U+2069), so that direction marks in it can't reorder the words around it, such as an import's counts. The window never sees a path: the shell opens the file dialog and holds the file it reads. The CSP never gets looser for scripts or remote content (no `'unsafe-inline'` or `'unsafe-eval'` for scripts, no remote images); inline styles stay allowed for Svelte and FullCalendar. Capabilities stay minimal.
  - **The shell**: desktop notification bodies are escaped, because Linux notification servers interpret markup. Tray menu labels escape `_`, which the menu reads as a keyboard-shortcut marker.
  - **Files and requests**: `.ics`, CalDAV XML and SQL are only produced through a library's writer or bound parameters, never by building strings, so a title like `x\r\nATTENDEE:…` can't inject a property. Export `.zip` entry names made from Account and Calendar names are sanitized, so a Calendar named `../../.bashrc` stays in its folder. Import reads `.zip` contents in memory and never extracts them, within fixed limits: at most 10,000 entries, and at most 128 MiB for a file to import and for the `.ics` files in a `.zip` unpacked together, counted as they are unpacked rather than from the sizes the `.zip` claims (a heavy user's Google Takeout export, about 15,000 Events, unpacks to some 15–45 MB). Exceeding them makes a translated error entry.
- **Sync engine**:
  - A change the user makes is a new Snapshot at once (see Calendar History). Nothing records it as unsent: what to send is the difference between the Event Versions the user has and those the server last had (ADR 0019).
  - An Outgoing Sync sends that difference with conditional requests; an Incoming Sync fetches what changed on the server, incrementally. A Calendar has one sync activity at a time: each waits for the other.
  - An Incoming Sync compares per Occurrence what it fetched, the user's current versions and the versions with the server's Current-Version Mark, which are what the server held when FreeCal last looked. An Occurrence only the server changed follows the server; one only the user changed stays to be sent; one both changed to the same result agrees; one both changed differently is compared by field group: the times (with the time zone and the repeat rule), the title, the Location, the description and the Unimplemented Fields (ADR 0017). Where each group changed on at most one side, the two are combined, each group from the side that changed it (a Server Event Merge, below); where both changed the same group, or one side the times and the other any other group but the Unimplemented Fields, it is a Conflict, as are edit/remote delete and delete/remote edit. A change to a Recurring Event counts as a change to every Occurrence and is never combined with a change to one Occurrence, so a series edit against a remote Occurrence edit is a Conflict on the whole Recurring Event.
  - The server's changes are taken in at once, in one Database Transaction (ADR 0019): one Snapshot records every server version fetched (an Incoming Sync Snapshot), and those of Events only the server changed become current. Each Event combined follows as a Snapshot of its own with the combination (a Server Event Merge), which is sent like any change; a toast says so: “Standup was combined with a change on the server” with "Undo" and "Open", or “3 Events were combined with changes on the server” with "Show", which opens the History at that sync; also where the server changed only fields FreeCal doesn't show. Undoing a Server Event Merge brings back the user's version without the server's change. Each Event in Conflict follows as a Snapshot of its own in which it takes the server's version (a Server Event Replacement). Nothing is sent for it, and the user's version stays in the Calendar History. No Calendar ever stops syncing for a Conflict. A Conflict stays open until the user resolves it: keeping the server's version, restoring their own (an Undo of the Server Event Replacement, sent like any change), or changing the Event again. Each Resolution is recorded once and names the Snapshot that ended the Conflict, none exactly when the server's version was kept. A redo of a restore puts the server's version back and leaves the Conflict resolved.
  - A server Calendar enters the Local Store empty when the user adds it, and its First Sync is its first Incoming Sync: a Full Fetch, every resource fetched and taken in as one Incoming Sync Snapshot when all have arrived (ADR 0018). The same Full Fetch runs after the server resets a sync token and on every Incoming Sync of a server without ETags (ADR 0019). It also runs once a week per Calendar as Mark Reconciliation, in the background, to check FreeCal's record of what the server holds; where a resource's ETag is unchanged but its content differs from that record, any difference from the user's version is a Conflict, as it can't be known which side changed, with a Log line and nothing else (ADR 0019, "An untrusted base"). Interrupted by the network or by FreeCal closing, it starts again from the beginning at the next Incoming Sync. The window is never locked by it.
  - Before an Outgoing Sync sends, it checks the Mass-Change Guard (ADR 0019): if it would delete or change more than 10 Events and more than 5% of the Calendar on the server (both, so that a small Calendar isn't paused at every change), it sends nothing and the Calendar is paused, as a Sync Error. An Event isn't counted when its current version began with an import or a Backup restore and the server doesn't hold it yet: the import preview or the restore's confirmation was the approval, and the Snapshot's recorded origin is all that keeps it. Everything else counts: an undo or a redo, of an import too, many small edits made offline, or a fault in FreeCal. The Sync Error names the numbers and offers "Send", which runs that one Outgoing Sync unchecked; nothing stores the approval. To drop the changes, the user undoes them. A paused Calendar keeps taking in Incoming Syncs, and is no longer paused once what differs is under the thresholds. Incoming Syncs aren't checked: an Undo from the History takes one back.
  - Being offline is a Sync Status, not a Sync Error. It is decided per Account: a network-level failure (DNS, connection refused, timeout) makes that Account Offline, while an error response from the server is a Sync Error.
- **Overall status** (shown by the tray icon and the window's status indicator): Conflict if any Calendar has a Conflict; otherwise Sync Error if any Account or Calendar has one; otherwise Offline if there is at least one server Account and **every server Account** is Offline; otherwise Syncing if any is syncing; otherwise Online and synced. If only some server Accounts are Offline, only the sidebar marks them. "Syncing" is shown only when a sync has run for more than about 1 second, or when the user started it (sync now, the shortcut, the tray menu), so routine polls don't make the display flicker. The Signals are still sent straight away; only the display waits.
- **Sync timing**: every 5 minutes while the window is open, every 15 minutes in the background, plus syncs on window focus, on wake from sleep and after local edits. Hard-coded for v1 and may become settings later. FreeCal also listens to the system's network status through the NetworkMonitor portal. When the network comes back, it syncs right away, which sends what is unsent. While there is no network at all, it skips polls and marks every server Account Offline without trying. Otherwise, whether an Account is Offline is still decided by its actual requests.
- **Calendar History** (ADRs 0018 and 0020): the Events of all Calendars at one moment are a Snapshot, and every change makes a new one from the one before, on one line: an action of the user, an import, a Backup restore, an Undo, an Incoming Sync Snapshot (in Read-only Calendars too), a Server Event Merge and a Server Event Replacement. A step that changes several Calendars together, such as a move, or an import or a restore into several, is one Snapshot. A Calendar enters empty, a server Calendar's Events following with its First Sync's Incoming Sync Snapshot; imports and restores never create Calendars. FreeCal shows the newest Snapshot; the server's Current-Version Marks record what each server holds. Snapshots older than 90 days are dropped, apart from those ADR 0018 keeps: for versions the server still holds, for open Conflicts, and those a kept Undo takes back.
  - An Undo takes back one earlier Snapshot as a new Snapshot (ADR 0020): what that Snapshot changed goes back to how it was before it, and the changes since stay. It is compared per Occurrence, as the two sides are (ADR 0019), and sent like any change, checked by the Mass-Change Guard, which counts every Undo, an import's too. Where something the Snapshot changed has changed since, the Undo combines them by the field groups of sync (ADR 0019), each group from the side that changed it. Where it can't combine them, as the same group or the times against another group changed, in any Calendar it spans, nothing is undone and a toast says why, naming the later change: “Couldn't undo "Move Standup": Standup was changed on the server since” or “… by "Resize Standup"”, with "Open Standup" and "Undo both changes", which undoes it with the earlier state winning. Where the later change is a Server Event Replacement, the toast says “Standup was replaced by the server's version” and offers "Restore my version" instead of "Undo both changes". An Undo that would change nothing is refused too. The Calendar History is only added to: nothing waits, and an Incoming Sync after an undo is taken in as after any change.
  - Ctrl+Z undoes the user's own newest change still in effect, across all Calendars, and a restart doesn't reset it: an action of the user, an import, a Backup restore, or "Stop waiting and mark read-only". It passes over Incoming Sync Snapshots (First Syncs too), Server Event Merges, Server Event Replacements, Undos and the Snapshots only in Calendars marked read-only. A refused Ctrl+Z stays there: the next press is refused again until the user undoes both changes; older changes can still be undone from the History. Ctrl+Shift+Z and Ctrl+Y redo: they undo the newest Undo still in effect, however it was made, until the user makes a change of their own; syncs don't end that. A refused redo offers "Redo over the server's change". No undo asks first: a toast after each says what was undone, a change on the server too ("Undone in “Work”: the change on the server from 14:02, 3 Events, also on the server"), and offers "Redo"; a toast after each redo says what was redone, without a button. A Snapshot spanning several Calendars is undone whole; where one of them is marked read-only, such as a move into it, Ctrl+Z stops there and the undo is refused, naming that Calendar, without "Undo both changes". In Read-only Calendars, Incoming Syncs still take the server's changes in, and changes made before the mark are still sent. A Calendar whose writes are refused but that isn't marked is undone like any other, and its changes wait. Undo and redo change Events with guests like any Event until the attendee features (ticket 126).
  - The ⋮ main menu offers "History…": the Snapshots of all Calendars, newest first, each with its time, its Calendars, what made it (the user's action, an import, a Backup restore, changes from the server, "replaced by the server's version", "combined with a change on the server", an Undo naming what it took back) and how many Events it changed, with filters for one Calendar and for "only my changes"; the Incoming Sync Snapshot, Server Event Merges and Server Event Replacements of one Incoming Sync show as one line that opens. A Calendar's menu in the sidebar opens it filtered to that Calendar. Each line but those spanning a Calendar marked read-only offers "Undo", a First Sync's too, which undoes that Snapshot whole, in all Calendars it spans, a change from a server too, as above, and with the same toast. Snapshots that an Undo has taken back show it.
  - An Event's details offer its History: the Event's versions, read through the Calendar History, without an undo of its own. A change in the Unimplemented Fields alone shows as "changed in fields FreeCal doesn't show" (ADR 0017). Before a Server Event Merge it shows the server's version as it was before combining, "on the server, before combining" (ADR 0018).
- **Backups**: daily, compressed, skipping Calendars unchanged since the last Backup, 14 kept. They include the Local Account's Calendars. A restore asks for a date and lists, for each Calendar with a Backup, its newest Backup from that date or before, Calendars that are gone included, each with a Target Calendar: by default its own Calendar while it exists, otherwise the writable Calendar with the same name, otherwise none. Opened from a Calendar's menu, only that Calendar's Backup has a Target Calendar at first; from the app menu, every Calendar that still exists has its own. A Calendar can be the Target Calendar of one Backup only, and a Read-only Calendar of none. A restore never creates a Calendar: for a Backup whose Calendar is gone, the user cancels, creates one and restores again. The Target Calendars then hold their Backups' Events and no others, in one Snapshot spanning them, undone like any other change; a restore over an Event with an open Conflict resolves it, as any change of the user's to the Event does.
- **Recurrence**: the core expands Recurring Events into Occurrences for the requested range. The frontend never interprets repeat rules. Editing supports this / this and following / all, and Exceptions are preserved where possible.
- **Attendees**: attendee features come before v1 (US-151); their design starts with a grilling session (ticket 126). Until they come, any Event with attendees other than the user is read-only, and its details say "has guests" (edit it in Google or on the server for now). Attendee data is never shown and always preserved.
- **Choosing server Calendars**: when a CalDAV or Google Account is added, FreeCal lists the Calendars it discovered as Available Calendars and the user chooses which to add; adding them stores them at once and their First Syncs run as their first Incoming Syncs (see "Adding server Calendars" under the frontend). Calendars that appear on the server later stay Available Calendars until the user adds them. The Account's line in the sidebar offers "Manage Calendars…", which fetches the server's current list and lets the user add Available Calendars or remove Calendars. Removing a server Calendar from FreeCal deletes only its local copy, never touches the server, and makes it an Available Calendar again.
- **Writability** (ADR 0019, "When the server refuses changes"): a Calendar is read-only when it carries the read-only mark. The user sets it, or FreeCal does when a Calendar is added whose server doesn't allow changes. The mark only stops new changes: changes made before it and not yet sent are still sent, so a change the user regrets is undone before marking. The user can remove the mark only after FreeCal has asked the server and it didn't say no (a server that says nothing counts as allowing); while the server can't be reached, removing it fails with a message. A server that stops accepting changes later, found by a write it refuses for lack of privileges, makes it like being offline in one direction: the Calendar has the Sync Error "writes refused", stays editable, and its changes wait. Every Poll then reads whether the server allows changes again, until it does or the Calendar is marked. The bar for "writes refused" offers "Stop waiting and mark read-only", which after a confirmation ("Discard 3 unsent changes in “Work” and mark it read-only? You can remove the mark once the server accepts changes again.") drops the waiting changes, takes the server's state as a change of its own, which Ctrl+Z can take back once the mark is removed, and sets the mark; on a Calendar already marked it offers "Stop waiting". FreeCal also reads whether the server allows changes on a sync the user starts and on the syncs at launch.
- **Moves across Accounts**: implemented as create in the target, then delete in the source, recorded as one Snapshot spanning both Calendars. The warning is shown only when the Event has Provider-specific details that the target can't hold.
- **Import/export**:
  - Import accepts `.ics` and `.zip` of `.ics` files; CSV is not supported.
  - Time zone names in imported and synced data that aren't IANA names are mapped to IANA names: a path ending in one (`/mozilla.org/20050126_1/Europe/Berlin`), a Windows name as Outlook writes it (`W. Europe Standard Time`, through CLDR's `windowsZones` table), or a custom `VTIMEZONE`'s `X-LIC-LOCATION`. A time whose zone can't be mapped is treated like a floating time: pinned by ADR 0007 and counted in the import preview. UTC times keep their instant and get the file's `X-WR-TIMEZONE` when it names one, as Google's exports do, otherwise UTC.
  - Running an import looks up again which Events the Calendar has, by UID: "update" gives them the imported version (a version that still has no time zone at either end keeps the zone pinned before, ADR 0007 rule 2), "skip" leaves them, "copy" adds the imported version with a new UID. An import is one Snapshot, undone with Ctrl+Z while it is the newest; later, a Calendar's History goes back to before it, which takes that Calendar's later changes with it. An Event the user changes the time of loses its pinned mark (ADR 0007 rule 4).
  - Export produces a single `.ics`, or for everything a `.zip` with one `.ics` per Calendar organised by Account.
  - Google-only fields are written as `X-` properties and read back on import.
  - Existing UIDs trigger one update / skip / copy choice per import; "update" is chosen by default.
  - Each `.ics` of a `.zip` gets its own Target Calendar: by default the writable Calendar with the same name (the file's `X-WR-CALNAME`, otherwise its file name without `.ics`), otherwise none, which leaves the file out. The preview can change each or leave it out, and two files can share one Target Calendar. An import never creates a Calendar: for a file without a Calendar, the user cancels, creates it and imports again. The whole `.zip` is one import and one Snapshot spanning its Target Calendars, undone whole.
  - Importing into Read-only Calendars is not offered.
  - **Opening files**: FreeCal accepts `.ics` and `.zip` files as command-line arguments (macOS: open-file events) and registers as a handler for `text/calendar` in its `.desktop` file. Each file goes through the normal import flow (choose a Calendar, preview, confirm) and is one undoable import. The core reads a file's contents as soon as it arrives, because mail clients may delete their temporary copy, and holds it as a waiting import until it is imported or dismissed. Waiting imports keep their arrival order; a file that can't be read or parsed becomes an entry with a translated error naming it, and doesn't stop the others.
- **Time zones and locale**:
  - The Display Time Zone is the system time zone unless the user overrides it in Settings, and is shown in the UI. While an override is set, changes to the system time zone are ignored. New Events default to it, and each Event can have its own time zone.
  - The date format is read from the system locale. Weeks start on Monday by default, whatever the locale; Settings can switch to Saturday or Sunday. The grid, the week view's range and the date field's popover read one shared first-day-of-week value. It only affects display: repeat rules keep their own week start (`WKST`), and new rules get the RFC 5545 default, Monday. The clock is 24-hour by default, whatever the locale; Settings can switch it to 12-hour. All time formatting (grid, details, editor) reads one shared clock value. Settings can override the locale's date format through a "Formats" region (a curated list of about 30, names from `Intl.DisplayNames`, each shown with 31 December of the current year in short and long form), formatted with `Intl.DateTimeFormat`.
  - All UI strings go through an i18n layer; v1 ships English only.
- **Frontend**:
  - **Visual style**: neutral and flat (in the style of Notion Calendar and shadcn/ui), defined once as a shared base in `app.css`: colour, spacing and font tokens with a light and a dark value each, outline, solid, danger and ghost buttons, inputs, a menu and a shared modal `Dialog` that every modal dialog uses. Calendar colours are the only strong colours; everything else stays near-greyscale, so that markers on sidebar rows stay readable. The system UI font is used, with sizes in `rem` and no fixed heights around text, and long names cut off with "…". Icons come from `@lucide/svelte`. The grid uses FullCalendar's `classic` theme. Its palette variables are pointed at FreeCal's tokens, so the grid has the window's light and dark colours and neutral accents. Text on a filled Event is near-black or white, whichever contrasts more with the Calendar colour. Titles that don't fit end in "…". Light or dark follows the system unless overridden in Settings.
  - **Sidebar**: each Calendar row has a colour dot (filled when shown, a ring when hidden) and toggles on click. Its ⋮ menu (also on right-click, the context-menu key and Shift+F10) offers the colour swatches, Rename, Show only this and Delete. Deleting asks in a modal dialog. A row's tooltip names the Calendar and says whether it is shown and what a click does. When the Local Account has no Calendars, its section shows a hint pointing to "+".
  - **Main menu and Settings**: a ⋮ main menu at the right end of the toolbar offers Settings…, History…, About FreeCal and Quit. Settings (also Ctrl+,) is a modal dialog with the sections Date & time, Appearance and Background, in that order. Background holds "Keep running in the system tray" (background running) and "Start at login", with no hint; FreeCal shows its tray icon only while background running is on. Every change takes effect and is saved at once. "Settings" is the word everywhere, including the UI.
  - **Quitting**: Quit (main menu or tray) and closing the window when that quits FreeCal first try to send unsent changes for a few seconds under "Working…". If changes are still unsent, a dialog lists the Calendars and reasons, with "Cancel" focused and "Quit anyway". Logout and shutdown never wait for this; what is unsent stays in the Local Store and is sent after the next start.
  - FullCalendar v7 (MIT standard edition) is wrapped in a `CalendarGrid` component. It only displays the Occurrences it receives and reports user actions (range selected, Event clicked, moved, resized). FreeCal owns all state, including which Event is selected.
  - When an Occurrence is dropped, the frontend asks for the recurrence scope and either commits the move or reverts it.
  - Keyboard shortcuts are handled by FreeCal, not FullCalendar.
  - A status indicator in the window shows the overall status (the same as the tray icon), plus how long ago the last finished sync was: "Synced 3 minutes ago", or for another state "Offline · last sync 3 minutes ago". The time is in the largest whole unit (seconds, minutes, hours, days), rounded half up, so 1 h 25 min is "1 hour" and 1 h 31 min is "2 hours"; under a minute it shows no time, just "Synced" or the state, so nothing counts up every second. The icon sits at the left end of the toolbar, before Today, with the text as its tooltip at all times. The text sits at the bottom of the sidebar, left-aligned with the Calendar names; while the sidebar is hidden, only the tooltip shows it. The sidebar draws marks, not text, at about the size of its text: an Account's or a Calendar's line carries the Status Mark of every state that applies to it, side by side (Conflict, Sync Error, Offline, Syncing), and none when there is nothing to report. Each state is shown on the line it belongs to and not repeated: Offline and an Account's own Sync Errors on the Account, a Conflict and a Calendar's own Sync Errors on the Calendar. A click on a Calendar's Conflict mark opens the Conflict list with that Calendar's Conflicts. A click on a Sync Error mark shows its message and its action (log in again, retry, send what a paused Calendar holds back). The Offline and Syncing marks have a tooltip only; the Syncing mark follows the overall status's delay rule, and its tooltip and the status indicator's show how far a sync that takes long has come. After the Status Marks, a Calendar's line carries the Unsent Mark (an hourglass) while any of its Events is unsent, with the reason as its tooltip (Offline, writes refused, or waiting to be sent) and no count; a click on it does nothing. Read-only Calendars carry a lock.
  - **Adding server Calendars**: the dialog lists the Available Calendars and the user ticks the ones to add; "Add" stores them and closes it at once. Each appears in the sidebar, empty, with the Syncing mark, until its First Sync has finished; then its Events appear all at once. The mark's tooltip says "Loading for the first time" with the progress (what is counted depends on the Provider), and after a Sync Error or while Offline the mark's tooltip adds "Not loaded yet"; a retry is the Sync Error's own. Both texts are read from the Sync Status's last finished sync, none yet. Removing the Calendar from FreeCal cancels its First Sync. The window is never locked, and the user can create Events in a Calendar still loading.
  - **A change of the user's replaced by the server's is never missed**, and FreeCal is insistent about it while syncing goes on. While any Calendar has an open Conflict, a bar across the top of the window says so ("2 changes in “Work” were replaced by the server's"; for several Calendars, how many and the total), with "Review", which opens the Conflict list. The bar can't be dismissed; it goes when the Conflicts are resolved. A toast says so when it happens with the window open. There is no dialog. Each Conflict in the list offers "Keep the server's version" and "Restore my version", and the list "Keep all" for a Calendar.
  - **Event chips stay sparse**: a chip carries at most one mark, at its right edge: the Conflict badge, or else the Unsent Mark on an Occurrence with unsent changes. The mark takes room from the title and is never dropped, on small chips too. In the month view, timed Events show a dot in the exact Calendar colour, then their time and title, with the text in the normal colour (as the `classic` theme draws them). The pointer is a hand over the whole chip and its text can't be selected; empty slots keep the arrow. The Unsent Mark appears once the change has waited more than a few seconds, or straight away when its Account is Offline or its Calendar's writes are refused, so that it doesn't flash on every edit. It is a mark and not a paler colour, because a faded look already means past or tentative in Google-like calendars and a colour change is lost on light Calendar colours. Read-only and "has guests" are not shown on chips. The grid simply offers no move or resize for those Events.
  - **Dialog close button**: every plain `Dialog` has a ✕ at the top right that does the same as Escape. Confirmations (`alertdialog`) have none, because an explicit choice is their point. Dialogs have a maximum height and their body scrolls, so they fit at the minimum window size.
  - **Event details** are a centred modal `Dialog`, not a popover. A row of icon buttons sits at the top right, above the title: Edit (pencil), Delete (trash) and Close (✕); for read-only Events only ✕. Each icon has a tooltip and an accessible name through `t`. A click on the backdrop closes the details. Delete deletes at once, and the toast says "Event deleted"; for an Event that repeats it first asks whether to delete the Occurrence alone or all.
  - **Toasts** appear at the bottom of the window. A confirmation ("Imported …", "Event deleted", "Undone: …") disappears after 5 seconds, paused while the pointer is over it or it has keyboard focus. A toast reporting a problem, such as an undo that left an Event in two Calendars, stays until dismissed. A new toast replaces the one showing.
  - **Event editor**: keeps its text Cancel and Save buttons. Closing it (✕, Cancel, Escape) asks "Discard changes?" only when the draft differs from what it started with. Changing the start date or time moves the end by the same amount, keeping the Event's length; changing the end changes only the end.
  - **Time field**: a combobox of FreeCal's own instead of the native `type="time"` input (WebKitGTK's can't be given a picker or custom keys). It accepts `14`, `1430`, `14:30`, `14.30`, `14h30`, `2:30p`, `2.30 pm` and any minute, and normalises on Enter, Tab or blur; invalid input stays, marked red, and blocks Save with the "incomplete" message. `a` and `p` anywhere in the field set AM or PM in both clock modes (on a 24-hour clock `p` turns 2:00 into 14:00, `a` the reverse) and are not typed. On a 12-hour clock an hour from 13 to 23 becomes PM. The list has 15-minute steps and scrolls to the current value. When start and end are on the same day, the end list starts at the start time and shows durations ("15:30 (1 h 30 min)"); otherwise it shows the whole day. ↓ opens the list; while open, ↑/↓ move, Enter picks and Escape closes only the list. ↑/↓ never step the time.
  - **Date field**: FreeCal's own instead of the native `type="date"` input, whose GTK popover draws a grey band over the field and which shows US order whatever the locale. Typing follows the order of the date format, with `.`, `/` or `-` as separators, and ISO `2026-10-04` always works; `4` means the 4th of the shown month and `4/10` that day in the shown year; two-digit years mean 20xx; no words like "tomorrow". Invalid input stays, marked red, as for times. A popover (ARIA date-picker dialog) shows a month grid with ‹ › for months, today ringed, the selected day in the accent colour and weeks starting on the first-day-of-week setting. ↓ opens it; arrows move by day, PgUp/PgDn by month, Enter picks and Escape closes only the popover. The end-date popover marks the start date, highlights the days between start and end and disables the days before the start; the start-date popover shows the end date and the range dimmed, with every day selectable, since the end follows the start.
  - **Window size**: the window has a fixed minimum size (880×560, set in `tauri.conf.json`) at which the sidebar at its default width and the week view still fit. A tiling window manager can still make the window smaller (KWin on X11 does so on purpose for quick-tiled windows, KDE bug 434615). The content then keeps its minimum size and the page scrolls.
  - **Event details** show the Unsent Mark and "Not yet synced: <reason>" for unsent changes, and say when the Event is read-only, giving the reason: a Read-only Calendar, or "has guests" with the hint to edit it in Google or on the server. When FreeCal couldn't read everything of the Event's resource on the server (ADR 0017, the round-trip check), the details say so: "FreeCal couldn't read everything in this event. Changing it here may remove data that other apps stored in it." The Event can still be changed.
  - Trying to drag or resize a read-only Event shows a short message saying why it can't change.
  - On an "Occurrences changed" Signal for a shown Calendar, the frontend fetches the visible range again and keeps the current selection. An open Event editor is never overwritten: the user's draft stays, and saving it is an ordinary edit. If the server's version has replaced it by then, saving the draft is a change of the user's to the Event, sent as made, and resolves the Conflict (ADR 0019).
- **View state**: month view on first launch, then the last-used view, always opening on today. There is no setting for the first-launch view.
- **Tracking today**: a mode, like "follow my position" in a map app. The Today button is a toggle, and its pressed state *is* the mode.
  - It is turned on when FreeCal opens and when the user presses Today, which also jumps to today.
  - It is turned off when the user un-presses Today (the view stays where it is) or changes the date: prev/next, the date picker, or clicking a day number. This holds even if the new period also contains today.
  - It stays on when the user switches between day, week and month, scrolls the time grid, selects, creates or edits Events, or opens dialogs.
  - When a "Date changed" Signal arrives, the view jumps to the period containing the new today only while tracking. Otherwise only the today highlight moves.
- **Desktop interfaces** (fakeable in tests):
  - **Keyring**: Secret Service via libsecret; report an error if it's unavailable.
  - **Notifications**: reminders with snooze and dismiss; while the window is closed, one notification per new Sync Error and one per Calendar when the server's version replaces changes of the user's ("“Work”: 3 of your changes were replaced by the server's"), with none for further Conflicts in that Calendar until its open ones are resolved.
  - **Tray**: StatusNotifierItem through Tauri, on its tray crate's KSNI backend (AppIndicator gives no click events). A left click opens the window; a right click opens the menu. One icon showing the overall status (see Sync engine). The menu offers Open FreeCal, Sync now, problem lines (each Calendar with Conflicts and their number, then each Sync Error; at most 8, then a line "n more…" that opens the window) and Quit.
  - **Tray detection**: a D-Bus check for a StatusNotifierWatcher with a registered host, made at every window close. A StatusNotifierWatcher that comes up while FreeCal runs, as at a start at login, gets the tray icon then.
  - **Autostart**: through the Background portal where available; off by default.
  - **File hand-off**: forwarded arguments from a second launch, and open-file events on macOS, both feed the same "add waiting imports" core operation.
  - **Network status**: the NetworkMonitor portal (it also works outside Flatpak).
- **Google OAuth**: browser-based login with a loopback redirect and PKCE.
  - The shared FreeCal client is set to "In production", unverified, for the developer and testers. Unverified clients have a lifetime cap of 100 users.
  - The public 1.0 offers "bring your own client" with a guided setup.
  - Verification comes after 1.0.
- **Packaging**: before 1.0, `.deb`, `.rpm` and AppImage built by Tauri. All OS integration goes through portal-friendly APIs so that the Flathub release at 1.0 needs no code changes.
- **License**: GPLv3 (ADR 0003). All dependencies must be GPLv3-compatible.

## Testing Decisions

- **What makes a good test**: it checks behaviour visible through a seam (what the user or an external server would see), never internal structure. Tests must keep passing through refactors that don't change behaviour.
- **Seam 1: the core application interface** (the main seam). Almost all behaviour is tested here:
  - CalDAV sync against a real **Radicale** server started per test run.
  - Google sync against a **fake Google HTTP server** that mimics the Calendar REST API (sync tokens, ETags, 410 "token expired", permissions). The real Google Provider code is exercised.
  - A real SQLite database in a temporary directory, never mocked.
  - A controllable clock for polling, reminders, the Calendar History's retention and Backup timing.
  - Recording fakes for the keyring, notifications and tray, a controllable fake network status and system time zone, and a recording Signal subscriber.
  - Covered here: changes made offline and sent later, every Conflict scenario, the Mass-Change Guard's thresholds and "Send", with imports and Backup restores not counted and their undo counted, the Calendar History (a Snapshot per change, Snapshots spanning Calendars, Ctrl+Z passing over Incoming Sync Snapshots and Server Event Replacements, an Undo refused by a later change on the server or of the user and "Undo both changes", redo after a sync and a refused redo, undoing a sync from the History, restoring and redoing at a Server Event Replacement and the Resolution each writes, the refused Ctrl+Z offering "Restore my version", an Undo combined with a later change where the managed fields changed on one side only, Ctrl+Z passing over Snapshots only in read-only Calendars and refused at one spanning a read-only Calendar, dropping after 90 days with open Conflicts and the Snapshots kept Undos take back staying), the server's Current-Version Marks as the base of the comparison, a Conflict ending at once with the server's version, a Server Event Replacement per Event in Conflict, a Server Event Merge where different field groups changed, one sync activity per Calendar, a First Sync as a Full Fetch into a Calendar stored empty, an Event created there meanwhile sent after it, an interrupted one starting again at the next Incoming Sync, an Undo of its Incoming Sync Snapshot asked by the Mass-Change Guard, the Store Check run after every scenario (ADR 0018), Mark Reconciliation after 7 days and a Conflict where the base is untrusted, never an unsent edit replaced, Backup creation, skipping and restore, read-only enforcement (server-reported, user-set, the pre-1.0 default, "has guests"), Unimplemented Fields kept across edits, moves between Calendars and undo (ADR locked Local Store being refused, and waiting imports (contents read on arrival, arrival order, error entries, "Waiting imports changed").
  - Conflict and Mass-Change Guard scenarios are written test-first.
- **Seam 2: the frontend against a fake core interface**. Thin Svelte component tests (Vitest) for `CalendarGrid` and the Event editor. They check that user actions (click and drag to create, drag to move or resize, the recurrence scope prompt including cancel-reverts, keyboard shortcuts, disabled editing for read-only and "has guests" Events, including the message on a refused drag) produce the right core calls. The fake core can also emit Signals, so tests check that the view re-fetches on "Occurrences changed", that the status indicator and sidebar markers follow "Sync status changed", that an open editor's draft survives a re-fetch, that an import preview for a waiting import opens only when no modal dialog is showing, that the Unsent Mark follows its delay rule, that the Conflict bar follows its rules, that a Calendar with no finished sync yet shows "Loading for the first time" or "Not loaded yet", that tracking today starts, ends and reacts to "Date changed" as specified, that each setting is written once and applied, that the frontend's defaults are used on a startup failure, and that the quit warning appears only for changes still unsent.
- **The hostile test Event**: one shared fixture, available at both seams, with a payload in every field: HTML and script (`<img src=x onerror=…>`, `<script>`), an `.ics` property injection (`\r\nATTENDEE:…`), notification markup, `_` for the tray, `../` for file names, and links with allowed and disallowed schemes. Every ticket that shows, writes or sends Event or Calendar text runs it through its path (see "Untrusted content").
- **The Provider interface is not a test seam.** Tests never replace a Provider.
- **No end-to-end tests of the real Tauri window in v1.** A manual release checklist is run against a real Google test account before each release; Nextcloud tests come later.
- **Prior art**: none. This is a new codebase, so these tests set the pattern.

## Out of Scope

- ICS feed subscriptions, Microsoft Graph / Outlook, Exchange EWS, GNOME Online Accounts, vdir folders.
- Settings for sync timings, retention values and the default view; the secondary time-zone column; a keyboard shortcuts overview.
- A toast offering Undo after each change.
- Moving Events with the keyboard, natural-language quick-add, search, editing reminders, upcoming Events in the tray menu.
- Translations other than English.
- Tasks (VTODO / Google Tasks) and contacts (CardDAV / Google People).
- Google OAuth verification of the shared client (after 1.0).
- The Flathub release (at 1.0), Snap and AUR packaging by the project.
- FullCalendar Premium features (timeline, print).
- Automatic copies beyond the Backups; system backups are expected to cover the data directory.

## Further Notes

- Build order: the **Local** vertical slice first (grid, editor, Local Store, Calendar History, Backups, import/export), then **CalDAV** (developed and tested against Radicale), then **Google**.
- Expected disk usage is about 30 MB for a typical user (about 3,000 Events) and about 150 MB for a heavy user (about 15,000 Events), dominated by Backups.
- The Flathub manifest will need permission to talk to `org.kde.StatusNotifierWatcher` over D-Bus.
- The second-launch hand-off and macOS open-file events are checked by hand in the real app; their code is plumbing into the "add waiting imports" operation, which is tested at the core seam.
- Once frontend code exists, add a rule to `CLAUDE.md` that Svelte code uses Svelte 5 runes only, because AI-generated code often slips into Svelte 4 syntax.
- The shared unverified Google client is a temporary measure with an explicit end point (verification).
