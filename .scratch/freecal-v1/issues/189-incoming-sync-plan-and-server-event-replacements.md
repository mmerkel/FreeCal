# 189: The comparison against the server's marks; Incoming Sync Snapshots and Server Event Replacements; Propagate goes

**What to build:** An Incoming Sync compares what it fetched with the user's current versions and the server's marks through 177's `compare_event` (ADR 0019) and writes one Incoming Sync Snapshot per Calendar. For an Event in Conflict the server's version becomes current at once and the User's Version ends, a Server Event Replacement. No Calendar stops syncing. Propagate comes out. Old ticket 152 (`git show design/snapshot-line:.scratch/freecal-v1/issues/152-comparison-and-incoming-sync-snapshots.md`) as written. Recording Conflicts is 190, resolving them 191, the Server Event Merge 198.

- **Plan, then write** (layout, "The Incoming Sync"): inside one Database Transaction, read the server's marks and the current versions of the fetched UIDs, compute the Incoming Sync Plan (`IncomingSyncPlan`, `sync/plan.rs`, pure) with `compare_event` per UID (`Base` = the versions with the server's mark, `Ours` = the current ones, `Theirs` = the fetched ones), then the `IncomingSyncWriter` (`history/incoming.rs`) writes it. Only that writer moves the server's marks, and it has no operation that moves marks alone. `incoming.rs`'s `mirror_and_propagate` becomes fetch → plan → write; the First Sync, until 194, goes the same way with an empty `Base`.
- **The outcomes per UID:** only the server changed it: it follows the server; only the user: it stays to be sent; both to the same result: they agree, and the server's mark moves to the user's row; both differently: a Conflict of the whole UID (177's rule for Recurring Events included). Until 198, an outcome `compare_event` could combine is treated as a Conflict too. "Changed" compares content, so an edit back by hand to what the server has is no change; the Unimplemented Fields count like any field.
- **One Incoming Sync Snapshot per Calendar,** in one Database Transaction that no code may split: the server's versions of what the server alone changed begin with it; for a UID in Conflict, a **Server Event Replacement**: the server's versions of every single Event of the UID begin with it and become current, carrying both marks, an edit against a deletion on the server too, and the User's Versions end with it, with no copy and no zero-length Event Version; the server's marks move to the fetched versions, with their ETags. A Snapshot that would change nothing isn't made. Nothing is sent for a replacement. The plan's Conflict branch is where 190 writes the Conflict's rows.
- **Unsent Changes. Glue until 192, named:** after the Incoming Sync, the Calendar's Unsent Changes are set to the Combined Event Keys whose current Event Version differs from the one with the server's mark, keeping the time and reason of those that stay.
- **What comes out:** Propagate (`event/mod.rs`'s pairing and `propagate_to_event_rows`) with its special cases for Unsent Changes, which made the old Conflict handling. The Sender's conditional writes stay; what the ETag tests below assert about the outcome no longer holds until 192 sends from the marks.
- **Until 190,** a replacement shows nothing beyond the server's version, and its User's Version is dropped after 90 days like any other (no real Local Store exists).
- **Tests:** each case of ADR 0019's list a unit test of `sync/plan.rs`; through the core interface against Radicale for the wiring: each outcome for an edit, a creation and a deletion on either side; the Unimplemented Fields changed on one side (followed or sent) and on both (replaced); a change to a Recurring Event against a change to one Occurrence (the whole UID replaced); changes to different Exceptions on each side both kept; an Undo not yet sent followed by another change on the server to the same Event (replaced, as for any edit); an Incoming Sync Snapshot followed by a second change on the server to the same Event (followed); two Events in Conflict and one the server alone changed in one Incoming Sync, all in its one Snapshot; an Incoming Sync whose only change is a replacement makes its Snapshot; one that changes nothing makes none; an edit against a delete on the server makes the Event go; an Undo of the Incoming Sync Snapshot limited to a replaced Event (181) restores the User's Version and sends it.
