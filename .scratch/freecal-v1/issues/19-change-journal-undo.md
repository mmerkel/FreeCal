# 19: Undo through the Change Journal

**What to build:** The user can see every change in the Change Journal as one timeline, undo any one of them, or undo everything in a Calendar since a given time, and can see and undo an Event's History from its details. Undo follows ADR 0009 and the rules of tickets 69 and 72.

**Blocked by:** 70, 72, 125

**Status:** ready-for-agent

**Effort:** M

- [ ] The Change Journal list: one timeline, newest first, of every Journal Transaction (the user's changes, imports including those into Local Calendars, syncs as "Changed on the server: 3 Events in Work", Conflict resolutions, Snapshot restores, undos)
- [ ] A Journal Transaction expands into its Events, each with Undo; the Journal Transaction has "Undo all" for the Events still not undone
- [ ] Undo one Journal Event Modification: the previous Event Version is written back under the same identity (original ID, all details), later changes to the same Events with it
- [ ] Undo everything for a Calendar since a given time
- [ ] A History button in the Event's details lists the Event's Journal Event Modifications, each with Undo
- [ ] Dangerous Undos ask first as in ticket 70; the confirmation is the Mass-Change Guard's approval, so the next sync doesn't pause the Calendar
- [ ] Undo sends "Occurrences changed"
- [ ] What Ctrl+Z undoes and Ctrl+Shift+Z redoes comes from the core, worked out from the Change Journal (the Undo History: the user's own Journal Transactions, not undone, newest first, across restarts; redo: the undos made since the user's last change), instead of the list the frontend keeps (`SessionUndo`, `src/lib/sessionUndo.ts`), so that an undo from the timeline or an Event's History counts at once

Moving it into the core leaves one source of truth. Strongest con: two more calls on the core interface, and the redo rule has to be stated in Change Journal terms. Its name ("Session Undo", proposed in ticket 70) is decided here.
- 2026-11-14: Core layer done (shell and frontend next). The core interface gains `change_journal()`, `journal_transaction_events(id)`, `event_history(event_id)`, `session_undo()` and the Undo Target `calendarSince { calendarId, since }`. Decisions, for review, each with its strongest con:
  - **Decision, for review:** Session Undo is worked out by the core from the Change Journal. Ctrl+Z undoes the newest Journal Transaction since FreeCal started that is a user action, an import or a redo and isn't wholly undone. Ctrl+Shift+Z redoes, by undoing it, the newest undo since the user's last change that isn't a redo and isn't undone. An undo is a redo when the Journal Transaction it was asked to undo is an undo that isn't a redo itself. Each step names the user action or import it is about (`userChange`), so the frontend keeps only its labels for the toasts. Con: a new stored link (`journal_transaction.undoes`); an undo whose target has expired counts as a plain undo.
  - **Decision, for review:** the session starts after the newest Journal Transaction at launch, held in memory. Con: if the 90-day removal empties the whole Change Journal while FreeCal runs (no change for 90 days), IDs start again at 1 and Ctrl+Z misses this session's changes until a restart.
  - **Decision, for review:** a whole Journal Transaction whose undo changed nothing (every Event skipped) leaves Session Undo, whichever button undid it (ticket 70's rule, now in the core's memory). Con: an undo from the list that skips everything also hides that change from Ctrl+Z.
  - **Decision, for review:** an undo from the list, a History or "since…" joins what Ctrl+Shift+Z redoes, if made since the user's last change. Con: Ctrl+Shift+Z can redo an undo the user made in the list, possibly of a sync.
  - **Decision, for review:** undoing a Calendar since a time picks every Journal Event Modification made then or later whose Event Version before or after is in that Calendar, each with what it brings along: the rest of a user action's or an undo's Journal Transaction, the Event Rows of its UID in an import's or an Incoming Sync's. Nothing to undo changes nothing. Con: the other half of a move between Calendars is undone too, and the Dangerous Undo names it only when it counts as a later change.
  - **Decision, for review:** an Event's History lists the Journal Event Modifications of every Event Row with its UID, in any Calendar: a Recurring Event with its Exceptions, and an Event moved across Accounts. Con: unrelated Events sharing a UID in two Calendars (one invitation in both) share a History.
  - **Decision, for review:** each listed Journal Event Modification carries what its Undo undoes: that Event for an import's or an Incoming Sync's, else the whole Journal Transaction (ADR 0009); none once undone. Con: in a user action's expanded list every Event's Undo undoes all of it; the frontend should offer only "Undo all" there (`undonePerEvent`).
  - **Decision, for review:** the list reads every Journal Transaction at once, newest first, with its number of Events (Event Rows, as ticket 72 counts), how many are undone, its Calendars and up to 3 titles; a Journal Transaction's Events are read when it expands. Con: no paging; 90 days of a busy Change Journal go in one call.
  - **Decision, for review:** a Journal Event Modification now stores the Calendar and title of the Event Version it made, so the list names created Events and the Calendars they went into. Trade-off: two more columns, instead of deriving them from the next Journal Event Modification of the Event, which breaks when one is missing.
  - **Decision, for review:** `TransactionOrigin` is now an interface type, `firstSync` included, though the list never has one. Con: a dead branch in the frontend's switch.
  - Box "Dangerous Undos ask first": the core's part holds (the confirmation is `undo(target, approved)`); the Mass-Change Guard on syncs is ticket 22, which must let an approved undo's Unsent Changes through. The box stays open until 22.
  - Conflict resolutions and Snapshot restores appear in the list once their tickets record them with a Transaction Origin of their own.
  - New terms: **Session Undo** (from ticket 70, kept): the user's own changes of this session that Ctrl+Z undoes, and the undos since their last change that Ctrl+Shift+Z redoes (`SessionUndo`, `session_undo()`). **Session Undo Step** (new term): the next Journal Transaction Ctrl+Z or Ctrl+Shift+Z undoes, with the user action or import it is about (`SessionUndoStep`). `ListedJournalTransaction`, `ListedJournalEventModification`, `JournalEventModificationKind` (created, edited, deleted) and `UndoTarget::CalendarSince` are named after existing terms; `journal::Session` is what the core remembers of the session.
  - Tests: `core/tests/change_journal_list.rs`, and `caldav_sync.rs` (`undo::an_incoming_sync_is_listed_in_the_change_journal_and_not_on_session_undo`).
- 2026-11-14: Undo reaches beyond a session, as the user decided: Session Undo becomes the **Undo History** (term agreed), worked out from the stored Change Journal alone, so a restart changes nothing. This replaces the core-layer decisions above about the session start and the in-memory pass-over. The core interface now has `undo_history()` instead of `session_undo()`. Changes:
  - The user's decision: a whole Journal Transaction whose undo changed nothing (every Event skipped) is marked so in the Local Store (`journal_transaction.undo_changed_nothing`), and the Undo History passes over it for good. Con: once its Calendar is writable again, Ctrl+Z still won't reach it; the list or History can undo it.
  - The user's decision: the kind of user action is part of its Journal Transaction: `TransactionOrigin::UserAction { action }`, with `UserAction` created, edited, moved (a drag or resize) or deleted, stored in `journal_transaction.user_action`.
  - **Decision, for review:** an Undo History Step carries the whole listed Journal Transaction of the user change it is about (`userChange`), not just its ID, so the toast names the action and titles without another call. Con: an import's toast can no longer name its file, which isn't stored; it names the titles instead.
  - **Decision, for review:** a stored user action whose kind FreeCal didn't write reads as an edit. Con: a wrong toast verb for a tampered row, nothing worse.
  - Ctrl+Z after a restart can undo a change the user has forgotten (the strongest con of the choice); the toast names what was undone, and Ctrl+Shift+Z brings it back.
  - New terms: **Undo History Step** (new term): the next Journal Transaction Ctrl+Z or Ctrl+Shift+Z undoes, with the user change it is about (`UndoHistoryStep`). `UserAction` names the kind of a user action. Session Undo, Session Undo Step and `journal::Session` are gone.
  - Tests: `core/tests/change_journal_list.rs` (`the_undo_history`: `outlasts_a_restart`, `names_the_kind_of_each_user_action`, and the pass-over now checked across a restart).
