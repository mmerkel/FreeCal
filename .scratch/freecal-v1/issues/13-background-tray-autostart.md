# 13: Background running, tray basics and autostart

**What to build:** Where a system tray exists, closing the window keeps FreeCal running in the background (on by default); without a tray, closing quits. A tray enabled while FreeCal runs is noticed at the next close. The user can turn background running off and turn start-at-login on. The tray menu offers Open FreeCal and Quit. Both options live in the Background section of the Settings dialog (ticket 33). Spec: US-103–US-108 and US-129.

**Blocked by:** 01, 33

**Status:** done

**Effort:** M

- [x] At every window close, a D-Bus check for a StatusNotifierWatcher with a registered host decides whether to keep running or quit
- [x] Background running is on by default and can be turned off, so closing always quits
- [x] Start at login is off by default and uses the Background portal where available
- [x] A StatusNotifierItem tray icon (works natively on KDE Plasma) with a menu: Open FreeCal, Quit; a left click opens the window, a right click the menu
- [x] When the window is re-created, the frontend subscribes to Signals first and then reads current state
- [x] Tray detection, tray and autostart are behind fakeable desktop interfaces with tests
- [x] The Background section of Settings has "Keep running in the background" and "Start at login" switches. The background switch is always enabled, with the hint "Needs a system tray; without one, closing quits", because a tray is only checked for at window close
- [x] Turning on start at login goes through the Background portal at the moment the switch is flipped (the portal may ask the user); if it is refused, the switch goes back off with a translated message

- 2026-11-10 (research, `docs/research/autostart-state.md`): keep the stored setting; the user confirmed it. Every app found that uses the portal from a Flatpak stores the choice itself, because the Background portal can't be asked whether autostart is on. For the shell layer:
  - Every `RequestBackground` call must send `autostart` with the stored choice: a call that leaves it out deletes the entry. Call the portal only when the switch is flipped, never at startup.
  - Outside a Flatpak, the portal needs FreeCal's app ID (from the launcher's systemd unit, or from `org.freedesktop.host.portal.Registry`, which is likely to be deprecated) and an installed `.desktop` file, and FreeCal must pass its own `commandline`, or the entry gets no `Exec` line (read from the code, not tested). A run from `cargo` has neither, so the XDG autostart file is also the fallback when the portal can't tell FreeCal's app ID.
- 2026-11-10 (implementation, layer 2 of 3: the shell). Decisions, for review:
  - **decision, for review:** for background running the window is destroyed, not hidden, so that it holds no memory in the background; Open FreeCal and a second launch create it again from `tauri.conf.json` (`reopen_main_window`, `src-tauri/src/main.rs`), and the frontend starts as at launch, subscribing first and then reading. Strongest con: reopening reloads the frontend, which takes a moment and loses what the window showed beyond the stored state (an open dialog, the scroll position).
  - **decision, for review:** start at login asks the Background portal first; outside Flatpak, when the portal didn't do it (no portal, or response 2 as without an app ID), FreeCal writes or deletes `~/.config/autostart/io.github.mmerkel.FreeCal.desktop` itself, the same file the portal writes (`StartAtLogin::set`, `src-tauri/src/autostart.rs`). Inside Flatpak only the portal counts. Refused (the user cancelled, or background running isn't allowed) is `StartAtLoginRefused`; anything else that fails is `StartAtLoginFailed`. Strongest con: outside Flatpak, a portal that failed for another reason (it couldn't write the file) is papered over by FreeCal's own write, so two writers own one file.
  - **decision, for review:** FreeCal doesn't call `org.freedesktop.host.portal.Registry.Register`, which is expected to be deprecated. Strongest con: a host build started from a terminal never gets an app ID, so it always takes the file path.
  - **decision, for review:** the autostart entry runs FreeCal's plain command, so at login the window opens as at any launch. Strongest con: the window pops up at every login; starting straight into the tray would need a tray check at login, when the tray may not be up yet (a follow-up if wanted).
  - **decision, for review:** tray Quit with the window there brings it to the front and emits `freecal://quit-asked`; with FreeCal in the background it quits at once, as ticket 18's comment asked.   - **decision, for review:** the tray menu's labels are English text in the shell, which has no translations. Strongest con: they won't follow the frontend's i18n until the shell gets one.
