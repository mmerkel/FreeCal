# 147: Undo and redo are Snapshots; the Change Journal goes

**What to build:** The third part of the Calendar History: Ctrl+Z makes an Undo, a Snapshot that takes back one earlier Snapshot (ADR 0020), and the Change Journal, the hash of an Event Version and undo per Event come out. This is step 1 of the order in which the old model goes.

- **An Undo** is a Snapshot whose origin names the Snapshot it takes back, written once, by a foreign key checked when the Database Transaction commits (`DEFERRABLE INITIALLY DEFERRED`), an edge of the drop's rule, so that the Snapshot it takes back is kept as long as the Undo is (ADR 0018, "Keeping and dropping"). Its content is ticket 167's comparison per Occurrence, with what the taken-back Snapshot left as what both are compared with, the current versions as one side and the versions it ended as the other; where nothing has changed since, the Event goes back to the version before, as a copy (ADR 0018). It is made in one Database Transaction for all the Calendars, through the one place that makes a change's Snapshot, so it is sent like any change.
- **One function takes back any Snapshot** it is given: Ctrl+Z's target, an Undo for redo, a line of the Calendar History (ticket 159), an Incoming Sync Snapshot limited to one Event to restore it (ticket 134). An Incoming Sync Snapshot can be taken back this way though Ctrl+Z never reaches one.
- **Limited to one Event** (ADR 0020): the function takes an optional UID, recorded beside the Snapshot the Undo takes back (a CHECK allows it only on an Undo). The Undo then takes back only that UID's Events, in every Calendar the Snapshot spans, so a move is taken back on both sides unless one side's Calendar can't be written. Everything else holds for it: it leaves out what it can't take back and asks first, it is combined by field groups, its redo an Undo of it. Ctrl+Z is never limited. The Store Check gains: a limited Undo's UID was changed by the Snapshot it takes back.
- **Where both changed** (ADR 0020): an Occurrence that the Undo and a later change both change is combined by ticket 167's field groups, each group from the side that changed it, as in sync; it is a Conflict, and the Event left out, where both changed the same group, the Unimplemented Fields too, or one the times and the other any other group but the Unimplemented Fields, or the Undo a whole Recurring Event and the later change one Occurrence. No extra Snapshot: the Undo's content is the combination.
- **What a Snapshot left behind,** what an Undo compares with, is the Event Versions ending with it that began before it, never a zero-length Event Version (ADR 0018); so an Undo of an Incoming Sync Snapshot brings back the user's version of an Event merged or replaced there, not the server's before it.
- **What it leaves out** (ADR 0020, "Asking first"): an Event the comparison finds in a Conflict it can't combine, or in a Calendar marked read-only or removed. The function first reports, writing nothing, what it would take back and what it would leave out, each Event with why: for a Conflict, the Occurrences and the first Snapshot after the taken-back one that changed each (its origin and, for the user's own, its description), so that the window can name it and, for an Incoming Sync Snapshot that replaced the Event, offer its restore; for a Calendar, which one and whether it is read-only or removed. For a move with one side left out, it reports what taking back the other side does: restore the Event in the origin, or delete it from the target. The caller then asks for the Undo of the rest, or with "over the later changes", where the version the taken-back Snapshot ended wins in every Occurrence changed on both sides ("Undo all over the later changes", "Redo all over the later changes"); the Undo records that it was made over a later change, for the Calendar History to show. Where nothing is left out, the caller makes it at once. Refused, writing nothing: an Undo that would change nothing, or of which Undos in effect already take back all (limited: that UID).
- **A move after a Calendar's removal:** a Snapshot of a move (an action of the user that records it, ticket 146), and an Undo or redo of one through the Snapshot it takes back, whose UID has Event Versions in one Calendar only, had its other side in a removed Calendar. It is reported as a move with that side gone, never taken back as a create or a delete.
- **Ctrl+Z's target:** the core says which Snapshot the next Ctrl+Z takes back: the newest of the user's own Snapshots in effect, across all Calendars, by when each was made. The user's own: an action of the user, an import, a Backup restore and "Stop waiting" (from ticket 166). Passed over: Incoming Sync Snapshots, the First Sync's among them, and so their Server Event Replacements and Merges, Undos, and a Snapshot of which every Event still in effect is in a Calendar marked read-only or removed, checked at each call. In effect: some UID it changed isn't taken back by an Undo in effect, whole or limited to that UID; Ctrl+Z on a Snapshot partly taken back takes back the rest. At any other Snapshot Ctrl+Z stops: the window undoes it or asks; nothing skips to the change before.
- **Redo** takes back the newest Undo in effect that isn't itself a redo (an Undo of an Undo), by the same function, however that Undo was made, passing over Undos of which every Event still in effect is in a Calendar marked read-only or removed. The core says which one; there is none once the user has made a change of their own after it. Syncs don't end it. Nothing is dropped when it ends.
- **The Calendar History is only added to.** Nothing is written beside the Undo's Snapshot; the redo path, its end and the Snapshots dropped with it don't exist.
- **The Sent Event Rows** name each Event Version by its row ID instead of its hash, as a row never changes.
- **What comes out of the core:** `journal_transaction`, `journal_event_modification` and their SQL (`core/src/store/sql/journal.rs`); the hash and its format; undo per Event and its search for changes in between (`core/src/journal/undo.rs`); the Change Journal's listings (`core/src/journal/list.rs`); the Undo History read from the Change Journal; the Dangerous Undo; the Transaction Origin, which the Snapshot's origin replaces; the 90-day removal of Journal Transactions (dropping Snapshots is ticket 148); ticket 145's carried ID column. What is left of `core/src/journal/mod.rs`, the running of a set of writes as one step, belongs to the Calendar History's module, and one such step makes one Snapshot.
- **What comes out of the core interface and the window:** `undo` with its targets, `change_journal`, `journal_transaction_events`, `event_history`, `undo_history`, and the Journal Transaction in the result of every change (`Changed<T>`); the Change Journal dialog (`src/lib/ChangeJournalDialog.svelte`) and its menu entry; the History button in an Event's details; the Undo button on toasts, whose target was a Journal Transaction. Ctrl+Z and Ctrl+Shift+Z call the new undo and redo, and a refusal shows as a toast with the core's reason in plain words; ticket 158 words the toasts and adds their buttons. The Calendar History window and the Event's History return with their own tickets.
- **Write Permissions** stay for now, under the Calendar History's module in place of the Change Journal.
- **The Store Check** gains: an Undo takes back an older Snapshot.
- **Tests:** `core/tests/change_journal.rs`, `change_journal_list.rs` and `undo_per_event.rs` are replaced by tests of the Calendar History through the core interface: undo and redo of each kind of change, of a move and of an import into several Calendars, across a restart; an undo leaving out an Event changed later by the user, with its name, then the rest taken back, and "over the later changes"; an undo combined with a later change to the Unimplemented Fields alone, and a Conflict where both changed them; Ctrl+Z passing over a Snapshot only in a read-only Calendar, checked again after the mark is removed; a move into a read-only Calendar restored in its origin only; a move whose origin, and one whose target, was removed afterwards, reported as a move, never as a create or a delete; Ctrl+Z reaching an import again after the rest was taken back; redo after a change of the user offered no more; a redo never offered for a redo; an Incoming Sync Snapshot taken back by its Snapshot; a Snapshot already taken back refused; a First Sync's Snapshot never taken back; an Undo limited to one Event of a move across Calendars and of an import, Ctrl+Z then taking back the rest of the import, and a limited Undo of an Event the Snapshot didn't change refused. The tests of undo reaching the server in `core/tests/caldav_send.rs` are kept and rewritten to Ctrl+Z. The prototype's walkthroughs 1, 2, 10, 11, 12, 13 and 18 (`core/prototypes/calendar-history.PROTOTYPE.html`) are cases to cover; 4, 7 and 8 (restore) are ticket 134's, 15 ticket 166's.
- **Docs:** `GLOSSARY.md` loses or revises the entries Change Journal, Journal Transaction, Journal Event Modification, Record a Journal Event Modification, Transaction Origin, Dangerous Undo, Event Row, First Sync and Local Store, and the lines in other entries that name them. `CODING_STANDARDS.md` follows where it names the Change Journal.

Spec: US-81, US-146, US-150; "Calendar History". ADRs 0018, 0020.

**Blocked by:** 146, 167

**Status:** ready-for-agent

**Effort:** M

- [ ] An Undo is a Snapshot naming the one it takes back, made by ticket 167's comparison, in all Calendars the Snapshot spans that can be written, in one Database Transaction
- [ ] Any Snapshot, a First Sync's too, can be taken back by the one function, Incoming Sync Snapshots included
- [ ] Where the managed fields changed on at most one side, an Undo combines with the later change; otherwise the Event is left out; what is left out, Events in read-only and removed Calendars too, is reported with why before anything is written; the rest, or everything "over the later changes", is taken back on request, and the Undo records it
- [ ] An Undo refers to the Snapshot it takes back by a deferred foreign key
- [ ] An Undo limited to one UID takes back that UID's Events in every Calendar the Snapshot spans; a Snapshot partly taken back stays in effect for Ctrl+Z
- [ ] The core names the next Ctrl+Z's Snapshot and the next redo's Undo by the rules above, checking writability at each call
- [ ] A move whose one side's Calendar is read-only or removed is reported as such and taken back on the other side only
- [ ] Redo takes back the newest Undo in effect until the user's next change; the Store Check passes after each step
- [ ] An undo and a redo in a server Calendar reach the server (tests against Radicale)
- [ ] The Change Journal's tables, the hash, undo per Event, the listings, the Dangerous Undo and the carried ID column are gone from the code and the schema
- [ ] The core interface and the window no longer name a Journal Transaction; the generated types are rewritten
- [ ] `GLOSSARY.md` and `CODING_STANDARDS.md` follow
