# 147: Undo and redo are Snapshots; the Change Journal goes

**What to build:** The third part of the Calendar History: Ctrl+Z makes an Undo, a Snapshot that takes back one earlier Snapshot (ADR 0020), and the Change Journal, the hash of an Event Version and undo per Event come out. This is step 1 of the order in which the old model goes.

- **An Undo** is a Snapshot whose origin names the Snapshot it takes back, written once, by a foreign key checked when the Database Transaction commits (`DEFERRABLE INITIALLY DEFERRED`), an edge of the drop's rule, so that the Snapshot it takes back is kept as long as the Undo is (ADR 0018, "Keeping and dropping"). Its content is ticket 167's comparison per Occurrence, with what the taken-back Snapshot left as what both are compared with, the current versions as one side and the versions it ended as the other; where nothing has changed since, the Event goes back to the version before, as a copy (ADR 0018). It is made in one Database Transaction for all the Calendars, through the one place that makes a change's Snapshot, so it is sent like any change.
- **One function takes back any Snapshot** it is given: Ctrl+Z's target, an Undo for redo, a line of the Calendar History (ticket 159), a Server Event Replacement to restore (ticket 134). An Incoming Sync Snapshot can be taken back this way though Ctrl+Z never reaches one.
- **Where both changed** (ADR 0020): an Occurrence that the Undo and a later change both change is combined by ticket 167's field groups, each group from the side that changed it, as in sync; it is refused where both changed the same group, the Unimplemented Fields too, or one the times and the other any other group but the Unimplemented Fields, or the Undo a whole Recurring Event and the later change one Occurrence. No extra Snapshot: the Undo's content is the combination.
- **What a Snapshot left behind,** what an Undo compares with, is the Event Versions ending with it that began before it, never a zero-length Event Version (ADR 0018); so an Undo of an Incoming Sync Snapshot takes back nothing of an Event merged or in Conflict there.
- **Refused whole,** writing nothing, when the comparison finds a Conflict it can't combine in any Calendar, when it would change nothing, when an Undo in effect already takes it back, and when it spans a Calendar marked read-only. The refusal says which: for a Conflict, the Occurrences and the first Snapshot after the taken-back one that changed each (its origin and, for the user's own, its description), so that the window can name it and, for a Server Event Replacement, offer its restore. With "both" asked for, undo or redo, the version the taken-back Snapshot ended wins in every Occurrence changed on both sides ("Undo both changes", "Redo over the server's change"); the Undo records that it was made over a later change, for the Calendar History to show.
- **Ctrl+Z's target:** the core says which Snapshot the next Ctrl+Z takes back: the newest of the user's own Snapshots in effect, across all Calendars, by when each was made. The user's own: an action of the user, an import, a Backup restore and "Stop waiting" (from ticket 166). Passed over: Incoming Sync Snapshots, the First Sync's among them, Server Event Replacements (from ticket 152), Server Event Merges (from ticket 168), Undos, and the Snapshots only in Calendars marked read-only. In effect: no Undo in effect takes it back. At a Snapshot spanning a Calendar marked read-only and another, Ctrl+Z stops and is refused.
- **Redo** takes back the newest Undo in effect that isn't itself a redo (an Undo of an Undo), by the same function, however that Undo was made, passing over Undos only in Calendars marked read-only. The core says which one; there is none once the user has made a change of their own after it. Syncs don't end it. Nothing is dropped when it ends.
- **The Calendar History is only added to.** Nothing is written beside the Undo's Snapshot; the redo path, its end and the Snapshots dropped with it don't exist.
- **The Sent Event Rows** name each Event Version by its row ID instead of its hash, as a row never changes.
- **What comes out of the core:** `journal_transaction`, `journal_event_modification` and their SQL (`core/src/store/sql/journal.rs`); the hash and its format; undo per Event and its search for changes in between (`core/src/journal/undo.rs`); the Change Journal's listings (`core/src/journal/list.rs`); the Undo History read from the Change Journal; the Dangerous Undo; the Transaction Origin, which the Snapshot's origin replaces; the 90-day removal of Journal Transactions (dropping Snapshots is ticket 148); ticket 145's carried ID column. What is left of `core/src/journal/mod.rs`, the running of a set of writes as one step, belongs to the Calendar History's module, and one such step makes one Snapshot.
- **What comes out of the core interface and the window:** `undo` with its targets, `change_journal`, `journal_transaction_events`, `event_history`, `undo_history`, and the Journal Transaction in the result of every change (`Changed<T>`); the Change Journal dialog (`src/lib/ChangeJournalDialog.svelte`) and its menu entry; the History button in an Event's details; the Undo button on toasts, whose target was a Journal Transaction. Ctrl+Z and Ctrl+Shift+Z call the new undo and redo, and a refusal shows as a toast with the core's reason in plain words; ticket 158 words the toasts and adds their buttons. The Calendar History window and the Event's History return with their own tickets.
- **Write Permissions** stay for now, under the Calendar History's module in place of the Change Journal.
- **The Store Check** gains: an Undo takes back an older Snapshot.
- **Tests:** `core/tests/change_journal.rs`, `change_journal_list.rs` and `undo_per_event.rs` are replaced by tests of the Calendar History through the core interface: undo and redo of each kind of change, of a move and of an import into several Calendars, across a restart; an undo refused by a later change of the user, with its name, and "both"; an undo combined with a later change to the Unimplemented Fields alone, and the current ones winning where both changed them; Ctrl+Z passing over a Snapshot only in a read-only Calendar and refused at a move into one; redo after a change of the user offered no more; a redo never offered for a redo; an Incoming Sync Snapshot taken back by its Snapshot; a Snapshot already taken back refused; a First Sync's Snapshot never taken back. The tests of undo reaching the server in `core/tests/caldav_send.rs` are kept and rewritten to Ctrl+Z. The prototype's walkthroughs 1, 2, 10, 11, 12, 13 and 18 (`core/prototypes/calendar-history.PROTOTYPE.html`) are cases to cover; 4, 7 and 8 (restore) are ticket 134's, 15 ticket 166's.
- **Docs:** `GLOSSARY.md` loses or revises the entries Change Journal, Journal Transaction, Journal Event Modification, Record a Journal Event Modification, Transaction Origin, Dangerous Undo, Event Row, First Sync and Local Store, and the lines in other entries that name them. `CODING_STANDARDS.md` follows where it names the Change Journal.

Spec: US-81, US-146, US-150; "Calendar History". ADRs 0018, 0020.

**Blocked by:** 146, 167

**Status:** ready-for-agent

**Effort:** M

- [ ] An Undo is a Snapshot naming the one it takes back, made by ticket 167's comparison; a Snapshot spanning Calendars is taken back whole, in one Database Transaction
- [ ] Any Snapshot, a First Sync's too, can be taken back by the one function, Incoming Sync Snapshots included
- [ ] Where the managed fields changed on at most one side, an Undo combines with the later change; otherwise it is refused whole, writing nothing, in each case listed, and says why; "both" undoes or redoes over the later change, and the Undo records it
- [ ] An Undo refers to the Snapshot it takes back by a deferred foreign key
- [ ] The core names the next Ctrl+Z's Snapshot and the next redo's Undo by the rules above
- [ ] Redo takes back the newest Undo in effect until the user's next change; the Store Check passes after each step
- [ ] An undo and a redo in a server Calendar reach the server (tests against Radicale)
- [ ] The Change Journal's tables, the hash, undo per Event, the listings, the Dangerous Undo and the carried ID column are gone from the code and the schema

- [ ] `GLOSSARY.md` and `CODING_STANDARDS.md` follow
