# 87: Sync matches server objects by href

**What to build:** Incoming changes are matched to the server objects FreeCal holds by href, and each object updates only its own rows (ADR 0010). The UID still groups a Calendar's rows into a Recurring Event with its Exceptions.

**Blocked by:** 86

**Status:** done

**Effort:** M

- [x] A changed object replaces its own rows with what it now holds, whatever their UIDs; a new object adds its rows; a removed object takes its rows with it. `Store::event_at` and the UID-change special case in `sync::apply` go
- [x] Replacing an object's rows touches only that object's rows: `Loaded::take`, which replaces the whole UID group and deletes every stored Exception the incoming version lacks, isn't used as it is, since in Google each Exception is an object of its own and would be deleted with every change to its Recurring Event
- [x] At most one Exception per recurrence ID per object, enforced where `Loaded` writes Exceptions, not by the schema: iCalendar allows several components with one UID and RECURRENCE-ID (revisions told apart by SEQUENCE), and a unique index would turn a server's harmless duplicate into a Sync Error. Of several in one object, the one with the highest SEQUENCE is kept (today `import::assemble` keeps the first). Where two objects with one UID each have one, both keep their rows and the first by ID is shown; reading stays tolerant of duplicates from another program
- [x] An object FreeCal can no longer read keeps its last readable version in the mirror and its rows as they were, and is recorded as unreadable, so that it can be shown as a problem later; it is fetched again on each sync until it reads
- [x] An object moved to another href on the server is still changed, not deleted and added again
- [x] Core tests: two objects with one UID on a server without sync tokens no longer take each other's rows on every sync (each sync recorded no unit); a Google-like Recurring Event whose Exceptions are objects of their own keeps them when only its object changes; two components with one recurrence ID in an object; an object whose UID changes; an unreadable object

Out of scope: Exceptions without their Recurring Event (ticket 88); a server change arriving while an object is pending (ticket 20).

## Comments

- 2026-10-25 (from 86): `Unit::remove_objects` deletes the objects at an href after `sync::apply` deleted the UID group `Store::event_at` finds. Rows of the object it doesn't find, such as Exceptions without their Recurring Event, lose their `object_id` through `ON DELETE SET NULL`, outside the Change Journal. "A removed object takes its rows with it" should delete them through the unit first. The first sync mirrors every object it lists, also a second one with a UID already loaded, which stays without rows.
- 2026-10-25: Done. A sync gets one `remote::Fetched` per object: the object, and its Events, Exceptions unpaired, or none if FreeCal can't read it. `sync::take` serves the first sync and later ones. `event::take_object` replaces an object's own rows, pairing them by UID and normalised recurrence ID, and `event::latest` keeps the highest `SEQUENCE` there and in `Loaded::take`; `import::assemble` no longer drops later revisions. An Exception in an object of its own is paired with its Recurring Event, the first in the same batch, otherwise the one stored. A moved object is a new href holding a UID of rows of an object removed in the same sync; it takes that object's row. A removed object deletes its rows through the unit (`Unit::remove_object`). Unreadable objects get a `server_object.unreadable` column (new migration). `remote::Held` passes it to `Remote::changes`, which fetches them again with a sync token too. The grid shows the first Exception by ID of several for one Occurrence, with one query per Exception in range. Beyond the ticket: a new object holding nothing FreeCal keeps isn't mirrored, and a known one that comes to hold nothing leaves the mirror with its rows, so the mirror holds no object without rows that would look like an unsent delete. Left as before: an object unreadable on its first fetch isn't recorded, so with a sync token it isn't fetched again until it changes. No test sees a sync set the unreadable mark, as the interface doesn't show it; the re-fetch test sets it in the Local Store. Two objects that each hold the Recurring Event with one UID both show, as before. Tests in `caldav_sync.rs` (`server_objects`) write objects straight into Radicale's storage with `Radicale::write_event_file`, as Radicale refuses a second object with a UID and a change of UID.
