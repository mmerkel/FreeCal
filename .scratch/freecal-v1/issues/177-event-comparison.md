# 177: The comparison of the two sides, as one function

**What to build:** The Event Comparison: one pure function that compares two sides of one UID with what both are compared with, per Occurrence and by Field Group, and gives the outcome for the UID (ADR 0019, "Whether the server changed"; ADR 0020, "Where both changed"). Undo (180) and the Incoming Sync (189) both call it. Old ticket 167 (`git show design/snapshot-line:.scratch/freecal-v1/issues/167-comparison-of-the-two-sides.md`) plus old 21's rule per Occurrence for Recurring Events. Nothing is written; nothing calls it yet.

- **Where and what:** `core/src/comparison.rs`: `EventVersionContent` (managed fields and 175's tree, without row ID, Calendar or Snapshots; compared through the recurrence ID's `NormalForm` and the tree's canonical form, never by `derive`), `compare_event(base, ours, theirs, on_conflict) -> UidOutcome` over every single Event of the UID, keyed by recurrence ID. `OnConflict` is `Report` or `Win(Side)` ("… all over the later changes", ADR 0020). 177 settles `UidOutcome`'s variants.
- **Per Occurrence:** changed on one side only, that side's version; both to the same result, they agree (the outcome names both, so the caller keeps one row); both differently, compared by Field Group (the times with the time zone and repeat rule, the title, the Location, the description, the Unimplemented Fields): each group from the side that changed it where no group changed on both and the times didn't change against any group but the Unimplemented Fields; otherwise a Conflict, unless `Win` decides. "Changed" compares canonical forms. A deletion is a change; a deletion against any change is a Conflict.
- **Recurring Events** (from old 21): a change to the Recurring Event itself (any managed field, its rule and excluded dates included), its creation or deletion counts for every Occurrence; an Exception changed, created or removed counts for its own. A change to the Recurring Event against a change to one Occurrence on the other side is a Conflict on the whole UID, never combined: groups combine within one Event Version only. A Conflict on any Occurrence is a Conflict of the whole UID.
- **The groups** come from one exhaustive function over every managed field, destructured without `..`, so a managed field added later doesn't compile until it has a group.
- **Entries go with their field** (decided 2026-11-28 with the user, `conformance.md` item 4): what the Unimplemented Fields keep of a managed property belongs to that field's group, not to the Unimplemented Fields group: entries under `DTSTART`, `DTEND`, `RRULE`, `EXDATE`, `RECURRENCE-ID` and the kept `VTIMEZONE`s to the times (a rule FreeCal can't expand with its excluded dates included), under `SUMMARY` to the title, `LOCATION` to the Location, `DESCRIPTION` to the description. Every other entry, the content of properties and components FreeCal doesn't manage, is the Unimplemented Fields group. So a combination never takes a field from one side and its entries from the other, and a change to a rule FreeCal can't expand is a change to the times. One function gives an entry's group from its name; as names are strings, the compiler can't check it, so a test lists every managed property's name and its group. Strongest con: a few more Conflicts, and a rule the compiler doesn't hold.
- A helper builds the three maps for one single Event, for the simplest tests.

Spec: "Calendar History"; "Sync engine". ADRs 0017 ("Part of the version"), 0019 ("Whether the server changed", "A Server Event Merge"), 0020 ("Where both changed"). Layout: "New terms" (Event Version Content, Event Comparison, Sides); "Interfaces designed twice", "The comparison: `compare_event`"; "By phase", P1, 177.

- 2026-11-28: Started from commit `c1ea7b5`.
- 2026-11-28: Built the Event Comparison in `core/src/comparison/mod.rs` with its tests in `comparison/tests.rs` (29 unit tests, one or more per box). Nothing calls it yet (180, 189); the module carries `allow(dead_code)` until then. Decisions, for review, each with its strongest con:
  1. **decision, for review:** `Win(side)` settles only what would be a Conflict, with the winner's version whole; an Occurrence whose groups combine stays combined under `Win` too. Con: ADR 0020 says the earlier state wins "in every Occurrence changed on both sides", which read literally includes the combinable ones.
  2. **decision, for review:** a Conflict of the whole UID (the Recurring Event against an Exception) under `Win(side)` gives the winner's versions of every Occurrence of the UID, never a mix of one side's Recurring Event and the other's Exceptions. Con: where the winner changed only an Exception, the loser's change to the whole series is lost with it.
  3. **decision, for review:** a change to the Recurring Event both sides made to the same result doesn't count against the other side's change to an Exception (it agrees, and the Exceptions are compared on their own). Con: a rule one could read as "the Recurring Event changed on both, so every Occurrence changed on both".
  4. **decision, for review:** each side's Exceptions are keyed by the Normal Form against that side's own Recurring Event (`UidVersions::new`); where the Recurring Event's zone or all-day changed, an Exception shows as removed and created on that side, which the change to the Recurring Event already makes a change to every Occurrence. Two versions of one side for one Occurrence refuse the side (`None`), left to the caller. Con: the caller must handle a side that doesn't key.
  5. **decision, for review:** an Event Version Content's canonical form compares the recurrence ID by its Normal Form without a Recurring Event (as obtained, normalised), the excluded dates as a set (sorted and without repeats, as `exdates_of` stores them; changed with the user, 2026-11-28, from "as stored text"), and `zone_pinned` and `description_html` as fields of the times and the description. Con: an excluded date in another form than the Normal Form (stored by something other than FreeCal's own writers) still counts as different text.
  6. **decision, for review:** two different creations of one Occurrence (no base) are a Conflict, as every group counts as changed on both. Con: an Exception both sides created for one Occurrence of a series is a Conflict even where the groups would combine against the Occurrence; ticket 217 (written 2026-11-28 with the user) compares them with the Occurrence the base's Recurring Event gives.
