# Sync compares the user's versions with the server's marks: what differs is sent, ETags say what the server changed, and a Conflict ends at once with the server's version

This supersedes ADRs 0014 and 0015. It comes from the grilling of 2026-11-15 (see ADR 0017) and builds on the Calendar History (ADR 0018); the code follows with later tickets. Rewritten after the grilling of 2026-11-22 on the second point of `.scratch/freecal-v1/critiques.md`: as first written, sync read a User's Pointer and a Server's Pointer per Calendar, and a Conflict stopped the whole Calendar from syncing until the user merged the two in a Snapshot with two parents (tag `design/snapshot-tree`; see "Considered Options"). Adjusted after the grilling of 2026-11-22 on point 2 of `.scratch/freecal-v1/critiques-2.md`: changes to different field groups are combined in a Server Event Merge instead of a Conflict ended by an Automatic Resolution, and the server's version of an Event merged or in Conflict is a zero-length Event Version of the Incoming Sync Snapshot. Adjusted after the discussion of 2026-11-26 on point 7 of `.scratch/freecal-v1/critiques-2.md`: the Server Event Merges and Server Event Replacements are part of the Incoming Sync Snapshot, undone per Event by an Undo limited to one Event (ADR 0020), and a Conflict is a row of `conflict` naming the Last Agreed Version, kept after it is resolved (tag `design/server-event-snapshots` keeps the form before). "Merge" in this ADR means the Server Event Merge, except where a Snapshot with two parents is named.

Sync kept three records of its own: the list of Unsent Changes, the Mirror's text of every Server Object, and the Conflict tables with copies of two versions. With the user's and the server's Current-Version Marks (ADR 0018), all three are derived, and sync becomes one question: what to do where the two marks differ. Three sources answer it, each for one thing only: **ETags say whether the server changed; the Current-Version Marks say what to send; the Calendar History is only for undo, Conflicts and the Mass-Change Guard.**

**What to send.** The Events whose current Event Version on the user's side differs from the one with the server's mark, or exists on one side only. "Differs" compares content (ADR 0018, "Event Versions"): the same row is equal, different rows are compared by canonical form, so an edit back to what the server has sends nothing. Nothing records that a change is unsent. The Sender builds each Server Object from the user's Event Versions alone (ADR 0017): versions on both sides is an update, on the user's side only a create, on the server's side only a delete. An Unsent Change, as the user sees it, is such a difference.

**Whether the server changed.** ETags and sync tokens say which Server Objects changed; only those are fetched. Where they can't, the Incoming Sync is a **Full Fetch**: every resource of the Calendar is fetched and compared with the versions carrying the server's mark, through the same code. That happens when the Calendar has no sync token (its First Sync, and after the server reset the token) and on every Incoming Sync of a server that gives no ETags. A Full Fetch also runs as **Mark Reconciliation**, in the background as a Calendar's next Incoming Sync, once its last Full Fetch is more than 7 days old; that time is stored beside the sync token, and any Full Fetch sets it (decided 2026-11-22, on point 5 of `.scratch/freecal-v1/critiques.md` and point 1 of `critiques-2.md`). It is the one check of the server's marks against what the server holds. A Full Fetch writes like any Incoming Sync and never locks the window (decided 2026-11-22, on point 4 of `.scratch/freecal-v1/critiques.md`). What was fetched is compared per Occurrence, three ways: the fetched versions, the user's current ones, and the ones with the server's mark, which are what the server held when FreeCal last looked. An Occurrence only the server changed follows the server; one only the user changed stays to be sent; one changed on both sides to the same result agrees, and the server's mark moves to the user's row; one changed differently on both sides is compared by **field group**: the times (with the time zone and the repeat rule), the title, the Location, the description, and the Unimplemented Fields (ADR 0017). Where each group was changed on at most one side, FreeCal combines them, each group from the side that changed it, in a **Server Event Merge**; where both sides changed the same group, or one side the times and the other any other group but the Unimplemented Fields, it is a Conflict (decided 2026-11-22, on point 2 of `.scratch/freecal-v1/critiques-2.md`). The times are kept apart because most changes that are each sensible but wrong together involve the time: a meeting moved while someone writes about its old day or room. The groups are compared within one Event Version: a change to the Recurring Event itself counts as a change to every Occurrence (ADR 0014, unchanged), so a change to a whole Recurring Event against a change on the server to one Occurrence is a Conflict on the whole Recurring Event, never combined, as a series' new title written into an Exception would have to guess whether that Exception's title followed the series. One function names every managed field and its group, without a catch-all, so a field added later must be given a group to compile. An Undo compares by the same groups (ADR 0020).

**An untrusted base.** Where a Full Fetch finds a resource whose ETag equals the stored one but whose content differs from the version with the server's mark, FreeCal's own record is wrong, not the server's, and the three-way comparison has no base to trust: read as usual, a mark left on the user's unsent version would make the server's version look like the server's change and replace the user's edit without a Conflict. So the server's mark moves to the fetched version, an Occurrence where the user's current version is the same agrees, and any other is a Conflict, never a Server Event Merge, as it can't be known which side changed. That Conflict names no Last Agreed Version, as the version with the server's mark is the one not trusted, so it shows the two versions without saying what each side changed. The Log names the Calendar and UID; nothing else marks the case. A resource with no ETag to compare (gone from the server, or with no server's mark) goes through the usual comparison.

**An Incoming Sync** writes in one Database Transaction one **Incoming Sync Snapshot**, of one Calendar, in which every Event fetched that differs from the version with the server's mark is taken in (decided 2026-11-26, point 7 of `.scratch/freecal-v1/critiques-2.md`):

1. an Event the server alone changed: the server's versions begin with it and become current;
2. a **Server Event Merge**, for an Event combined: the server's versions begin and end with it, zero-length Event Versions (ADR 0018) that carry only the server's mark, and the combination begins with it on the user's side; it differs from the server's mark and is sent like any change;
3. a **Server Event Replacement**, for an Event in Conflict: the server's versions begin with it and become current, the User's Version ends with it, and a row of `conflict` (below) records the Conflict;
4. the server's marks moved to the fetched versions, with their ETags.

So the Incoming Sync Snapshot records everything an Incoming Sync took in, and the Calendar History shows its Merges and Replacements inside its entry. Each can be undone alone, by an Undo of the Incoming Sync Snapshot limited to that Event (ADR 0020). Where nothing the user sees would change, as where both sides reached the same content, only the marks move and no Snapshot is made. A First Sync is a Full Fetch with no server's marks yet, so all it fetches is taken in as one Incoming Sync Snapshot (ADR 0018). After it, the user's side holds every change the server has, and the server's marks hold what the server holds. If nothing differs then, nothing is left to send.

**The invariant.** The server's marks move forward only in a Database Transaction that also brings the user's side up to them. So every version the server holds has been taken in on the user's side, and an Outgoing Sync never takes the server back. No code may split an Incoming Sync across Database Transactions; the interface has no operation that moves the server's marks alone.

**Conflicts end at once, with the server's version** (decided 2026-11-22). The Server Event Replacement shows the Server Version and sends nothing. The User's Version stays in the Calendar History as the replaced Event Version, and an Undo of the Incoming Sync Snapshot limited to that Event restores it, sent like any change. An edit against a deletion on the server ends the same way: the Event is gone until the user restores it. The server's version wins because a wrong guess then reaches nobody else; the user's winning would overwrite a colleague's change on the server, and with it notify its attendees. No Calendar ever stops syncing for a Conflict.

**The Conflict tables** (decided 2026-11-26). A row of `conflict` names the Incoming Sync Snapshot, the Calendar and the UID, and the time it was resolved, empty while it is open. A row of `conflict_event`, a **Conflict Event** (`GLOSSARY.md`), stands for each single Event of that UID, the Recurring Event or an Exception, found on either side or in the Last Agreed Version: its recurrence ID and its **Last Agreed Version**, the Event Version with the server's mark before the fetch, empty where there was none or where the base is untrusted (above). The User's Version and the Server Version aren't stored: they are the Event Versions of that Calendar and UID that end and that begin with the Incoming Sync Snapshot. The Last Agreed Version is stored because the server's mark moves on and nothing else recalls it; with it the Conflict shows, per field group, what each side changed (reversing point 4 of `.scratch/freecal-v1/critiques-2.md`, where one column couldn't name the several Event Versions of a Recurring Event; one row per single Event can). Rows of `conflict` are written only by the Incoming Sync's comparison, in the branch that decides a Conflict, and an insert trigger refuses one whose Snapshot isn't an Incoming Sync Snapshot; this is the one invariant here that no query can check afterwards, as an Event in Conflict and one the server alone changed leave the same Event Versions.

The Conflict stays open until the user **resolves** it: by keeping the server's version, by restoring their own (an Undo of the Incoming Sync Snapshot limited to that Event, from the Conflict, the toast of a refused Ctrl+Z or the Calendar History, or an Undo of the whole Incoming Sync Snapshot), or by changing the Event again (any later Snapshot of the user's own, or Undo, that changes it). Each of these sets the time of resolution, which a trigger lets be set once and never changed. The row stays: the Conflict view, an Event's History and the toast of a refused Undo still say "replaced by the server's version" while its Incoming Sync Snapshot is kept, and it goes with that Snapshot (ADR 0018). Open Conflicts keep their Incoming Sync Snapshot (ADR 0018). So a redo of a restore leaves the Conflict resolved, as the user has chosen. A missed resolution leaves a Conflict showing, never hides one, and the Store Check asks that no open Conflict's Event was changed by the user or an Undo since. While a Calendar has open Conflicts, the Event carries the Conflict badge and the Calendar the Conflict Status Mark, the tray shows the Conflict state, and a bar that can't be dismissed names them; the spec has the details. Ctrl+Z passes over Incoming Sync Snapshots, and so over their Merges and Replacements (ADR 0020).

**A Server Event Merge** is no Conflict: nothing stays open and no row of `conflict` is written. It is recognised by its zero-length Event Versions, not by a record of its own. It is a guess that is sent, the one exception to "a wrong guess reaches nobody else", which is why the times are kept apart and nothing is combined across a Recurring Event and its Exceptions. After an Incoming Sync with Server Event Merges a toast says so: for one, `Standup was combined with a change on the server`, offering "Undo", the Undo of the Incoming Sync Snapshot limited to that Event, which brings back the user's version and is sent like any change, and "Open"; for several, `3 Events were combined with changes on the server`, offering "Show", which opens the Calendar History at that Incoming Sync. It shows also where the server changed only Unimplemented Fields. There is no desktop notification: nothing is lost, and the Server Event Merge stays in the Calendar History.

**An Outgoing Sync.** Its requests run outside any Database Transaction; one Database Transaction at the end records the outcome: the server's mark of each Event sent moves to the user's version that was sent. Every update and delete is conditional on the stored ETag (`If-Match`), so a write that succeeds proves nobody else changed that Server Object since FreeCal last read it; one that fails is left for the next Incoming Sync. What the server made of FreeCal's own write is no change by anyone. Where the server stored another form than was sent, that form is written as a new Event Version with the sent one's `begin` and `end`, which takes the server's mark, and the sent one is deleted (ADR 0018). A CalDAV answer with an ETag means the text was stored unchanged (RFC 4791 §5.3.4); without one FreeCal reads the resource back before the closing Database Transaction; Google's answer to a write is the stored event. Changes to other Events found in that fetch are someone else's and go through an Incoming Sync. A change the user makes while an Outgoing Sync runs ends the sent version on the user's side and is simply still different afterwards; it was made without seeing the server's form of the Event and is sent as the user made it. A Calendar has one sync activity at a time: an Incoming Sync waits for a running Outgoing Sync and the other way round (decided 2026-11-16). So a slow Outgoing Sync delays the fetch of others' changes to that Calendar.

**The Mass-Change Guard** checks every Outgoing Sync; Incoming Syncs aren't checked. If it would delete or change more than 10 Events and more than 5% of the Calendar on the server, it sends nothing and pauses the Calendar, as a Sync Error. It doesn't count an Event whose current version on the user's side began with an import or the restore of a Backup and doesn't have the server's mark, as the user approved those when making them. The approval is stored nowhere: the Snapshot's recorded origin (ADR 0018) is read. An Undo is always counted, also one taking back an import, a restore or a Server Event Replacement, whole or limited to one Event: undoing an import already sent asks once (decided 2026-11-21). This count is the one place where sync reads the Calendar History's origins (decided 2026-11-16).

**When the server refuses changes** (decided 2026-11-21). A server that doesn't let the user change a Calendar is treated like being offline in one direction: FreeCal can't tell whether that lasts a day or for good, so it keeps the user's changes and lets the user decide. The Calendar has the Sync Error "writes refused", beside Offline and a pause by the Mass-Change Guard: Incoming Syncs go on as ever, and the user edits, undoes and resolves Conflicts as in any writable Calendar, while the changes wait. Only the user's read-only mark makes a Read-only Calendar. While writes are refused and the Calendar isn't marked, every Poll also reads whether the server allows changes, and the waiting changes are sent once it does. The bar for "writes refused" offers "Stop waiting and mark read-only": after a confirmation that counts the Unsent Changes, a Snapshot with an origin of its own puts the versions with the server's mark in place of the user's, and the mark is set. Once the mark is removed, Ctrl+Z can take it back and so bring the waiting changes back (ADR 0020). FreeCal sets the mark itself when a Calendar is added whose server doesn't allow changes, as nothing waits yet. The user can remove the mark only after FreeCal has asked the server and it didn't say no, so a Calendar never becomes writable in a state FreeCal can't check; a server that says nothing about privileges counts as allowing changes, and a Local Calendar has no server to ask.

**Server Objects.** The Local Store keeps for each Server Object only where it is and which version FreeCal last saw: for CalDAV, the Calendar, UID, href and ETag. Its content is the Event Versions with the server's Current-Version Mark. A Server Object FreeCal can no longer read keeps those Event Versions and loses its stored ETag, so that it is fetched on every Incoming Sync until it reads, and Outgoing Syncs of its UID wait. On Google each Exception is a Server Object of its own; its table comes with ticket 26.

**One CalDAV resource per href and per UID.** ADR 0015's rules stay, with "mirrored" read as "kept in the CalDAV table". At most one resource is kept per href and per UID in a Calendar, by unique indexes. A fetched resource holding several UIDs, or a UID that a kept resource already holds (an Ambiguous UID), is an Ignored Resource, remembered with its ETag in `caldav_ignored_resource`, written to the Log, and not fetched again until it changes; one FreeCal can't read is remembered without an ETag and fetched every time. The kept resource keeps its UID for as long as it holds it. Among several candidates in one Incoming Sync the first by the fixed order keeps it: the one holding the single Event or the Recurring Event, then the lowest href; a resource moved to another href competes like any other. When the kept resource is removed, changes its UID or comes to hold several UIDs or nothing, or FreeCal itself deletes it, the Ignored Resources holding the UID are fetched again in the next Incoming Sync and the first by the fixed order takes over. FreeCal never writes to a server to repair such resources. `docs/research/caldav-duplicate-uids.md` holds the evidence.

## Considered Options

- **A recorded list of Unsent Changes** (ADR 0015): the user's intent is stored, not derived, but every write must add to the list, an undo must repair it, and Sent Event Rows must guard it against changes made while an Outgoing Sync runs.
- **The Mirror's text** (ADR 0015): see ADR 0017.
- **A Conflict table with copies of both versions** (ADR 0014, tag `design/change-journal`): a third and fourth copy of the Event columns, and a rule run on every write to keep them current.
- **A Calendar with a Conflict stopping to sync in both directions until the user merges** (in a Snapshot with two parents; this ADR as written until 2026-11-22, tag `design/snapshot-tree`): FreeCal never guessed, but one disputed Event in a busy shared Calendar held back every change in both directions, and ignoring the bar for a day could mean missing a moved meeting. It needed a Reference Snapshot, a Server's Pointer, merges with two parents and the state Tracking.
- **A Conflict whatever the fields, ended at once by an Automatic Resolution** where the managed fields changed on at most one side (this ADR until 2026-11-22): the server's mark needs a row holding exactly what the server holds, which a combination isn't, so a title changed against an alarm added made a Conflict, a Server Event Replacement, an Automatic Resolution and a row of `resolution`, and the Calendar History showed an ordinary concurrent change as a replacement and a resolution. The zero-length Event Version gives the server's version its row without them.
- **The server's version of a merged Event as a row marked server-only by a flag**: no Snapshot for it, but every query and index of the user's side has to filter the flag, and an empty `begin` would mean either "older than the kept Snapshots" or "server-only".
- **Two lines, one of the user's Snapshots and one of the server's**, each Event Version with a stretch on each: a server-only row has a place and the server's history is kept, but it is a second Snapshot table, two more references to respect when dropping, and a server's Snapshot at every Outgoing Sync's outcome; and it checks nothing against the server, as the server's mark would be read from that same line. Mark Reconciliation is the check.
- **A Server Event Merge and a Server Event Replacement as Snapshots of their own after the Incoming Sync Snapshot**, each referring to it (2026-11-22 to 2026-11-26, tag `design/server-event-snapshots`): each Event's part undone by an ordinary whole Undo, and a Conflict recorded by the line itself (a Replacement Snapshot without a row of `resolution`), so that no missed write could hide one. But it needed two more origins, a copy of the server's version for each Conflict, a column referring to the Incoming Sync Snapshot with its CHECK, its edge in the drop and its rule in the Store Check, zero-length Event Versions for Conflicts too, an Incoming Sync Snapshot made though it changed nothing visible, and an Undo of a whole Incoming Sync that took back nothing of its Merges and Replacements. With an Undo that can be limited to one Event (ADR 0020), they are part of the Incoming Sync Snapshot; the strongest con of this is that a Conflict is now a row the comparison must write.
- **The combination within the Incoming Sync Snapshot, with Undos always whole** (rejected 2026-11-22): taking back the server's part of one Event would need an Undo of the whole Incoming Sync, and the toast could offer no Undo. An Undo limited to one Event (ADR 0020) removed the objection.
- **Field-level merging as an opt-in setting** (the spec until 2026-11-22): two paths, and a rule that depends on a preference.
- **Every field group combining freely, the times too, and across a Recurring Event and its Exceptions**: more Merges, but a moved meeting combined with an edit written for its old day is a wrong guess sent to the server, and a series' new title written into an Exception has to guess whether its title followed the series.
- **The Unimplemented Fields of the server winning where both sides changed them** (ADR 0017 until 2026-11-22): no Conflict about fields the user can't see, but a rule of its own beside the groups' and different from the Undo's.
- **A desktop notification for a Server Event Merge**: seen when FreeCal is in the background, but nothing is lost; the toast and the Calendar History suffice.
- **A Conflict held per Event, with the rest of the Calendar syncing on**: FreeCal never guesses and little goes stale, but each Event in Conflict needs its own base kept, and that state would decide what is sent; the review state of a Resolution decides only what is shown.
- **The user's version winning**: the user's edit stays in view, but a guess is sent at once and overwrites a colleague's change on the server.
- **A notice only** (a toast and a desktop notification): no stored state, but a toast is gone after 5 seconds, and with FreeCal in the background the notification is the only trace.
- **The User's Version shown beside the server's as a ghost chip** until resolved: the replaced edit stays in the grid, but there are two chips for one Event, a Conflict on a whole series doubles it, and dragging a ghost needs rules.
- **A grace period** before the server's version wins, or **asking when the window is focused** and deciding otherwise: both keep the per-Event hold's state as well as the guessing, or make the rule depend on whether the user happens to be there.
- **The server's Snapshot as a second parent of the Incoming Sync Snapshot**, so that the server's version could be found again: the Incoming Sync Snapshot already holds it, and two parents bring back the merges.
- **A table of open Conflicts, a row deleted when its Conflict ends**: every row is open, so the foreign key alone keeps its Incoming Sync Snapshot, with no trigger; but with the Merges and Replacements inside the Incoming Sync Snapshot the row is the only trace that an Event was in Conflict, and deleting it would make a refused Undo say "changed on the server" where the server's version had replaced the user's.
- **A table of `resolution` beside the Conflicts**, naming how each ended and the Snapshot that ended it (2026-11-22 to 2026-11-26): a full record, but nothing reads how a Conflict ended, the Calendar History shows a restore or a later edit anyway, and the Snapshot that ended it was an edge of the drop of its own.
- **Storing the User's Version and the Server Version in the Conflict Event too**: one read per Conflict, but a second record of what the Event Versions ending and beginning with the Incoming Sync Snapshot already say.
- **Only "keep the server's version" stored, the other ends read from the Calendar History**: one write, but a redo of a restore would open the Conflict again.
- **A switch for the user to stop syncing a Calendar**: a way to hold back Outgoing Syncs, but a state the Calendar History doesn't describe.
- **Deciding a sync's direction by ancestry**: no ETags needed, but it trusts the Calendar History for writes to a server. ETags are used because they are the server's own word.
- **Comparing content on every sync, for every server**: one path without ETags, but every Event is fetched each time, and a server that stores a different form than sent looks changed for ever.
- **Mark Reconciliation only when the server resets a sync token**: costs nothing extra, but may never run on a server that keeps its tokens.
- **Mark Reconciliation on every start**: finds a fault sooner, but refetches every Calendar many times a week for a fault that may never happen.
- **An interval that doubles after each Mark Reconciliation that finds nothing**: adapts by itself, but is stored state per Calendar and a cap as arbitrary as the week; run less often instead once the Logs show no case (`.scratch/freecal-v2/issues/02-mark-reconciliation-less-often.md`).
- **No Last Agreed Version stored** (2026-11-22 to 2026-11-26): nothing but the Conflict view needs it after the Incoming Sync, and "the user knows which change was theirs"; but after days offline they may not, and with Conflicts decided by field groups, which groups each side changed is what the Conflict is about. A Conflict Event per single Event names the several Event Versions of a Recurring Event, which one column couldn't. Storing instead which field groups each side changed, per Occurrence, was rejected: a second form of what the Event Versions hold.
- **The usual comparison where the base is untrusted**, with a Log line: one rule, but it replaces an unsent edit with no Conflict in the very case Mark Reconciliation is for.
- **The user's version winning where the base is untrusted**: keeps the edit in the grid, but overwrites the server on a guess, as ADR 0019 rejects for Conflicts.
- **A Sync Error, or a toast asking for a bug report, where the base is untrusted**: makes the fault seen, but the user can do nothing about it, and the Conflict has already made it safe.
- **Marking the untrusted base in the Server Event Replacement's origin**: tells a false Conflict from a real one without the Log, but stores state that only debugging reads.
- **A separate Provider for CalDAV servers without ETags**: a second code path for a case the common one covers by fetching everything.
- **One Database Transaction per UID sent**: each success is recorded at once, but the closing Database Transaction would run once per Event.
- **The server's form of FreeCal's own write as a Snapshot of its own**: no row is replaced, and the Calendar History shows what the user sent, but every write to a server that normalises would make the user's last change look changed on the server since, so its Undo would be refused unless Undo passed over such Snapshots; and the Calendar History would have two entries per write. (Rejected on 2026-11-15 because an undo that moved a pointer got stuck; that reason went with ADR 0020.)
- **The Mass-Change Guard on the user's actions, not on syncs**: one question when the user acts, no paused Calendar and no false alarm from edits that add up, but nothing would stand between a fault in deriving what to send and the server.
- **The Mass-Change Guard on every Outgoing Sync, imports and restores included**: one rule that reads no origins, but it asks a second time about what the user just confirmed.
- **A stored approval** (a field on the Calendar naming the approved Snapshot, or a flag on the Snapshot): sync would read no origins, but it repeats what the Snapshot's origin already says and would have to be cleared after an Outgoing Sync and on undo.
- **The Mass-Change Guard on Incoming Syncs too**: not needed, as an Incoming Sync writes nothing to the server and an Undo can take it back.
- **Holding the server's changes while redo is possible** (Held during Undo, 2026-11-21): redo brought back exactly what was undone, but every undo followed by a change on the server stopped syncing until the user redid to the end. With an Undo as a Snapshot, redo survives syncs and nothing waits.
- **The server's read-only as a Read-only Calendar** (as built with tickets 56 and 120): FreeCal never tries an edit that will fail, but Unsent Changes waiting when access is lost have no way out but the server, and Undos and Conflicts need rules of their own there.
- **Asking whether to wait when writes are first refused**: the user decides at once, but a dialog interrupts for a state that often passes; the bar lets the user decide when they like.
- **Reading privileges on every Poll for every Calendar the server doesn't let the user change**: regained access shows everywhere, but at one more request per Poll for each subscription and holiday Calendar, for ever.
- **Removing the mark after a warning instead of asking the server**: works offline, but lets the user start changes that are sure to wait.

## Consequences

- Intent is derived. Any fault that changes the user's Event Versions or the server's marks becomes writes to the server; the Mass-Change Guard and the tests of the comparison carry that weight; Mark Reconciliation finds a wrong server's mark within a week.
- Every Calendar is fetched whole once a week, a few MB for a large one.
- Where the base was untrusted and only the server had changed, the user sees a Conflict that isn't one and keeps the server's version to end it.
- On a server without ETags, a wrong server's mark can't be told from a change of the server's.
- A Server Event Merge sends a guess: two edits to different groups that contradict each other, such as a title "Cancelled: …" against a new Location, reach the server combined. The toast and an Undo per Event take it back, after the server has had it.
- A Conflict on the Unimplemented Fields alone is about fields the user can't see; the Conflict can only say that the server changed details FreeCal doesn't show.
- A move of the meeting against any other change of a managed field, and a change to a whole Recurring Event against a change to one Occurrence, stay Conflicts.
- A Conflict is a row the comparison writes, no longer a Snapshot of its own: a fault that skips the write hides the Conflict, and no query can find it afterwards. The tests of the comparison carry that weight.
- A Server Event Merge has no record of its own; it is read from its zero-length Event Versions.
- A kept Conflict keeps the Snapshots with which its Last Agreed Versions ended, often older than its Incoming Sync Snapshot, for as long as it is kept.
- FreeCal decides every Conflict itself, for the server. The user's edit leaves the grid until they restore it, and the spec's "FreeCal asks instead of guessing" becomes "FreeCal takes the server's version, keeps yours, and shows you what it decided until you've looked".
- A Conflict is the only state of sync stored outside the Calendar History; it decides only what is shown.
- An Incoming Sync makes one Snapshot. The Calendar History shows it as one entry that opens, listing its Merges and Replacements.
- The Mass-Change Guard's count reads which Snapshot began an Event's current version, against the rule that the Calendar History is only for undo and Conflicts. It is the one exception, and it decides only whether to ask, never what to send.
- Small edits made offline add up to a paused Calendar.
- The Calendar History shows when FreeCal took the server's changes in, not when the server had them.
- If FreeCal stops in the middle of an Outgoing Sync, the next Incoming Sync finds changed ETags and fetches again; the server's form of that write then arrives as an Incoming Sync Snapshot, and until then the Events show as not sent.
- On a CalDAV server that answers a write without an ETag, someone else's change to the same Event between the write and the read-back is recorded as the server's form of the user's write.
- Sent Event Rows, the rule for whether a Conflict exists run on every write, Propagate's special cases for Unsent Changes, and the Sender's "nothing to send" comparison of texts go.
- Undoing a DELETE already sent creates the Event again under a new href, now with its Unimplemented Fields.
- A Calendar marked read-only when it was added, whose server allows changes later, shows it only when the user removes the mark, and removing it needs the server to be reachable.
- A server that says a Calendar is read-only though it would accept changes can't be overridden.
- While writes are refused, the user's changes wait, and Conflicts are ended for the server as ever; "Stop waiting and mark read-only" drops the user's waiting changes.
