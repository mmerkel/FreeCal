# Unimplemented Fields live on the Event Version, as a tree in canonical form

This is the ADR ticket 129 asks for. With ADRs 0018 to 0020 it comes from the grilling of 2026-11-15 on the branch `explore/unknown-fields-and-change-journal`, which was free to reverse earlier decisions where that made the code simpler and more consistent. The code follows with later tickets, after a prototype; until then it keeps ADRs 0009, 0014 and 0015.

Until now, what a server holds about an Event beyond the fields FreeCal manages lived only in the Mirror, as the text received, and the CalDAV writer patched FreeCal's fields into that text. A resource built without a Server Object lost those fields: an Event moved to another Calendar, the undo of a DELETE already sent, and the new Recurring Event of "this and following events" (ticket 129). We now keep them as Unimplemented Fields on every Event Version (ADR 0018), so they are recorded, compared, restored and moved with the Event, and a writer always builds a Server Object from Event Versions alone. The Mirror's text and the patching writer go.

**The format.** The Unimplemented Fields of one Event Version are a tree of named entries, a Rust type stored through serde in one column, in a canonical form: two trees are equal exactly when their stored forms are, whatever order or layout the server sent. An entry's name says where it is understood:

- A name with a format's prefix (`ical:`, `google:`, later perhaps Microsoft Graph's) holds what only the reader and writer of that format understand. Everything read from iCalendar text is `ical:`, from a CalDAV resource, an `.ics` file or a feed alike. `caldav:` is reserved for what only CalDAV holds and is assigned to nothing yet. Each Provider names the prefixes it holds: Local and ICS feed `ical:`, CalDAV `ical:` and `caldav:`, Google `google:` (decided 2026-11-16). A structured item that doesn't convert to another Provider without loss, such as an alarm or an attachment, stays whole under its format's name.
- A neutral name holds a field whose meaning and value are the same across Providers, such as status, show-as, visibility, sequence, created and updated, or `RDATE`. Neutral names are assigned when Google's reader is built, not before.

A move or an import into a Calendar carries the neutral entries and those with a prefix the target's Provider holds, and drops the rest. That is one rule for every Provider: a move between a Local and a CalDAV Calendar drops nothing, and one from Google into a Local Calendar drops the `google:` entries, which no export or Backup of a Local Calendar could write. When a field changes home (from a format's name to a neutral one, or to a column of its own once FreeCal manages it), a migration rewrites every Event Version, in Rust, and what doesn't convert stays under its format's name. Code reads only the current form.

**What is in the tree.** Only what FreeCal doesn't manage. The values of managed properties are not repeated. Parameters FreeCal doesn't know on a managed property (`LANGUAGE`, `ALTREP`, `X-` parameters) are one entry under the property's name, without its value; an edit of that managed field drops them, as they described the old value. `DURATION` is the exception: it is fully managed, read as the end and always written as `DTEND`, so nothing of it is kept, not even its parameters (decided 2026-11-28, ticket 176). `RANGE=THISANDFUTURE` changes what an Exception means, so it becomes a managed field (ticket 75), not an entry. An Exception the user makes by changing one Occurrence takes the Recurring Event's entries, and so does the new Recurring Event of "this and following events", both without the calendar-level ones (decided 2026-11-16). The properties a writer sets fresh on every write (`DTSTAMP`, `LAST-MODIFIED`) are not kept, nor are the time zone definitions of zones FreeCal knows, which the writer writes fresh. The `VTIMEZONE` of a `TZID` FreeCal doesn't know is kept as an `ical:VTIMEZONE` entry on each Event whose tree uses that `TZID`, and written once per resource (decided 2026-11-28, ticket 176). `SEQUENCE` is kept as an entry and written back unchanged: FreeCal changes no Event with guests, and who raises it is decided with the attendee features (ticket 126; decided 2026-11-16). What a CalDAV resource holds at the calendar level, outside its Events, sits under an `ical:` name on the resource's single Event or Recurring Event, or on its first Exception when it holds only Exceptions.

**What the reader can't represent exactly.** The reader consumes only what it represents exactly. Where it has a precise rule for a case, such as a property RFC 5545 allows only once, that rule decides, and what it drops on purpose is listed beside it. Anything else of a managed property that the reader can't represent exactly goes into the tree whole: a second `DESCRIPTION`, a second `RRULE`, a value form FreeCal doesn't model. An edit of that managed field drops it, as with unknown parameters, because it described the old value. The reader writes to the Log each violation of the RFCs it notices while reading; there is no separate validator. (Decided 2026-11-22, point 3 of `.scratch/freecal-v1/critiques.md`.)

**The round-trip check.** When a CalDAV resource is fetched, FreeCal writes it back from what the reader took, in memory, and compares the two texts, both parsed only into components, properties, parameters and values. The comparison ignores folding, line endings, the letter case of names, order where the tree ignores it, and what the writer sets fresh (`DTSTAMP`, `LAST-MODIFIED`, `PRODID`, `VERSION`, a default `CALSCALE`). A managed value may differ if the reader reads the same managed field from both texts, and what a precise rule drops on purpose may be missing. Anything else missing was lost. In that case the Log names the resource and the parts that couldn't be carried, and the CalDAV table holds a mark beside the ETag, written with it on every fetch. The mark changes what is shown, not what is done: the Event's details say that FreeCal couldn't read all of it and that changing it here may remove data other apps stored in it. Edits, deletes, Conflicts and sends work as for any Event. Only CalDAV has the check for now; Google's reader gets the same for its JSON. An import is a copy and an ICS feed is read-only, so neither has it.

**Part of the version.** The Unimplemented Fields are fully part of the Event Version: a change to them alone is a change, makes a Snapshot when it comes from a server, shows in the Calendar History as "changed in fields FreeCal doesn't show", and is undone with the rest. In a Server Event Merge and an Undo (ADRs 0019 and 0020) they are one field group beside those of the managed fields: if only one side changed them, that side's are taken; if both did, it is a Conflict, or the Undo leaves the Event out and asks first (ADR 0020), as for any group (decided 2026-11-22 on points 2 and 3 of `.scratch/freecal-v1/critiques-2.md`, replacing the server's winning in sync and the current version's in an Undo).

## Considered Options

- **The Mirror's text, patched** (ADRs 0010, 0015): exact text kept, but the fields exist only where a Server Object does, which is ticket 129's three cases, and every further case needs its own rule for where the text comes from.
- **The Provider's raw data in a column of the Event Version** (iCalendar text or Google's JSON): nothing lost and no second schema, but the Event table would hold two formats, comparison would depend on order and layout, and a move between Providers would carry nothing.
- **Neutral names only**: one schema, but alarms, attachments and custom properties convert between iCalendar and Google's JSON only with loss, and the loss would happen on reading, before any move asked for it.
- **Provider names only**: no neutral schema to design, but a move between Providers would drop the status, the visibility and the like, which both sides hold in the same way.
- **Google through its CalDAV endpoint, so that one format serves all**: `docs/research/google-caldav.md`. Google's CalDAV rewrites what a client sends and lacks colours, conference data and control over guest mail; ADR 0002 stands.
- **The whole managed property kept beside FreeCal's field**, to keep its parameters: the same value stored twice, with a rule needed for when they disagree.
- **A placeholder row for the Recurring Event of a resource holding only Exceptions**, to carry the calendar-level entries: a row that is no Event, which every reader of Events would have to skip.
- **A Conflict when both sides changed the Unimplemented Fields**: the user would be asked to choose between two versions of fields FreeCal doesn't show.
- **A rule in the history for values in an old home**: a migration rewrites them instead, so that only one form is ever read.
- **No round-trip check, the reader's tests alone**: no code at runtime, but a gap in the reader would delete another client's data on the server at every write, unseen.
- **The server's text stored beside the CalDAV table's row**, for the check: it could be run again after an update without a fetch, but the Local Store would hold a second format again.
- **The stored text with the remainder patched in**: the writer keeps from the stored text what the reader didn't take and writes the managed fields and the tree around it. An edit in place loses nothing, but the remainder belongs to one resource's text, not to the Event Version: a move, the undo of a DELETE already sent and "this and following events" lose it unseen. It is outside the Calendar History, and a stale remainder, such as a second `RRULE`, can contradict an edit of the field it belongs to.
- **A Server Object that fails the check made read-only** until a fetch passes it: nothing is lost, but it would be the one lasting reason that an Event of a writable Calendar is read-only ("has guests" goes with the attendee features), with three more exceptions behind it: deleting the whole UID allowed but not a scoped delete, no Server Event Merge and no restore in a Conflict, and a check again after each update. With the reader's rule above its case is rare. It stays possible later if the Log shows real losses.
- **A notice when the check fails, by toast or notification**: fetches run in the background and come back with every change on the server, so it would be noise and gone by the time the user edits the Event. The details are where the user decides.

## Consequences

- The server's original text is no longer in the Local Store, neither for writing nor for inspection. A property FreeCal's reader fails to carry into the tree because of a bug in the reader is still lost on the next write of that Event. The round-trip check makes that visible, in the Log and in the Event's details, so each such bug costs data once, not on every write; a corpus of real servers' texts run through the same check in the tests is meant to find them first.
- Each precise rule of the reader that drops something must be listed with the check, or the check reports it as a loss.
- An Event's details can warn of a loss that the user's next edit causes; they don't prevent it.
- A field can have three homes over its life: a format's name, a neutral name, a column. Each change is a migration over all Event Versions.
- Neutral names are a second schema that SQL can't check. Whether a name is truly neutral shows only once Google's reader exists; with three Providers each neutral name needs three converters.
- An edit of a managed field silently drops that property's unknown parameters, such as the `LANGUAGE` of a title.
- An undo can take back another client's change to an alarm.
- Unimplemented Fields changed on both sides are a Conflict about fields the user can't see. As the user's side changes them only through an Undo, an import, a restore or an earlier Server Event Merge, never by editing, this is rare.
- Changes made on a server to fields the user can't see appear in the Calendar History as changes.
- Which Exception is "the first" is arbitrary, and the calendar-level entries move when that Exception is deleted.
