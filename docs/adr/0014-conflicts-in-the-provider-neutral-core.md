# Conflicts are found in the Provider-neutral core, per Occurrence

A Conflict is the state of an Event, so it is found, held and resolved by Provider-neutral code next to the Change Journal, not by the Sync Engine. For each Calendar and UID a server changed, the Sync Engine reads the Server Version, and the previous Server Version from the Mirror's data before it is overwritten. A neutral step then goes through the Occurrences: one with no Unsent Change is propagated to the Event Rows; one with an Unsent Change that the server didn't change keeps the User's Version, to be sent later; one changed on both sides is a Conflict. A change to the Recurring Event itself, on either side, counts as a change to every Occurrence. Without a readable previous Server Version, every Occurrence counts as changed by the server. Once any Occurrence is in Conflict, the Conflict covers the whole Event, so holding, showing and resolving it stay per Event.

While a Conflict is open, the User's Version stays in the Event Rows with its Unsent Changes, and the Sender sends nothing for the UID. A Conflict is one row of `conflict`, and keeps copies, as Event fields, of the Server Version and of the Last Agreed Version in `conflict_event`, told apart by a side column. The Last Agreed Version is the previous Server Version, read from the Mirror's data before it is overwritten. So the core never asks the Sync Engine for either, and an open Conflict stays complete even if its Server Object later becomes unreadable. The kind of Conflict and what each side changed are derived from the copies and the Event Rows when read, never stored. One rule decides whether a Conflict exists, run whenever either side of a UID changes, by an Incoming Sync or by a local write: sides equal, no Conflict, and the Unsent Changes go; the server back at the Last Agreed Version, no Conflict, and the User's Version is sent; the user back at it, no Conflict, and the Server Version is propagated; otherwise the Conflict is held, its copies replaced. (Amendment of 2026-11-09.) Conflicts are written in step with Event Rows and Unsent Changes, so the Change Journal's Write Permission guards them. Changes to different Occurrences of one Event are merged without asking: both can be kept, so FreeCal isn't guessing. Field-level merge of two changes to one Event stays out of scope (spec).

## Considered Options

- **Conflicts in the Sync Engine, per Provider**: "a server change to a Server Object while one of its Combined Event Keys is unsent" (ADR 0011) would have been written once per Provider, though the badge, the list, both versions, the common version from the Change Journal and resolving are all about Events.
- **Per UID**: one rule without comparing Server Versions, but an unsent change to one Exception would conflict with a server change to another Exception of the same Recurring Event.
- **The Server Version read again from the Mirror while the Conflict is open**: nothing stored twice, but the core would call into the Sync Engine.
- **The Server Version as one JSON value on `conflict`**: one table less, but a second serialisation of Event fields that SQL can't check.
- **The User's Version moved into the Conflict** (2026-11-09): the Server Version propagated to the Event Rows, the Unsent Changes removed and the User's Version kept in the Conflict, so that the Sender needs no rule and "Your version" makes an ordinary Unsent Change again. Rejected because the user's own edit would vanish from the grid until resolved, and an edit during the Conflict would edit the Server Version beside a second, stored User's Version.
- **The common version from the Change Journal** (2026-11-09): no extra copy, but the Change Journal keeps 90 days and undos blur which Journal Event Modification started the user's changes.

## Consequences

- An Incoming Sync propagates through the neutral step: Propagate a Server Object writes only the Occurrences the rules above let through.
- `conflict_event` is a third copy of the Event columns, next to `event` and `journal_event_modification`, holding both sides a Conflict keeps.
- On CalDAV, where a Server Version comes whole, finding what the server changed takes the comparison with the previous Server Version; on Google, a changed Google Server Object is one Occurrence or the Recurring Event.
- The rule runs in the Change Journal's write path as well as in Propagate, as a local edit, undo or import can end a Conflict.

## Amendments

- 2026-11-09, grilling of tickets 133 to 137: the User's Version stays in the Event Rows, and the Sender holds back a UID in Conflict, as an Incoming Sync stores the Server Version's ETag in the Mirror and a send would otherwise overwrite it without asking. `conflict_server_event` became `conflict_event`, which also keeps the Last Agreed Version, so that what each side changed is computed on reading and a later Incoming Sync can tell a server that reverted its change. The rule for whether a Conflict exists runs on every change to either side, since the user may edit, move, delete and undo an Event in Conflict. Resolving is one choice, the User's Version or the Server Version, for every kind. Choosing the Server Version is a Journal Event Modification like any change to Event Rows; choosing the User's Version changes no Event Rows, records nothing and can't be undone, as raising a Conflict records nothing.
