# Sync reads the two pointers: what differs is sent, ETags say what the server changed, and a Calendar is Tracking while it has no Conflict

This supersedes ADRs 0014 and 0015. It comes from the grilling of 2026-11-15 (see ADR 0017) and builds on the Calendar History (ADR 0018); the code follows with later tickets. The prototype of 2026-11-15 (`core/prototypes/calendar-history.PROTOTYPE.html`) settled the server's form of FreeCal's own write, and added the Reference Snapshot and the rule that Tracking means no Conflict.

Sync kept three records of its own: the list of Unsent Changes, the Mirror's text of every Server Object, and the Conflict tables with copies of two versions. With a User's Pointer and a Server's Pointer per Calendar, all three are derived, and sync becomes one question: what to do when the two pointers differ. Three sources answer it, each for one thing only: **ETags say whether the server changed; the Current-Version Marks say what to send; ancestry is only for the Calendar History and undo.**

**What to send.** The Events whose Event Version with the user's Current-Version Mark differs from the one with the server's, or exists on one side only. "Differs" compares content (ADR 0018, "Event Versions"): the same row is equal, different rows are compared by canonical form, so an edit back to what the server has sends nothing. Nothing records that a change is unsent. The Sender builds each Server Object from the user's Event Versions alone (ADR 0017): versions on both sides is an update, on the user's side only a create, on the server's side only a delete. An Unsent Change, as the user sees it, is such a difference.

**Whether the server changed.** ETags and sync tokens say which Server Objects changed; only those are fetched and compared. A server that gives no ETags has every resource fetched on each Incoming Sync and compared for equality, through the same code. The two sides are then compared per Occurrence, three ways: the server's versions, the user's, and those of the Reference Snapshot (below): an Occurrence only the server changed follows the server, one only the user changed stays to be sent, one changed on both sides to the same result agrees and the user's side takes over the server's row, and one changed differently on both sides is a Conflict. A change to the Recurring Event itself counts as a change to every Occurrence (ADR 0014, unchanged). The managed fields and the Unimplemented Fields are compared as two parts (ADR 0017).

**Tracking and the Reference Snapshot.** A Calendar is Tracking its server exactly while it has no Conflict and isn't Held during Undo (below): the user's side follows the server and the server is brought to the user's side. Tracking is not stored and the user has no switch for it; the user can only end Conflicts and continue after an undo. What is stored, per Calendar, is the Reference Snapshot: the server's Snapshot the user's side last took in. It is always set, from the First Sync on, and it is what both sides are compared with. It moves to the Server's Pointer whenever a comparison of the two sides leaves no Conflict and when an Outgoing Sync records its outcome, and at no other time. So a Calendar is Tracking exactly while its Server's Pointer is on its Reference Snapshot; while it isn't, the Calendar has a Conflict, is Held during Undo, or both. The last Snapshot the two pointers have in common can't serve: after an undo not yet sent it is the user's own Snapshot, so a later change on the server would look like the only change and the undo would be lost without a word.

**An Incoming Sync** does two steps in one Database Transaction. First, if the server's Events changed, it moves the Server's Pointer to a new Snapshot holding the server's state; the Reference Snapshot stays. Second, if the Server's Pointer is off the Reference Snapshot, it runs the comparison of the two sides: with a Conflict left, or while the User's Pointer has a redo path (Held during Undo, below), nothing more happens; otherwise the User's Pointer follows to the server's Snapshot if the user's side was on the Reference Snapshot, or else a Join takes the server's changes in, and the Reference Snapshot moves to the Server's Pointer. A Join is a new Snapshot on the user's side whose only parent is the User's Pointer's Snapshot, with an Incoming Sync as its origin; the server's Snapshot is not its parent, so the user's side stays one line and undoing a Join takes back the server's changes, asking first as for any Snapshot from a server (decided 2026-11-21). The user ending a Conflict is the same second step with the user's choices, and it also runs after every move of the User's Pointer while the Server's Pointer is off the Reference Snapshot (a change, an undo, a redo) and when the user continues after an undo. So the Server's Pointer is off the Reference Snapshot exactly while the two sides are in Conflict or the Calendar is Held during Undo, which the Store Check asks, and this is the only code that compares the two sides.

**Held during Undo.** A Calendar with a server is Held during Undo while its User's Pointer has a redo path and its Server's Pointer is off the Reference Snapshot: the server's changes have been fetched, but taking them in would end the redo path, so they wait. Nothing is stored for it; both conditions are read from the Calendar History (decided 2026-11-21). The comparison of the two sides still runs, so a Conflict shows as soon as it exists, and a Calendar can have a Conflict and be Held during Undo at once. An undo alone doesn't hold anything: while the Server's Pointer is on the Reference Snapshot the undo is sent as any change, and a redo is sent again. The hold ends when the redo path ends: by the last redo, by a change the user makes, or by "Continue" in the window, which drops the Snapshots beyond the User's Pointer; the second step then runs. While there is also a Conflict, ending it makes a merge, which ends the redo path too; the window says so instead of offering "Continue".

**The invariant.** While a Calendar is Tracking, the Server's Pointer moves forward only in a Database Transaction that also brings the user's side up to it, by following or by a Join, unless the User's Pointer has a redo path, when the Calendar becomes Held during Undo. An Incoming Sync whose user's side has nothing of its own makes one Snapshot both pointers move to; otherwise the server's side branches off and a Join takes its changes in. So outside the Incoming Sync's code, "the user's side is behind the server's" can only mean that the user undid something, and the server is to be brought to the user's side. No code may split the two steps of an Incoming Sync across Database Transactions. An Outgoing Sync needs the Server's Pointer to be on the Reference Snapshot, so a fault that did split them would send nothing and leave a state the Store Check reports, instead of taking the server back.

**An Outgoing Sync.** Its requests run outside any Database Transaction; one Database Transaction at the end records the outcome. Every update and delete is conditional on the stored ETag (`If-Match`), so a write that succeeds proves nobody else changed that Server Object since FreeCal last read it. If everything was sent and the server holds what the user has, the Server's Pointer goes to the Snapshot that was sent, backwards too after an undo. What the server made of FreeCal's own write is no change by anyone: a new Snapshot on the server's side always means that someone else changed the server. Where the server stored another form than was sent, that form is written as a new Event Version which takes the sent one's place in every Snapshot that held it, and the sent one is dropped; Event Versions still never change, only links are rewritten, in the Outgoing Sync's closing Database Transaction. A CalDAV answer with an ETag means the text was stored unchanged (RFC 4791 §5.3.4); without one FreeCal reads the resource back before the closing Database Transaction; Google's answer to a write is the stored event. Changes to other Events found in that fetch are someone else's and make a sync Snapshot. If not everything could be sent, one new Snapshot holds the server's state. A change the user makes while an Outgoing Sync runs moves the User's Pointer on and is simply still different afterwards; it was made without seeing the server's form of the Event and is sent as the user made it. The closing Database Transaction also moves the Reference Snapshot to the Server's Pointer, whether everything was sent or not: what FreeCal itself sent is nothing new to the user's side. This holds because a Calendar has one sync activity at a time: an Incoming Sync waits for a running Outgoing Sync and the other way round (decided 2026-11-16). So a slow Outgoing Sync delays the fetch of others' changes to that Calendar. The Mass-Change Guard checks every Outgoing Sync; Incoming Syncs aren't checked. It doesn't count an Event when the Snapshot that last changed it on the user's side is an import or the restore of a Backup that the server's side hasn't reached, as the user approved those when making them. The approval is stored nowhere: the Snapshot's recorded origin (ADR 0018) is read. This count is the one place where sync reads ancestry (decided 2026-11-16).

**Conflicts.** While a Calendar has a Conflict, nothing is sent and nothing from the server is taken in, while FreeCal keeps fetching, so the Server's Pointer follows the server. No table and no mark on an Event holds a Conflict. Which Events are in Conflict, and the Server Version, User's Version and Last Agreed Version of each, are read by comparing both pointers with the Reference Snapshot. When the user ends a Conflict, one merge Snapshot with both sides as parents is made, also when the user picks one side whole and its content equals that parent's; undo can then ask which side to go back to (ADR 0020). It is the only Snapshot with two parents: the version the user turned down stays in the Calendar History, where after a Join the server's Snapshot is dropped once nothing reaches it (decided 2026-11-21). A Conflict that goes away by itself, because one side came to agree with the other, ends at once: with the user's change, undo or redo that made them agree, or with the Incoming Sync that fetched the server's; after an undo the Calendar is then Held during Undo. While a Calendar has a Conflict, its line in the sidebar carries the Conflict Status Mark, and FreeCal is insistent about open Conflicts with a bar in the window and a dialog when a Calendar stops Tracking; the spec has the details. A Calendar that is Held during Undo without a Conflict has a Status Mark and a bar of its own, with "Continue"; with a Conflict too, only the Conflict's show, and its bar adds that resolving it ends what the user could redo.

**When the server refuses changes** (decided 2026-11-21). A server that doesn't let the user change a Calendar is treated like being offline in one direction: FreeCal can't tell whether that lasts a day or for good, so it keeps the user's changes and lets the user decide. The Calendar has the Sync Error "writes refused", beside Offline and a pause by the Mass-Change Guard, and stays Tracking: Incoming Syncs follow or make a Join, and the user edits, undoes and ends Conflicts as in any writable Calendar, while the changes wait. Only the user's read-only mark makes a Read-only Calendar. While writes are refused and the Calendar isn't marked, every Poll also reads whether the server allows changes, and the waiting changes are sent once it does. The bar for "writes refused" offers "Stop waiting and mark read-only": after a confirmation that counts the Unsent Changes, the User's Pointer goes to the Server's Pointer, as when it follows, which also ends a Conflict and a redo path, and the mark is set. FreeCal sets the mark itself when a Calendar is added whose server doesn't allow changes, as nothing waits yet. The user can remove the mark only after FreeCal has asked the server and it didn't say no, so a Calendar never becomes writable in a state FreeCal can't check; a server that says nothing about privileges counts as allowing changes, and a Local Calendar has no server to ask.

**Server Objects.** The Local Store keeps for each Server Object only where it is and which version FreeCal last saw: for CalDAV, the Calendar, UID, href and ETag. Its content is the Event Versions with the server's Current-Version Mark. A Server Object FreeCal can no longer read keeps those Event Versions and loses its stored ETag, so that it is fetched on every Incoming Sync until it reads, and Outgoing Syncs of its UID wait. On Google each Exception is a Server Object of its own; its table comes with ticket 26.

**One CalDAV resource per href and per UID.** ADR 0015's rules stay, with "mirrored" read as "kept in the CalDAV table". At most one resource is kept per href and per UID in a Calendar, by unique indexes. A fetched resource holding several UIDs, or a UID that a kept resource already holds (an Ambiguous UID), is an Ignored Resource, remembered with its ETag in `caldav_ignored_resource`, written to the Log, and not fetched again until it changes; one FreeCal can't read is remembered without an ETag and fetched every time. The kept resource keeps its UID for as long as it holds it. Among several candidates in one Incoming Sync the first by the fixed order keeps it: the one holding the single Event or the Recurring Event, then the lowest href; a resource moved to another href competes like any other. When the kept resource is removed, changes its UID or comes to hold several UIDs or nothing, or FreeCal itself deletes it, the Ignored Resources holding the UID are fetched again in the next Incoming Sync and the first by the fixed order takes over. FreeCal never writes to a server to repair such resources. `docs/research/caldav-duplicate-uids.md` holds the evidence.

## Considered Options

- **A recorded list of Unsent Changes** (ADR 0015): the user's intent is stored, not derived, but every write must add to the list, an undo must repair it, and Sent Event Rows must guard it against changes made while an Outgoing Sync runs.
- **The Mirror's text** (ADR 0015): see ADR 0017.
- **Deciding a sync's direction by ancestry** (whichever pointer is ahead in the graph is followed): no ETags needed, but it trusts the graph for writes to a server, and it must tell an undo from having fallen behind. With the invariant the two readings agree; ETags are used because they are the server's own word.
- **Comparing content on every sync, for every server**: one path without ETags, but every Event is fetched each time, and a server that stores a different form than sent looks changed for ever.
- **A separate Provider for CalDAV servers without ETags**: a second code path for a case the common one covers by fetching everything.
- **A record of whether the user's side fell behind or was undone**: the invariant makes "behind" mean "undone" everywhere outside the Incoming Sync.
- **A Conflict table with copies of both versions** (ADR 0014): a third and fourth copy of the Event columns, and a rule run on every write to keep them current.
- **A Conflict held per Event, with the rest of the Calendar syncing on**: less goes stale, but each Event needs a mark saying it is held back, and the pointers no longer describe a whole Calendar.
- **One Database Transaction per UID sent**: each success is recorded at once, but an Outgoing Sync makes as many Snapshots as it has Events.
- **The server's form of FreeCal's own write as a Snapshot of its own**: no links rewritten, but "a sync" would then also mean "the server rewrote what I sent", and undo gets stuck: it goes back to the user's form, the Outgoing Sync repeats, the server reforms it, and a new Snapshot puts the user where they were. The prototype shows it.
- **The server's form amending only the Snapshot that was sent**, and later ones that took the version over from it: earlier Snapshots keep what the server really held, but an undo to a Snapshot that was never sent itself writes that Event to the server again in the user's old form, and the rewrite needs a walk over the Snapshot's descendants.
- **The last common Snapshot as what a Conflict is compared with**: nothing stored, but wrong after an undo that isn't sent yet (see "Tracking and the Reference Snapshot").
- **The Reference Snapshot empty while Tracking**, set when a Conflict arises and cleared when it ends (the first form, 2026-11-15): the same information, but an Incoming Sync needs "set unless set", and the rule that the user's side being behind means an undo rests on the code alone. Always set, an Outgoing Sync can ask the Local Store whether the user's side has taken the server in (amended 2026-11-16, checked with the prototype).
- **The Snapshot both pointers were last on together as the Reference Snapshot**: it goes stale while the pointers stay apart without a Conflict. After a Join not yet sent, a second change by someone else to the same Event would be compared with the state before the first and read as a Conflict.
- **A switch for the user to turn Tracking off**: a way to hold back Outgoing Syncs, but a second reason for a Calendar not to be Tracking, which the Reference Snapshot alone couldn't tell from a Conflict.
- **The Mass-Change Guard on the user's actions, not on syncs**: one question when the user acts, no paused Calendar and no false alarm from edits that add up, but nothing would stand between a fault in deriving what to send and the server.
- **The Mass-Change Guard on every Outgoing Sync, imports and restores included**: one rule that reads no ancestry, but it asks a second time about what the user just confirmed.
- **A stored approval** (a field on the Calendar naming the approved Snapshot, or a flag on the Snapshot): sync would read no ancestry, but it repeats what the Snapshot's origin already says and would have to be cleared after an Outgoing Sync and on undo.
- **The Mass-Change Guard on Incoming Syncs too**: not needed, because undo takes a sync back and asks first.
- **A merge with both sides as parents for every Incoming Sync that finds changes on both sides** (the first form, 2026-11-15): the Calendar History records the real order and keeps the server's Snapshots, but undo has to ask which side at every such merge, and going back through the server's side after an undo not yet sent brings back what was undone. With a Join the user's side is one line; its order isn't the real order, so undoing only one's own edit means taking back a later Join first.
- **Taking the server's changes in after an undo, ending the redo path** (ADR 0020 as first written): nothing waits, but a sync can take redo away at any moment without a word.
- **A dialog for every Incoming Sync while the user's side is behind**: it tells the user, but it is a Conflict in all but name, comes at random moments, and leaves open the case of an undo followed by a change.
- **Moving the new Snapshot in before the redo path** when it touches none of its Events: redo survives, but Snapshots get new parents, so the Calendar History is no longer written only by adding, and a redo can bring back what the user undid to be rid of after an unrelated edit.
- **A stored flag for Held during Undo**: "Continue" would only clear it, but it is a second reason not to be Tracking that the Calendar History can't check; derived from the redo path it can't go stale.
- **Held during Undo hiding a Conflict, or the other way round**: one state at a time, but either Continue leads into a Conflict the user hasn't seen, or a precedence rule decides what the user is told.
- **The server's read-only as a Read-only Calendar** (as built with tickets 56 and 120): FreeCal never tries an edit that will fail, but Unsent Changes waiting when access is lost have no way out but the server, and undo, redo and Conflicts need rules of their own there.
- **Asking whether to wait when writes are first refused**: the user decides at once, but a dialog interrupts for a state that often passes; the bar lets the user decide when they like.
- **Reading privileges on every Poll for every Calendar the server doesn't let the user change**: regained access shows everywhere, but at one more request per Poll for each subscription and holiday Calendar, for ever.
- **Removing the mark after a warning instead of asking the server**: works offline, but lets the user start changes that are sure to wait.

## Consequences

- Intent is derived. Any fault that changes one side's Event Versions becomes writes to the server; the Mass-Change Guard and the tests of the comparison carry that weight.
- The Mass-Change Guard's count reads which Snapshot last changed an Event, against the rule that ancestry is only for the Calendar History and undo. It is the one exception, and it decides only whether to ask, never what to send.
- Small edits made offline or during a long Conflict add up to a paused Calendar.
- While a Conflict is open, the whole Calendar is stale in both directions, not just the Event in Conflict. The user can't hold back Outgoing Syncs in any other way.
- The Reference Snapshot is stored state, one field per Calendar, moved in two places (the comparison of the two sides and an Outgoing Sync's closing Database Transaction); the Store Check covers it. A fault that misses one of these moves leaves the Calendar looking as if it had a Conflict, with no Event in Conflict, until the next comparison of the two sides; the Store Check reports it.
- A Snapshot older than an Outgoing Sync can show the server's form of an Event Version, which the server didn't hold then: after an undo, even the First Sync's Snapshot.
- A Conflict can end without the user choosing a side, as soon as the two sides agree. An undo that takes back the user's part of a Conflict ends the Conflict at once; the Calendar is then Held during Undo until the user continues, redoes to the end or makes a change.
- An undo never left by redo, a change or "Continue" holds the server's changes back for as long, and the Calendar isn't Tracking meanwhile; the Status Mark and the bar say so.
- A Join puts the server's changes after the user's own on the user's side, whatever their real order. The server's own Snapshot is dropped once an Outgoing Sync moves the Server's Pointer to the user's side, so the Calendar History shows when FreeCal took the server's changes in, not when the server had them.
- A flag on the Calendar to hold back Outgoing Syncs can be added later beside the Reference Snapshot; for now there is none.
- If FreeCal stops in the middle of an Outgoing Sync, the next Incoming Sync finds changed ETags and fetches again; the server's form of that write is then recorded as a sync, and until then the Events show as not sent.
- On a CalDAV server that answers a write without an ETag, someone else's change to the same Event between the write and the read-back is recorded as part of the user's Snapshot.
- Sent Event Rows, the rule for whether a Conflict exists run on every write, Propagate's special cases for Unsent Changes, and the Sender's "nothing to send" comparison of texts go.
- Undoing a DELETE already sent creates the Event again under a new href, now with its Unimplemented Fields.
- A Calendar marked read-only when it was added, whose server allows changes later, shows it only when the user removes the mark, and removing it needs the server to be reachable.
- A server that says a Calendar is read-only though it would accept changes can't be overridden.
- While writes are refused, the user's changes and the server's go on side by side, and Conflicts can pile up; "Stop waiting and mark read-only" ends them all, and the user's waiting changes with them.
