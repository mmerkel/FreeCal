# Sync reads the two pointers: what differs is sent, ETags say what the server changed, and a Calendar is Tracking while it has no Conflict

This supersedes ADRs 0014 and 0015. It comes from the grilling of 2026-11-15 (see ADR 0017) and builds on the Calendar History (ADR 0018); the code follows with later tickets. The prototype of 2026-11-15 (`core/prototypes/calendar-history.PROTOTYPE.html`) settled the server's form of FreeCal's own write, and added the Reference Snapshot and the rule that Tracking means no Conflict.

Sync kept three records of its own: the list of Unsent Changes, the Mirror's text of every Server Object, and the Conflict tables with copies of two versions. With a User's Pointer and a Server's Pointer per Calendar, all three are derived, and sync becomes one question: what to do when the two pointers differ. Three sources answer it, each for one thing only: **ETags say whether the server changed; the Current-Version Marks say what to send; ancestry is only for the Calendar History and undo.**

**What to send.** The Events whose Event Version with the user's Current-Version Mark differs from the one with the server's, or exists on one side only. Nothing records that a change is unsent. The Sender builds each Server Object from the user's Event Versions alone (ADR 0017): versions on both sides is an update, on the user's side only a create, on the server's side only a delete. An Unsent Change, as the user sees it, is such a difference.

**Whether the server changed.** ETags and sync tokens say which Server Objects changed; only those are fetched and compared. A server that gives no ETags has every resource fetched on each Incoming Sync and compared for equality, through the same code. The two sides are then compared per Occurrence, three ways: the server's versions, the user's, and those of the Reference Snapshot (below), which while Tracking is where the Server's Pointer was before this fetch: an Occurrence only the server changed follows the server, one only the user changed stays to be sent, one changed on both sides to the same result agrees, and one changed differently on both sides is a Conflict. A change to the Recurring Event itself counts as a change to every Occurrence (ADR 0014, unchanged). The managed fields and the Unimplemented Fields are compared as two parts (ADR 0017).

**Tracking and the Reference Snapshot.** A Calendar is Tracking its server exactly while it has no Conflict: the user's side follows the server and the server is brought to the user's side. Tracking is not stored and the user has no switch for it; the user can only end Conflicts. What is stored, per Calendar, is the Reference Snapshot: empty while the Calendar is Tracking, and otherwise the Snapshot the Server's Pointer was on when the Conflict arose. It is what both sides are compared with. The last Snapshot the two pointers have in common can't serve: after an undo not yet sent it is the user's own Snapshot, so a later change on the server would look like the only change and the undo would be lost without a word.

**An Incoming Sync** does two steps in one Database Transaction. First, if the server's Events changed, it sets the Reference Snapshot to where the Server's Pointer is, unless one is set already, and moves the Server's Pointer to a new Snapshot holding the server's state. Second, if a Reference Snapshot is set, it runs the comparison of the two sides: with a Conflict left, nothing more happens; without one, the User's Pointer follows to the server's Snapshot if the user's side was on the Reference Snapshot, or else a merge Snapshot joins the two, and the Reference Snapshot is cleared. The user ending a Conflict is the same second step with the user's choices, and it also runs after every move of the User's Pointer while a Reference Snapshot is set (a change, an undo, a redo). So a Reference Snapshot is set exactly while the two sides are in Conflict, which the Store Check asks, and this is the only code that compares the two sides.

**The invariant.** While a Calendar is Tracking, the Server's Pointer moves forward only in a Database Transaction that also brings the user's side up to it, by following or by merging. An Incoming Sync whose user's side has nothing of its own makes one Snapshot both pointers move to; otherwise the server's side branches off and a merge joins the two. So outside the Incoming Sync's code, "the user's side is behind the server's" can only mean that the user undid something, and the server is to be brought to the user's side. No code may split the two steps of an Incoming Sync across Database Transactions: the next send would then take the server back.

**Sending.** The requests of a send run outside any Database Transaction; one Database Transaction at the end records the outcome. Every update and delete is conditional on the stored ETag (`If-Match`), so a write that succeeds proves nobody else changed that Server Object since FreeCal last read it. If everything was sent and the server holds what the user has, the Server's Pointer goes to the Snapshot that was sent, backwards too after an undo. What the server made of FreeCal's own write is no change by anyone: a new Snapshot on the server's side always means that someone else changed the server. Where the server stored another form than was sent, that form is written as a new Event Version which takes the sent one's place in every Snapshot that held it, and the sent one is dropped; Event Versions still never change, only links are rewritten, in the send's closing Database Transaction. A CalDAV answer with an ETag means the text was stored unchanged (RFC 4791 §5.3.4); without one FreeCal reads the resource back before the closing Database Transaction; Google's answer to a write is the stored event. Changes to other Events found in that fetch are someone else's and make a sync Snapshot. If not everything could be sent, one new Snapshot holds the server's state. A change the user makes while a send runs moves the User's Pointer on and is simply still different afterwards; it was made without seeing the server's form of the Event and is sent as the user made it. The Mass-Change Guard stays, for sends.

**Conflicts.** While a Calendar has a Conflict, nothing is sent and nothing from the server is merged, while FreeCal keeps fetching, so the Server's Pointer follows the server. No table and no mark on an Event holds a Conflict. Which Events are in Conflict, and the Server Version, User's Version and Last Agreed Version of each, are read by comparing both pointers with the Reference Snapshot. When the user ends a Conflict, one merge Snapshot with both sides as parents is made, also when the user picks one side whole and its content equals that parent's; undo can then ask which side to go back to (ADR 0020). A Conflict that goes away by itself, because one side came to agree with the other, ends at once: with the user's change, undo or redo that made them agree, or with the Incoming Sync that fetched the server's. The Calendar carries a Status Mark while it isn't Tracking, and FreeCal is insistent about open Conflicts; how is decided with the UI.

**Server Objects.** The Local Store keeps for each Server Object only where it is and which version FreeCal last saw: for CalDAV, the Calendar, UID, href and ETag. Its content is the Event Versions with the server's Current-Version Mark. A Server Object FreeCal can no longer read keeps those Event Versions and loses its stored ETag, so that it is fetched on every Incoming Sync until it reads, and sends for its UID wait. On Google each Exception is a Server Object of its own; its table comes with ticket 26.

**One CalDAV resource per href and per UID.** ADR 0015's rules stay, with "mirrored" read as "kept in the CalDAV table". At most one resource is kept per href and per UID in a Calendar, by unique indexes. A fetched resource holding several UIDs, or a UID that a kept resource already holds (an Ambiguous UID), is an Ignored Resource, remembered with its ETag in `caldav_ignored_resource`, written to the Log, and not fetched again until it changes; one FreeCal can't read is remembered without an ETag and fetched every time. The kept resource keeps its UID for as long as it holds it. Among several candidates in one Incoming Sync the first by the fixed order keeps it: the one holding the single Event or the Recurring Event, then the lowest href; a resource moved to another href competes like any other. When the kept resource is removed, changes its UID or comes to hold several UIDs or nothing, or FreeCal itself deletes it, the Ignored Resources holding the UID are fetched again in the next Incoming Sync and the first by the fixed order takes over. FreeCal never writes to a server to repair such resources. `docs/research/caldav-duplicate-uids.md` holds the evidence.

## Considered Options

- **A recorded list of Unsent Changes** (ADR 0015): the user's intent is stored, not derived, but every write must add to the list, an undo must repair it, and Sent Event Rows must guard it against changes made while a send runs.
- **The Mirror's text** (ADR 0015): see ADR 0017.
- **Deciding a sync's direction by ancestry** (whichever pointer is ahead in the graph is followed): no ETags needed, but it trusts the graph for writes to a server, and it must tell an undo from having fallen behind. With the invariant the two readings agree; ETags are used because they are the server's own word.
- **Comparing content on every sync, for every server**: one path without ETags, but every Event is fetched each time, and a server that stores a different form than sent looks changed for ever.
- **A separate Provider for CalDAV servers without ETags**: a second code path for a case the common one covers by fetching everything.
- **A record of whether the user's side fell behind or was undone**: the invariant makes "behind" mean "undone" everywhere outside the Incoming Sync.
- **A Conflict table with copies of both versions** (ADR 0014): a third and fourth copy of the Event columns, and a rule run on every write to keep them current.
- **A Conflict held per Event, with the rest of the Calendar syncing on**: less goes stale, but each Event needs a mark saying it is held back, and the pointers no longer describe a whole Calendar.
- **One Database Transaction per UID sent**: each success is recorded at once, but a send makes as many Snapshots as it has Events.
- **The server's form of FreeCal's own write as a Snapshot of its own**: no links rewritten, but "a sync" would then also mean "the server rewrote what I sent", and undo gets stuck: it goes back to the user's form, the send repeats, the server reforms it, and a new Snapshot puts the user where they were. The prototype shows it.
- **The server's form amending only the Snapshot that was sent**, and later ones that took the version over from it: earlier Snapshots keep what the server really held, but an undo to a Snapshot that was never sent itself writes that Event to the server again in the user's old form, and the rewrite needs a walk over the Snapshot's descendants.
- **The last common Snapshot as what a Conflict is compared with**: nothing stored, but wrong after an undo that isn't sent yet (see "Tracking and the Reference Snapshot").
- **A switch for the user to turn Tracking off**: a way to hold back sends, but a second reason for a Calendar not to be Tracking, which the Reference Snapshot alone couldn't tell from a Conflict.
- **No Mass-Change Guard**: considered because undo asks before reverting a sync; kept for sends, where a fault in deriving what to send would otherwise reach the server unchecked.

## Consequences

- Intent is derived. Any fault that changes one side's Event Versions becomes writes to the server; the Mass-Change Guard and the tests of the merge carry that weight.
- While a Conflict is open, the whole Calendar is stale in both directions, not just the Event in Conflict. The user can't hold back sends in any other way.
- The Reference Snapshot is stored state, one field per Calendar; the Store Check covers it.
- A Snapshot older than a send can show the server's form of an Event Version, which the server didn't hold then: after an undo, even the First Sync's Snapshot.
- A Conflict can end without the user choosing a side, as soon as the two sides agree. An undo that takes back the user's part of a Conflict moves the user's side on to the server's state at once, and the redo path ends there.
- A flag on the Calendar to hold back sends can be added later beside the Reference Snapshot; for now there is none.
- If FreeCal stops in the middle of a send, the next Incoming Sync finds changed ETags and fetches again; the server's form of that write is then recorded as a sync, and until then the Events show as not sent.
- On a CalDAV server that answers a write without an ETag, someone else's change to the same Event between the write and the read-back is recorded as part of the user's Snapshot.
- Sent Event Rows, the rule for whether a Conflict exists run on every write, Propagate's special cases for Unsent Changes, and the Sender's "nothing to send" comparison of texts go.
- Undoing a DELETE already sent creates the Event again under a new href, now with its Unimplemented Fields.
