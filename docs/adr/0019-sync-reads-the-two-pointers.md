# Sync reads the two pointers: what differs is sent, ETags say what the server changed, and a Conflict stops the Calendar Tracking

This supersedes ADRs 0014 and 0015. It comes from the grilling of 2026-11-15 (see ADR 0017) and builds on the Calendar History (ADR 0018); the code follows with later tickets, after a prototype.

Sync kept three records of its own: the list of Unsent Changes, the Mirror's text of every Server Object, and the Conflict tables with copies of two versions. With a User's Pointer and a Server's Pointer per Calendar, all three are derived, and sync becomes one question: what to do when the two pointers differ. Three sources answer it, each for one thing only: **ETags say whether the server changed; the Current-Version Marks say what to send; ancestry is only for the Calendar History and undo.**

**What to send.** The Events whose Event Version with the user's Current-Version Mark differs from the one with the server's, or exists on one side only. Nothing records that a change is unsent. The Sender builds each Server Object from the user's Event Versions alone (ADR 0017): versions on both sides is an update, on the user's side only a create, on the server's side only a delete. An Unsent Change, as the user sees it, is such a difference.

**Whether the server changed.** ETags and sync tokens say which Server Objects changed; only those are fetched and compared. A server that gives no ETags has every resource fetched on each Incoming Sync and compared for equality, through the same code. A Server Object that changed is merged per Occurrence by a three-way comparison of the server's new versions, the versions that had the server's Current-Version Mark before, and the user's: an Occurrence only the server changed follows the server, one only the user changed stays to be sent, one changed on both sides to the same result agrees, and one changed differently on both sides is a Conflict. A change to the Recurring Event itself counts as a change to every Occurrence (ADR 0014, unchanged). The managed fields and the Unimplemented Fields are compared as two parts (ADR 0017).

**Tracking.** Each Calendar is either Tracking its server or not. While it is, the user's side follows the server and the server is brought to the user's side. This one state is also the user's switch for sending and what a Conflict turns off.

**The invariant.** While a Calendar is Tracking, the Server's Pointer moves forward only in a Database Transaction that also brings the user's side up to it, by following or by merging. An Incoming Sync with nothing to send makes one Snapshot both pointers move to; otherwise the server's side branches off the last common Snapshot and a merge joins the two. So outside the Incoming Sync's code, "the user's side is behind the server's" can only mean that the user undid something, and the server is to be brought to the user's side. No code may fetch from a tracking Calendar without merging in the same Database Transaction: the next send would then take the server back.

**Sending.** The requests of a send run outside any Database Transaction; one Database Transaction at the end records the outcome. Every update and delete is conditional on the stored ETag (`If-Match`), so a write that succeeds proves nobody else changed that Server Object since FreeCal last read it. If everything was sent and the server holds what the user has, the Server's Pointer goes to the Snapshot that was sent, backwards too after an undo. What the server made of FreeCal's own write belongs to the Snapshot that was sent, after an undo too; a new Snapshot on the server's side always means that someone else changed the server. A CalDAV answer with an ETag means the text was stored unchanged (RFC 4791 §5.3.4); without one FreeCal reads the resource back before the closing Database Transaction; Google's answer to a write is the stored event. Changes to other Events found in that fetch are someone else's and make a sync Snapshot. If not everything could be sent, one new Snapshot holds the server's state. A change the user makes while a send runs moves the User's Pointer on and is simply still different afterwards. The Mass-Change Guard stays, for sends.

**Conflicts.** A Conflict makes its Calendar stop Tracking, in both directions: nothing is sent and nothing from the server is merged, while FreeCal keeps fetching, so the Server's Pointer follows the server. No table and no mark on an Event holds a Conflict. Which Events are in Conflict, and the Server Version, User's Version and Last Agreed Version of each, are read by comparing both pointers with the last Snapshot they have in common. Resolving, whether the user chooses or a merge needs no choice, makes one merge Snapshot with both sides as parents, also when the user picks one side whole and its content equals that parent's; undo can then ask which side to go back to (ADR 0020). Turning tracking back on by hand while the sides differ is the same merge. The Calendar carries a Status Mark while it isn't Tracking, and FreeCal is insistent about open Conflicts; how is decided with the UI.

**Server Objects.** The Local Store keeps for each Server Object only where it is and which version FreeCal last saw: for CalDAV, the Calendar, UID, href and ETag. Its content is the Event Versions with the server's Current-Version Mark. A Server Object FreeCal can no longer read keeps those Event Versions and loses its stored ETag, so that it is fetched on every Incoming Sync until it reads, and sends for its UID wait. On Google each Exception is a Server Object of its own; its table comes with ticket 26.

**One CalDAV resource per href and per UID.** ADR 0015's rules stay, with "mirrored" read as "kept in the CalDAV table". At most one resource is kept per href and per UID in a Calendar, by unique indexes. A fetched resource holding several UIDs, or a UID that a kept resource already holds (an Ambiguous UID), is an Ignored Resource, remembered with its ETag in `caldav_ignored_resource`, written to the Log, and not fetched again until it changes; one FreeCal can't read is remembered without an ETag and fetched every time. The kept resource keeps its UID for as long as it holds it. Among several candidates in one Incoming Sync the first by the fixed order keeps it: the one holding the single Event or the Recurring Event, then the lowest href; a resource moved to another href competes like any other. When the kept resource is removed, changes its UID or comes to hold several UIDs or nothing, or FreeCal itself deletes it, the Ignored Resources holding the UID are fetched again in the next Incoming Sync and the first by the fixed order takes over. FreeCal never writes to a server to repair such resources. `docs/research/caldav-duplicate-uids.md` holds the evidence.

## Considered Options

- **A recorded list of Unsent Changes** (ADR 0015): the user's intent is stored, not derived, but every write must add to the list, an undo must repair it, and Sent Event Rows must guard it against changes made while a send runs.
- **The Mirror's text** (ADR 0015): see ADR 0017.
- **Deciding a sync's direction by ancestry** (whichever pointer is ahead in the graph is followed): no ETags needed, but it trusts the graph for writes to a server, and it must tell an undo from having fallen behind. With the invariant the two readings agree; ETags are used because they are the server's own word.
- **Comparing content on every sync, for every server**: one path without ETags, but every Event is fetched each time, and a server that stores a different form than sent looks changed for ever.
- **A separate Provider for CalDAV servers without ETags**: a second code path for a case the common one covers by fetching everything.
- **A record of whether the user's side fell behind or was undone**: the invariant makes "behind" mean "undone" everywhere outside the Incoming Sync.
- **A Conflict table with copies of both versions** (ADR 0014): a third and fourth copy of the Event columns, and a rule run on every write to keep them current.
- **A Conflict held per Event, with the rest of the Calendar syncing on**: less goes stale, but each Event needs a mark saying it is held back, and the pointers no longer describe a whole Calendar.
- **One Database Transaction per UID sent**: each success is recorded at once, but a send makes as many Snapshots as it has Events.
- **The server's form of FreeCal's own write as a sync Snapshot**: no read-back tied to the send, but "a sync" would then also mean "the server rewrote what I sent", and undoing it would send the same text again.
- **No Mass-Change Guard**: considered because undo asks before reverting a sync; kept for sends, where a fault in deriving what to send would otherwise reach the server unchecked.

## Consequences

- Intent is derived. Any fault that changes one side's Event Versions becomes writes to the server; the Mass-Change Guard and the tests of the merge carry that weight.
- While a Conflict is open, the whole Calendar is stale in both directions, not just the Event in Conflict.
- If FreeCal stops in the middle of a send, the next Incoming Sync finds changed ETags and fetches again; the server's form of that write is then recorded as a sync, and until then the Events show as not sent.
- On a CalDAV server that answers a write without an ETag, someone else's change to the same Event between the write and the read-back is recorded as part of the user's Snapshot.
- Sent Event Rows, the rule for whether a Conflict exists run on every write, Propagate's special cases for Unsent Changes, and the Sender's "nothing to send" comparison of texts go.
- Undoing a DELETE already sent creates the Event again under a new href, now with its Unimplemented Fields.
- Still to decide with the prototype: how the Snapshot that was sent takes the server's form of it, given that Event Versions never change, in particular after an undo, where the Snapshot sent is an older one that others arose from.
