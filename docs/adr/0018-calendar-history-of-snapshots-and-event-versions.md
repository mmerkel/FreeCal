# The Calendar History: one line of Snapshots, and Event Versions that begin and end with them

With ADR 0020 this supersedes ADR 0009. It comes from the grilling of 2026-11-15 (see ADR 0017); the code follows with later tickets. Rewritten after the grilling of 2026-11-22 on the second point of `.scratch/freecal-v1/critiques.md`: as first written, the Calendar History was a tree per Calendar, with a User's Pointer and a Server's Pointer, merges (Snapshots with two parents) and Joins (tag `design/snapshot-tree`; see "Considered Options"). Adjusted after the grilling of 2026-11-22 on point 2 of `.scratch/freecal-v1/critiques-2.md`: the zero-length Event Version, and the Server Event Merge in place of the Automatic Resolution. Adjusted after the discussion of 2026-11-26 on point 7 of `.scratch/freecal-v1/critiques-2.md`: the Server Event Merges and Server Event Replacements are part of their Incoming Sync Snapshot instead of Snapshots of their own, and a Conflict is a row of its own naming the Last Agreed Version (tag `design/server-event-snapshots` keeps the form before).

The Change Journal recorded each change beside the Event Rows: the previous Event Version and a hash of the new one, in tables of their own, with Unsent Changes, the Mirror and the Conflict tables each holding a further view of the same Events. We replace all of them with one structure. The Events of all Calendars at one moment are a Snapshot, and the Snapshots form one line, each arisen from the one before. Each Event Version records the Snapshot it began with and the one it ended with; the server's Current-Version Mark records what the server holds. What FreeCal shows, what it has to send, what the server last had, what a Conflict is about and what an Undo takes back are all read from that one structure, so they can't disagree.

**Event Versions.** One table holds every Event Version: the fields FreeCal manages and the Unimplemented Fields (ADR 0017) of one single Event, Recurring Event or Exception, with its Calendar, UID and recurrence ID as obtained (ADR 0012), and two Snapshots: `begin`, the Snapshot it began with, and `end`, the one it ended with, empty while it is current. Its content never changes once written. Each write makes a new row, even when its content equals an earlier one: an edit back, both sides reaching the same content, an Undo or a redo bringing back an earlier state all write a copy. So each row is current for one unbroken stretch of the line, or for none (below), and two Event Versions are equal when their canonical forms are, never compared by row alone; the hash of an Event Version goes, and with it the hash format and its re-hashing migrations.

**Zero-length Event Versions.** A Snapshot's state is the Event Versions whose `begin` is that Snapshot or an earlier one and whose `end` is a later one or empty. The server's version of an Event that an Incoming Sync merges begins and ends with its Incoming Sync Snapshot (ADR 0019): a **zero-length Event Version**, in no Snapshot's state, never shown in the grid, there to carry the server's mark, as a combination is no version the server holds (decided 2026-11-22). The combination begins with the same Snapshot. An Event in Conflict needs none: its server's version becomes current with the Incoming Sync Snapshot and carries the server's mark itself (decided 2026-11-26). The schema enforces where it may occur, as a row hidden from the user's side changes what is sent: an insert trigger allows `end` equal to `begin` only where that Snapshot is an Incoming Sync Snapshot, and `end` comes after `begin` everywhere else. Every reading of a Snapshot's state uses the rule above; an Undo of a Snapshot takes as what it left behind only the Event Versions ending with it that began before it (ADR 0020).

Two Current-Version Marks say which rows are current. The user's is `end` being empty: one row per Calendar, UID and recurrence ID, by a partial unique index, so it can't disagree with the Calendar History. The server's is a stored mark, FreeCal's record of what the server holds (ADR 0019), one row per Calendar, UID and recurrence ID by a second unique index. Where one side takes over the other's version (a send succeeds, or both sides reached the same content) the server's mark moves to the user's row, and where the user's side takes the server's version (an Event only the server changed, or in Conflict) that version is one row with both marks from the start, so an Event Version both sides agree on is one row with both marks. The `event` table goes: `event` is a view over the rows whose `end` is empty, with a partial index over Calendar and start time, so reading the Occurrences of a window costs what it did.

**Snapshots.** A Snapshot is made by an action of the user, an import, the restore of a Backup, an Undo, which also records the Snapshot it takes back and, when it is limited to one Event, that Event's UID (ADR 0020), an Incoming Sync, with its Server Event Merges and Server Event Replacements (ADR 0019), or "Stop waiting and mark read-only" (ADR 0019), and records which, with the time it was made. Its parent is the Snapshot before it: the line's order is the order of the Snapshots' IDs, so no table of parents is needed. Which Calendars a Snapshot spans is read from the Event Versions that begin or end with it; a step that changes several Calendars together (a move, an import or a restore into several) is one Snapshot. The newest Snapshot is what FreeCal shows; no pointer names it. A Snapshot that would change nothing isn't made.

**Calendars.** A server Calendar enters the Local Store empty, when the user adds it, and a Local Calendar when the user creates it: with no Event Versions, so no Snapshot spans it yet (decided 2026-11-22, on point 4 of `.scratch/freecal-v1/critiques.md`, reversing the First Sync held in memory behind a modal dialog of 2026-11-16). An import or the restore of a Backup never creates a Calendar: each of its sources goes into an existing Target Calendar or is left out (decided 2026-11-21, reversing the Local Calendars an import created, of 2026-11-16). A server Calendar's First Sync is its first Incoming Sync and nothing else: with no sync token it is a **Full Fetch** (ADR 0019), every resource fetched and compared with the server's marks, of which there are none, so all of it is taken in as one Incoming Sync Snapshot, in one Database Transaction, as for any Incoming Sync. Nothing is written page by page and nothing records that a Calendar hasn't loaded yet: the Sync Status's last finished sync, none yet, says so, and the window shows it in the Syncing mark's tooltip ("Loading for the first time") and, after a failure, "Not loaded yet". The window stays usable throughout; the user can edit in the loading Calendar, and such a change is on the user's side only and sent afterwards. An interrupted First Sync is run again from the beginning by the next Incoming Sync. Removing the Calendar from FreeCal is the way to cancel it. The progress of an Incoming or Outgoing Sync that takes long, a First Sync's too, is shown in the window's status indicator and on the Calendar, not in a dialog; what is counted depends on the Provider.

**Keeping and dropping** (one rule since 2026-11-22, point 4 of `.scratch/freecal-v1/critiques-2.md`). What is kept is decided for Snapshots alone: a Snapshot is kept while a root reaches it, and every other Snapshot is dropped. The roots are the Snapshots of the last 90 days, the Incoming Sync Snapshots of open Conflicts and each Snapshot with which an Event Version carrying the server's mark ended. The edges lead from an Undo to the Snapshot it takes back (the prototype showed an Undo, kept by a row with the server's mark, outliving what it took back), and from an Incoming Sync Snapshot, through its Conflicts, to the Snapshots with which their Last Agreed Versions ended (ADR 0019), so that a kept Conflict can still show what each side changed. A Conflict goes with its Incoming Sync Snapshot (`ON DELETE CASCADE`). An Event Version goes with the Snapshot it ended with (`end` with `ON DELETE CASCADE`), so a kept Snapshot keeps every Event Version ending with it: the User's Version of a Conflict, the zero-length Event Versions of an Incoming Sync Snapshot, what a taken-back Snapshot replaced. A current Event Version has no `end` and is never dropped. `begin` refers to its Snapshot with `ON DELETE SET NULL`: empty, it means the Event Version began before the oldest kept Snapshot. A new kind of reference is a new root or edge, never a condition on Event Versions. The drop finds the Snapshots no root reaches and deletes them in one Database Transaction. The edges are foreign keys checked when the Database Transaction commits (`DEFERRABLE INITIALLY DEFERRED`), so a drop that misses an edge is refused whole; `ON DELETE RESTRICT` is checked at once and would force an order on the deletes. Two triggers enforce the roots that protect data, as a mistake in the roots would otherwise delete silently: one refuses to delete an Event Version carrying the server's mark, which the cascade would lose though the server holds it, and that invariant decides what is sent; the other refuses to delete an open Conflict, which would take its Incoming Sync Snapshot's User's Version with it. So a mistake in the drop is refused, except one that keeps too much. So a version the server still holds, after more than 90 days offline or with writes refused, keeps the Snapshot it ended with. The drop is tested by one scenario per root and per edge, and one in which a missed edge is refused at commit, each followed by the Store Check.

**Who may write.** The Write Permissions (ADR 0015) go. The Change Journal's made sure that no Event Row changed without its Journal Event Modification, its Unsent Change and the check for a Conflict; here a change is a new Snapshot with Event Versions beginning and ending, with no second table to forget. What remains is kept by the Local Store and by the shape of the interface:

- A zero-length Event Version only with an Incoming Sync Snapshot: the insert trigger (see "Zero-length Event Versions").
- An Event Version's content never changes: a trigger refuses every update but three, `end` from empty to a Snapshot, `begin` to empty (only the foreign key's cascade does it), and the server's mark. When an Outgoing Sync puts the server's form of an Event Version in the sent one's place (ADR 0019), the new row is written with the sent one's `begin` and `end`, and the sent one is deleted.
- One current Event Version per Calendar, UID and recurrence ID on each side: the two unique indexes. Event Versions, Snapshots and Conflicts refer to rows that exist: foreign keys.
- A Conflict only with an Incoming Sync Snapshot, and its time of resolution set once: an insert trigger and an update trigger (ADR 0019).
- An Undo's UID only on an Undo: a CHECK on the Snapshot table.
- An Incoming Sync's comparison and the writes it leads to are one Database Transaction (ADR 0019): the interface has no operation that moves the server's marks alone, only one that records what the server now holds and brings the user's side up to it.
- A stored ETag belongs to the Event Versions with the server's Current-Version Mark: one Database Transaction writes both. Every write runs in a Database Transaction, by its type, as before.

The functions that write Event Versions, Snapshots, marks and Conflicts are visible only to the Calendar History's module, and those of the CalDAV table and the Ignored Resources only to the Sync Engine's. Rust's visibility replaces the permission value.

**Where the invariants are recorded.** The invariants of the Local Store that can be asked of a stored state are recorded as the Store Check, beside the schema: a function in which each invariant is a named query, with one line stating the rule and its ADR, that reports every violation it finds. The tests run it after each scenario, so a rule that is wrong or no longer kept fails a test, and debug builds run it after every Database Transaction that writes the Calendar History, stopping with a panic on a violation; release builds never run it (decided 2026-11-22, on point 5 of `.scratch/freecal-v1/critiques.md`). An invariant that decides what is sent to a server is enforced by the schema, never by a query only, as the schema enforces it in use too. It covers what the schema can't enforce (`end` after `begin`, an Undo taking back an older Snapshot that is still kept, and, when limited to one Event, one whose UID that Snapshot changed, no open Conflict whose Event the user changed or an Undo changed since its Incoming Sync Snapshot, every Conflict having a Conflict Event for each single Event of its UID on either side or in the Last Agreed Version, each Last Agreed Version of the Conflict's Calendar, UID and recurrence ID, a zero-length Event Version only beside a version of the same Event beginning with the same Snapshot, every Event Version with a server's mark having a stored ETag where its Provider gives one); a constraint in the schema carries a comment naming the rule it enforces. The ADRs keep the reasons and don't repeat the list. An invariant about how a state was reached, such as ADR 0019's on the Incoming Sync, can't be a query: it stays a rule of the interface, stated in its ADR, and the Store Check says that it doesn't cover it.

**An Event's History** is a view of that Event's versions in the order of their `begin`, without an undo of its own. It shows the zero-length Event Version of a Server Event Merge as "on the server, before combining", before the combination that begins with the same Snapshot, the one place the user sees what the other side did. The server's version of an Event in Conflict is an ordinary entry, shown as "replaced by the server's version" while its Conflict is kept (ADR 0019).

## Considered Options

- **The Change Journal** (ADR 0009, tag `design/change-journal`): proven and in use, but the Event Rows, the previous versions, the Unsent Changes, the Mirror's text and the Conflict's copies are five stores that every write must keep in step, and each new field has to be added to each.
- **A history table beside the `event` table**, as first proposed: reads of current Events stay trivial, but the current row and its copy in the history are two stores kept in step by an invariant, and content the server and the user agree on is stored twice or three times.
- **A tree of Snapshots per Calendar with a User's Pointer and a Server's Pointer** (this ADR as written until 2026-11-22, tag `design/snapshot-tree`): undo moved a pointer back, and a Conflict held the server's line apart until the user merged. With an Undo a Snapshot of its own (ADR 0020) and Conflicts ended at once (ADR 0019), the server's line had no job left: its Reference Snapshot was always the Server's Pointer's Snapshot. The tree cross-checked the server's marks against the Server's Pointer, which the line can't.
- **One line per Calendar**, with a Snapshot Transition for each Calendar a Snapshot spans: a Calendar's history on its own, but a table of parents per Calendar, where the Undo History and the Calendar History are already one list across all Calendars, by time (ADR 0020).
- **A table of stretches** (Event Version, begin, end), with an Undo bringing an earlier row back: no copies, and an Event's earlier version stays the same row; but SQLite's unique indexes can't span two tables, so "one current version per Event" needs the Calendar, UID and recurrence ID copied onto the stretch, or a stored user's mark kept in step with it.
- **A link table naming the Event Versions that begin and end with each Snapshot**, written only by insert (the tree's form): no column changes after insert, but the current versions are a count of begins against ends, harder to index.
- **Snapshots older than 90 days dropped, with `begin` an ordered number without a foreign key**, checked by the Store Check: `begin` never changes, but it is the one reference to a Snapshot the Local Store doesn't enforce.
- **Retention as conditions on Event Versions and on Snapshots** (this ADR until 2026-11-22): each kept Event Version named directly, but every new kind of reference added a condition, and the conditions had already missed two cases: an Undo outliving the Snapshot it took back, and the zero-length Event Version of a Server Event Replacement kept by an open Conflict or an Undo, dropped as it had lost the server's mark while its Incoming Sync Snapshot was kept.
- **Edges from Event Versions as well as Snapshots**, a kept Event Version keeping only itself and its `end`: keeps less after a long time offline, but each kind of row needs its own roots, and a zero-length Event Version needs an edge of its own.
- **Testing the drop with generated histories** (edits, syncs, Undos, Conflicts and drops in random order, each followed by the Store Check; Alternative I of `.scratch/freecal-v1/critiques-2.md`): finds combinations nobody listed, but needs a generator of valid histories, and with the foreign keys and the triggers above every mistake in the drop but keeping too much is refused by the Local Store; a new reference is a new root or edge, enforced the same way.
- **Keeping every Snapshot row for ever**, dropping only old Event Versions: no cascade, but the Calendar History lists Snapshots that can't be undone or shown.
- **Keeping a Write Permission for the Calendar History's tables**: a value passed into every write shows a reviewer each call, where visibility lets any function inside the owning module call a low-level write, such as setting a mark. Rejected because no invariant is left that the value would guard and the schema or the interface doesn't; the owning module has to stay small enough for such a call to be obvious.
- **The invariants as comments on the schema, or in the ADRs only**: nothing to maintain beyond prose, but prose drifts from the code unnoticed, and no list says whether it is complete.
- **The First Sync held in memory, in a modal dialog** (2026-11-16 to 2026-11-22): a Calendar is never stored half loaded and never shown empty, but the window is locked for as long as a large Calendar loads, an interruption loses everything fetched and isn't retried, and the First Sync needs a write, a progress Signal, a Cancel and a dialog of its own. Its reasons against the form decided (an Undo of the first Incoming Sync Snapshot empties the Calendar on the server; a Calendar not loaded yet is stored and needs a status) are answered by the Mass-Change Guard, which counts every Undo, and by the Sync Status, which already records the last finished sync.
- **An empty first Snapshot for every Calendar**: not needed, as a Calendar with no Event Versions is spanned by no Snapshot.
- **Staging the fetched pages in a table outside the Calendar History**, read and cleared by the closing Database Transaction (Alternative D of `.scratch/freecal-v1/critiques.md`): an interrupted Full Fetch resumes, fetching only what the server's listing shows changed since, but it is a table with a lifecycle of its own and keeps the fetched text, a second format, in the Local Store. Deferred: it can come later as a cache inside the Incoming Sync, if Full Fetches on slow links turn out not to finish.
- **A dialog for the First Sync that doesn't lock the window**: needs a kind of dialog FreeCal doesn't have (focus, coming back to it, other dialogs opening over it), and keeps the First Sync's own write.
- **The First Sync stored page by page** (the spec's first form): Events appear as they load and an interrupted First Sync resumes, but a Calendar is stored without a complete first Incoming Sync Snapshot, with a flag and status texts for that state, and a paged rest can't remove Events deleted on the server meanwhile.
- **An import creating a Local Calendar for a file without a Target Calendar** (the form of 2026-11-16): a Takeout export migrates in one step, but an Undo of the import would then have to remove a Calendar. The same would hold for a restore of a Calendar that is gone.
- **The Store Check in use, before every Outgoing Sync and at startup, pausing a Calendar on a violation** (Alternative E of `.scratch/freecal-v1/critiques.md`): a fault in a user's Local Store would stop at the server, but the invariants that decide what is sent are already enforced by the schema on every write, the queries left decide undo, the display and dropping, never what is sent, and the faults that do send wrong writes (a wrong user's version, a server's mark on the wrong row) pass every query; it would add a paused Calendar the user can't mend. Mark Reconciliation (ADR 0019) checks the server's marks instead.
- **Refusing to undo a First Sync's Incoming Sync Snapshot** (ADR 0009, and this ADR until 2026-11-22): undoing it deletes the Calendar's Events on the server, but "first" has no clear meaning for a Calendar that was empty on the server, and the Mass-Change Guard asks before such an Undo is sent.

## Consequences

- A Calendar being added shows empty until its First Sync has finished, then all at once; only the Syncing mark and its tooltip say it is loading. An Event created there meanwhile may duplicate one not loaded yet.
- A First Sync that is interrupted, by the network or by FreeCal closing, starts again from the beginning at the next Incoming Sync; on a slow, unreliable link a large Calendar may take several attempts.
- An Undo of a Calendar's first Incoming Sync Snapshot, from the Calendar History, deletes its Events on the server once the Mass-Change Guard's question is answered.
- Migrating many Calendars, or restoring one that is gone, means creating each Calendar first. Cancelling the import's or the restore's dialog for that drops the Target Calendars chosen in it.
- An Event's row ID changes with every edit, undo and redo. The window and every caller identify an Event by its Combined Event Key (Calendar, UID, recurrence ID), never by row ID.
- A query that bypasses the `event` view sees old versions. Only the Calendar History's own code reads the table directly.
- Undoing and redoing a large import or restore writes as many rows as it changes, each time, until they are dropped after 90 days. An Event's History shows a version brought back by an Undo as a new entry.
- An Event Version may be in no Snapshot's state: every query of a Snapshot's state, and every reader of the schema, has to know that `begin` equal to `end` is a zero-length Event Version. The trigger's comment and the Store Check's list point to this ADR.
- An Event Version is not complete at insert: `end` is set once later, and `begin` is emptied once when its Snapshot is dropped.
- The server's Current-Version Mark is the only record of what the server holds, and only Mark Reconciliation, once a week (ADR 0019), checks it: until then a mark not moved leads to a write sent again, or to a change of the server's compared with the wrong base. The tests of the comparison carry that weight.
- After more than 90 days offline, or with writes refused for that long, single Snapshots outlive the 90 days, each with every Event Version that ended with it: an unsent change made by a large import keeps the import's earlier versions.
- A change to the schema touches three places: the schema, the Store Check and an ADR.
- The journal modules, the Conflict storage, the Unsent Changes, the Mirror and their tests are replaced; the spec's Change Journal section and ticket 19's list are rewritten. In `GLOSSARY.md`, Event Version now means a row of this table; the entries for the Change Journal, Journal Transaction, Journal Event Modification, Event Row, Mirror and those built on them are revised as the code changes.
- Write Permissions, Guards and Unguarded Writes go from the code, `CODING_STANDARDS.md` and `GLOSSARY.md` as the code changes (see "Who may write").
