# The Calendar History: one line of Snapshots, and Event Versions that begin and end with them

With ADR 0020 this supersedes ADR 0009. It comes from the grilling of 2026-11-15 (see ADR 0017); the code follows with later tickets. Rewritten after the grilling of 2026-11-22 on the second point of `.scratch/freecal-v1/critiques.md`: as first written, the Calendar History was a tree per Calendar, with a User's Pointer and a Server's Pointer, merges and Joins (tag `design/snapshot-tree`; see "Considered Options").

The Change Journal recorded each change beside the Event Rows: the previous Event Version and a hash of the new one, in tables of their own, with Unsent Changes, the Mirror and the Conflict tables each holding a further view of the same Events. We replace all of them with one structure. The Events of all Calendars at one moment are a Snapshot, and the Snapshots form one line, each arisen from the one before. Each Event Version records the Snapshot it began with and the one it ended with; the server's Current-Version Mark records what the server holds. What FreeCal shows, what it has to send, what the server last had, what a Conflict is about and what an Undo takes back are all read from that one structure, so they can't disagree.

**Event Versions.** One table holds every Event Version: the fields FreeCal manages and the Unimplemented Fields (ADR 0017) of one single Event, Recurring Event or Exception, with its Calendar, UID and recurrence ID as obtained (ADR 0012), and two Snapshots: `begin`, the Snapshot it began with, and `end`, the one it ended with, empty while it is current. Its content never changes once written. Each write makes a new row, even when its content equals an earlier one: an edit back, both sides reaching the same content, an Undo or a redo bringing back an earlier state all write a copy. So each row is current for one unbroken stretch of the line, and two Event Versions are equal when their canonical forms are, never compared by row alone; the hash of an Event Version goes, and with it the hash format and its re-hashing migrations.

Two Current-Version Marks say which rows are current. The user's is `end` being empty: one row per Calendar, UID and recurrence ID, by a partial unique index, so it can't disagree with the Calendar History. The server's is a stored mark, FreeCal's record of what the server holds (ADR 0019), one row per Calendar, UID and recurrence ID by a second unique index. Where one side takes over the other's version (a send succeeds, or both sides reached the same content) the server's mark moves to the user's row, so an Event Version both sides agree on is one row with both marks. The `event` table goes: `event` is a view over the rows whose `end` is empty, with a partial index over Calendar and start time, so reading the Occurrences of a window costs what it did.

**Snapshots.** A Snapshot is made by an action of the user, an import, the restore of a Backup, an Undo, which also records the Snapshot it takes back (ADR 0020), a Server Intake, a Server Event Replacement or an Automatic Resolution (ADR 0019), or "Stop waiting and mark read-only" (ADR 0019), and records which, with the time it was made. Its parent is the Snapshot before it: the line's order is the order of the Snapshots' IDs, so no table of parents is needed. Which Calendars a Snapshot spans is read from the Event Versions that begin or end with it; a step that changes several Calendars together (a move, an import or a restore into several) is one Snapshot. The newest Snapshot is what FreeCal shows; no pointer names it. A Snapshot that would change nothing isn't made.

**Calendars.** A server Calendar enters the Local Store empty, when the user adds it, and a Local Calendar when the user creates it: with no Event Versions, so no Snapshot spans it yet (decided 2026-11-22, on point 4 of `.scratch/freecal-v1/critiques.md`, reversing the First Sync held in memory behind a modal dialog of 2026-11-16). An import or the restore of a Backup never creates a Calendar: each of its sources goes into an existing Target Calendar or is left out (decided 2026-11-21, reversing the Local Calendars an import created, of 2026-11-16). A server Calendar's First Sync is its first Incoming Sync and nothing else: with no sync token it is a **Full Fetch** (ADR 0019), every resource fetched and compared with the server's marks, of which there are none, so all of it is taken in as one Server Intake, in one Database Transaction, as for any Incoming Sync. Nothing is written page by page and nothing records that a Calendar hasn't loaded yet: the Sync Status's last finished sync, none yet, says so, and the window shows it in the Syncing mark's tooltip ("Loading for the first time") and, after a failure, "Not loaded yet". The window stays usable throughout; the user can edit in the loading Calendar, and such a change is on the user's side only and sent afterwards. An interrupted First Sync is run again from the beginning by the next Incoming Sync. Removing the Calendar from FreeCal is the way to cancel it. The progress of an Incoming or Outgoing Sync that takes long, a First Sync's too, is shown in the window's status indicator and on the Calendar, not in a dialog; what is counted depends on the Provider.

**Keeping and dropping.** Snapshots older than 90 days are dropped. `begin` refers to its Snapshot with `ON DELETE SET NULL`: empty, it means the Event Version began before the oldest kept Snapshot. `end` refers to its Snapshot with `ON DELETE RESTRICT`. Dropping deletes, first, the Event Versions whose `end` is older than 90 days, that have no server's mark, that no Server Event Replacement names as its Last Agreed Version and whose `end` isn't a Server Event Replacement without a Resolution, so an open Conflict is never dropped; and then the Snapshots older than 90 days that no kept Event Version's `end` names and that no kept Undo takes back. An Undo refers to the Snapshot it takes back with `ON DELETE RESTRICT` (decided 2026-11-22: the prototype showed an Undo, kept by a row with the server's mark, outliving what it took back). So a version the server still holds, after more than 90 days offline or with writes refused, keeps the Snapshot it ended with, and the foreign keys enforce it. Dropping a Server Event Replacement drops its Resolution with it (ADR 0019).

**Who may write.** The Write Permissions (ADR 0015) go. The Change Journal's made sure that no Event Row changed without its Journal Event Modification, its Unsent Change and the check for a Conflict; here a change is a new Snapshot with Event Versions beginning and ending, with no second table to forget. What remains is kept by the Local Store and by the shape of the interface:

- An Event Version's content never changes: a trigger refuses every update but three, `end` from empty to a Snapshot, `begin` to empty (only the foreign key's cascade does it), and the server's mark. When an Outgoing Sync puts the server's form of an Event Version in the sent one's place (ADR 0019), the new row is written with the sent one's `begin` and `end`, and the sent one is deleted.
- One current Event Version per Calendar, UID and recurrence ID on each side: the two unique indexes. Event Versions, Snapshots and Resolutions refer to rows that exist: foreign keys.
- An Incoming Sync's comparison and the writes it leads to are one Database Transaction (ADR 0019): the interface has no operation that moves the server's marks alone, only one that records what the server now holds and brings the user's side up to it.
- A stored ETag belongs to the Event Versions with the server's Current-Version Mark: one Database Transaction writes both. Every write runs in a Database Transaction, by its type, as before.

The functions that write Event Versions, Snapshots, marks and Resolutions are visible only to the Calendar History's module, and those of the CalDAV table and the Ignored Resources only to the Sync Engine's. Rust's visibility replaces the permission value.

**Where the invariants are recorded.** The invariants of the Local Store that can be asked of a stored state are recorded as the Store Check, beside the schema: a function in which each invariant is a named query, with one line stating the rule and its ADR, that reports every violation it finds. The tests run it after each scenario, so a rule that is wrong or no longer kept fails a test, and debug builds run it after every Database Transaction that writes the Calendar History, stopping with a panic on a violation; release builds never run it (decided 2026-11-22, on point 5 of `.scratch/freecal-v1/critiques.md`). An invariant that decides what is sent to a server is enforced by the schema, never by a query only, as the schema enforces it in use too. It covers what the schema can't enforce (`end` after `begin`, an Undo taking back an older Snapshot that is still kept, every Undo of a Server Event Replacement having its Resolution, every Event Version with a server's mark having a stored ETag where its Provider gives one); a constraint in the schema carries a comment naming the rule it enforces. The ADRs keep the reasons and don't repeat the list. An invariant about how a state was reached, such as ADR 0019's on the Incoming Sync, can't be a query: it stays a rule of the interface, stated in its ADR, and the Store Check says that it doesn't cover it.

**An Event's History** is a view of that Event's versions in the order of their `begin`, without an undo of its own.

## Considered Options

- **The Change Journal** (ADR 0009, tag `design/change-journal`): proven and in use, but the Event Rows, the previous versions, the Unsent Changes, the Mirror's text and the Conflict's copies are five stores that every write must keep in step, and each new field has to be added to each.
- **A history table beside the `event` table**, as first proposed: reads of current Events stay trivial, but the current row and its copy in the history are two stores kept in step by an invariant, and content the server and the user agree on is stored twice or three times.
- **A tree of Snapshots per Calendar with a User's Pointer and a Server's Pointer** (this ADR as written until 2026-11-22, tag `design/snapshot-tree`): undo moved a pointer back, and a Conflict held the server's line apart until the user merged. With an Undo a Snapshot of its own (ADR 0020) and Conflicts ended at once (ADR 0019), the server's line had no job left: its Reference Snapshot was always the Server's Pointer's Snapshot. The tree cross-checked the server's marks against the Server's Pointer, which the line can't.
- **One line per Calendar**, with a Snapshot Transition for each Calendar a Snapshot spans: a Calendar's history on its own, but a table of parents per Calendar, where the Undo History and the Calendar History are already one list across all Calendars, by time (ADR 0020).
- **A table of stretches** (Event Version, begin, end), with an Undo bringing an earlier row back: no copies, and an Event's earlier version stays the same row; but SQLite's unique indexes can't span two tables, so "one current version per Event" needs the Calendar, UID and recurrence ID copied onto the stretch, or a stored user's mark kept in step with it.
- **A link table naming the Event Versions that begin and end with each Snapshot**, written only by insert (the tree's form): no column changes after insert, but the current versions are a count of begins against ends, harder to index.
- **Snapshots older than 90 days dropped, with `begin` an ordered number without a foreign key**, checked by the Store Check: `begin` never changes, but it is the one reference to a Snapshot the Local Store doesn't enforce.
- **Keeping every Snapshot row for ever**, dropping only old Event Versions: no cascade, but the Calendar History lists Snapshots that can't be undone or shown.
- **Keeping a Write Permission for the Calendar History's tables**: a value passed into every write shows a reviewer each call, where visibility lets any function inside the owning module call a low-level write, such as setting a mark. Rejected because no invariant is left that the value would guard and the schema or the interface doesn't; the owning module has to stay small enough for such a call to be obvious.
- **The invariants as comments on the schema, or in the ADRs only**: nothing to maintain beyond prose, but prose drifts from the code unnoticed, and no list says whether it is complete.
- **The First Sync held in memory, in a modal dialog** (2026-11-16 to 2026-11-22): a Calendar is never stored half loaded and never shown empty, but the window is locked for as long as a large Calendar loads, an interruption loses everything fetched and isn't retried, and the First Sync needs a write, a progress Signal, a Cancel and a dialog of its own. Its reasons against the form decided (an Undo of the first Server Intake empties the Calendar on the server; a Calendar not loaded yet is stored and needs a status) are answered by the Mass-Change Guard, which counts every Undo, and by the Sync Status, which already records the last finished sync.
- **An empty first Snapshot for every Calendar**: not needed, as a Calendar with no Event Versions is spanned by no Snapshot.
- **Staging the fetched pages in a table outside the Calendar History**, read and cleared by the closing Database Transaction (Alternative D of `.scratch/freecal-v1/critiques.md`): an interrupted Full Fetch resumes, fetching only what the server's listing shows changed since, but it is a table with a lifecycle of its own and keeps the fetched text, a second format, in the Local Store. Deferred: it can come later as a cache inside the Incoming Sync, if Full Fetches on slow links turn out not to finish.
- **A dialog for the First Sync that doesn't lock the window**: needs a kind of dialog FreeCal doesn't have (focus, coming back to it, other dialogs opening over it), and keeps the First Sync's own write.
- **The First Sync stored page by page** (the spec's first form): Events appear as they load and an interrupted First Sync resumes, but a Calendar is stored without a complete first Server Intake, with a flag and status texts for that state, and a paged rest can't remove Events deleted on the server meanwhile.
- **An import creating a Local Calendar for a file without a Target Calendar** (the form of 2026-11-16): a Takeout export migrates in one step, but an Undo of the import would then have to remove a Calendar. The same would hold for a restore of a Calendar that is gone.
- **The Store Check in use, before every Outgoing Sync and at startup, pausing a Calendar on a violation** (Alternative E of `.scratch/freecal-v1/critiques.md`): a fault in a user's Local Store would stop at the server, but the invariants that decide what is sent are already enforced by the schema on every write, the queries left decide undo, the display and dropping, never what is sent, and the faults that do send wrong writes (a wrong user's version, a server's mark on the wrong row) pass every query; it would add a paused Calendar the user can't mend. Mark Reconciliation (ADR 0019) checks the server's marks instead.
- **Refusing to undo a First Sync's Server Intake** (ADR 0009, and this ADR until 2026-11-22): undoing it deletes the Calendar's Events on the server, but "first" has no clear meaning for a Calendar that was empty on the server, and the Mass-Change Guard asks before such an Undo is sent.

## Consequences

- A Calendar being added shows empty until its First Sync has finished, then all at once; only the Syncing mark and its tooltip say it is loading. An Event created there meanwhile may duplicate one not loaded yet.
- A First Sync that is interrupted, by the network or by FreeCal closing, starts again from the beginning at the next Incoming Sync; on a slow, unreliable link a large Calendar may take several attempts.
- An Undo of a Calendar's first Server Intake, from the Calendar History, deletes its Events on the server once the Mass-Change Guard's question is answered.
- Migrating many Calendars, or restoring one that is gone, means creating each Calendar first. Cancelling the import's or the restore's dialog for that drops the Target Calendars chosen in it.
- An Event's row ID changes with every edit, undo and redo. The window and every caller identify an Event by its Combined Event Key (Calendar, UID, recurrence ID), never by row ID.
- A query that bypasses the `event` view sees old versions. Only the Calendar History's own code reads the table directly.
- Undoing and redoing a large import or restore writes as many rows as it changes, each time, until they are dropped after 90 days. An Event's History shows a version brought back by an Undo as a new entry.
- An Event Version is not complete at insert: `end` is set once later, and `begin` is emptied once when its Snapshot is dropped.
- The server's Current-Version Mark is the only record of what the server holds, and only Mark Reconciliation, once a week (ADR 0019), checks it: until then a mark not moved leads to a write sent again, or to a change of the server's compared with the wrong base. The tests of the comparison carry that weight.
- After more than 90 days offline, or with writes refused for that long, single Snapshots outlive the 90 days.
- A change to the schema touches three places: the schema, the Store Check and an ADR.
- The journal modules, the Conflict storage, the Unsent Changes, the Mirror and their tests are replaced; the spec's Change Journal section and ticket 19's list are rewritten. In `GLOSSARY.md`, Event Version now means a row of this table; the entries for the Change Journal, Journal Transaction, Journal Event Modification, Event Row, Mirror and those built on them are revised as the code changes.
- Write Permissions, Guards and Unguarded Writes go from the code, `CODING_STANDARDS.md` and `GLOSSARY.md` as the code changes (see "Who may write").
