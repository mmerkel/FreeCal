# Undo is a Snapshot that takes back an earlier one

With ADR 0018 this supersedes ADR 0009, and reverses its choice of undo per Event. It comes from the grilling of 2026-11-15 (see ADR 0017); the code follows with later tickets. Rewritten after the grilling of 2026-11-21 on the first point of `.scratch/freecal-v1/critiques.md`: as first written, undo moved a Calendar's User's Pointer back to the parent Snapshot (see "Considered Options"). Adjusted after the grilling of 2026-11-22 on the second point: the Calendar History is one line without pointers, and Conflicts end at once with a Server Event Replacement (ADRs 0018 and 0019), so merges with two parents and Joins are gone. Adjusted after the discussion of 2026-11-26 on point 7 of `.scratch/freecal-v1/critiques-2.md`: an Undo can be limited to one Event, and the Server Event Merges and Server Event Replacements are part of their Incoming Sync Snapshot (tag `design/server-event-snapshots` keeps the form before). The prototype `core/prototypes/calendar-history.PROTOTYPE.html` played the rules below through in the tree's form (tag `design/snapshot-tree`); it is reworked to the line next. Adjusted after the grilling of 2026-11-28 on point 5 of `.scratch/freecal-v1/critiques-2.md`: an Undo takes back what it can and asks first about the rest, in place of being refused whole, and Ctrl+Z passes over only Snapshots of which nothing can be undone.

Undo per Event had to work out which later changes stood in the way, undo those first, check hashes, and classify the result as benign or dangerous. Moving the User's Pointer back was one write, but it made Ctrl+Z step through syncs, so that a stray Ctrl+Z took back a colleague's change on the server, and taking back one's own change of two hours ago took back every sync since. It also made the server's changes wait while redo was possible, moved the Server's Pointer backwards, and made redo ask at forks and between Calendars. An undo that is a Snapshot of its own uses the comparison per Occurrence that sync already has (ADR 0019), and the Calendar History is only ever added to.

- **An Undo** is a Snapshot whose origin names the one earlier Snapshot it takes back, written once. Its content is the outcome of the comparison per Occurrence (ADR 0019): what the taken-back Snapshot left, the Event Versions ending with it that began before it (so never a zero-length one, ADR 0018), is what both are compared with, the current versions are one side, and the versions it ended the other. Where nothing has changed since, the Event goes back to the version before, as a copy (ADR 0018). It spans the Calendars that Snapshot spans and is made in one Database Transaction, then sent like any change. The Snapshot taken back is older and still kept, which the Store Check asks; a First Sync's Incoming Sync Snapshot too, which deletes the Calendar's Events on the server once the Mass-Change Guard has asked (decided 2026-11-22, ADR 0018). An import or a restore doesn't create Calendars (ADR 0018), so its Undo never removes one.
- **Limited to one Event** (decided 2026-11-26). An Undo can be limited to one UID, recorded beside the Snapshot it takes back: it then takes back only that UID's Events, in every Calendar the Snapshot spans, so a move is taken back on both sides, as it keeps its UID, unless one side's Calendar can't be written (see "Asking first"). Any Snapshot can be undone so from the Calendar History ("Undo this Event"); the Conflict's "Restore my version" and the Server Event Merge's toast "Undo" are such Undos of an Incoming Sync Snapshot (ADR 0019). Everything else about an Undo holds for it: it asks first where it can't be done whole, it is combined by field groups, and its redo is an Undo of it like any other. Ctrl+Z is never limited.
- **Asking first** (decided 2026-11-28, point 5 of `.scratch/freecal-v1/critiques-2.md`, in place of an Undo refused whole). An Undo takes back every Event it can and leaves out the rest. An Event can't be taken back when the comparison finds a Conflict, which is when something the Undo would take back has changed since (see "Where both changed"), or when its Calendar is marked read-only or was removed (ADR 0018). Where every Event can be taken back, the Undo is made at once. Otherwise nothing is written until the user has answered a dialog: one rule for every cause, moves included. The dialog names the Snapshot and lists each Event left out with why, naming the later change: `Standup was changed on the server since`, `… by "Resize Standup"` when the later change is the user's own, `Standup was replaced by the server's version`, `“Home” is read-only`, `its Calendar no longer exists`. Each has "Open"; one replaced by the server's version also has "Restore my version", the Undo of that Incoming Sync Snapshot limited to it (decided 2026-11-22). The dialog offers "Undo the others" with their number, while any can be taken back; "Undo all over the later changes", while a Conflict leaves any out, which makes the Undo with the state before the taken-back Snapshot winning in every Occurrence changed on both sides; and "Cancel". It is the same from Ctrl+Z and from the Calendar History.
- **A move with one side that can't be written** is taken back on the other side only, and the dialog says what that does. Where the origin can be written, the Event is restored there: `“X” is read-only. Restore Standup in “Work”? It stays in “X” too.`, or `The Calendar it was moved to no longer exists. Restore Standup in “Work”?`. Where only the target can, the Event is deleted there, and so gone: `The Calendar it came from no longer exists. Delete Standup from “Home”?`. Redo brings it back. A Snapshot records that it is a move (ADR 0018), and an Undo or redo of a move is one through the Snapshot it takes back, so a move whose one side was deleted with its Calendar isn't taken for a create or a delete in the other.
- **The Undo** is a Snapshot of its own holding what it took back, in effect whole; what it left out stays in effect in the Snapshot taken back. An Undo that would change nothing is refused with a toast.
- **Ctrl+Z** takes back the newest of the user's own Snapshots that is in effect, across all Calendars, by when each was made. The user's own are those of an action of the user (create, edit, move, delete), an import, a Backup restore and "Stop waiting and mark read-only" (ADR 0019). Incoming Sync Snapshots, a First Sync's among them, are not, and Ctrl+Z passes over them, and over Undos. It also passes over a Snapshot of which every Event still in effect is in a Calendar marked read-only or removed, checked at each press, as nothing there can be undone however the user answers. At any other Snapshot it stops: it undoes it, or asks as above, without a button to skip to the change before (decided 2026-11-28). After "Undo the others", the next Ctrl+Z reaches the same Snapshot and asks about the Events left; once a read-only mark is removed, it takes back those Events of that Calendar. A Snapshot is in effect while some UID it changed isn't taken back by an Undo in effect, whole or limited to that UID; Ctrl+Z on a Snapshot partly taken back takes back the rest. A restart doesn't reset it.
- **Redo** (Ctrl+Shift+Z, Ctrl+Y) takes back the newest Undo in effect, however it was made (Ctrl+Z, the Calendar History, "Undo all over the later changes"), by the same rule: a Snapshot whose origin names that Undo. It is offered until the user makes a change of their own; syncs don't end it, and nothing is dropped when it ends. A redo asks like an Undo; its dialog offers "Redo all over the later changes" in place of "Undo all over the later changes", and it passes over the Undos of which nothing left can be written, as Ctrl+Z does. As a redo is itself an Undo, the change it brings back is in effect again, and the next Ctrl+Z takes it back once more.
- **The Calendar History** window lists the Snapshots of all Calendars together, newest first, with filters for one Calendar and for the user's own changes. Any Snapshot can be undone from there, whole, in all Calendars it spans, or limited to one Event, an Incoming Sync Snapshot included, a First Sync's too. An Undo of a whole Incoming Sync Snapshot takes back its Server Event Merges and Server Event Replacements too, which resolves its Conflicts (ADR 0019). There is no undo for one Calendar alone and no taking a Calendar back to before a Snapshot: both would leave half a move without asking.
- **No question where an Undo can be done whole** (decided 2026-11-21, here and for an Incoming Sync Snapshot; since 2026-11-28 one that can't asks first, see "Asking first"): the toast after an Undo says what was undone, a change on the server too, and offers "Redo"; the toast after a redo says what was redone. The Mass-Change Guard counts every Undo at the Outgoing Sync that follows, an import's too (ADR 0019).
- **An Undo of a Server Event Replacement**, the Incoming Sync Snapshot's limited to that Event or whole, restores the User's Version, is sent like any change, and resolves the Conflict (ADR 0019). Its redo puts the server's version back, and the Conflict stays resolved. **An Undo of a Server Event Merge** likewise brings back the User's Version without the server's change and is sent; there is no Conflict to resolve. It is what the toast's "Undo" after a Server Event Merge does (ADR 0019).
- **Where both changed** (decided 2026-11-22, by the field groups since point 2 of `.scratch/freecal-v1/critiques-2.md`): an Event that the Undo and a later change both change is compared by the field groups of an Incoming Sync (ADR 0019) and combined, each group from the side that changed it; it is a Conflict, left out and asked about (see "Asking first"), where both changed the same group, or one the times and the other any other group but the Unimplemented Fields, or the Undo a whole Recurring Event and the later change one Occurrence. So sync and Undo combine by one rule, and Unimplemented Fields changed on both sides are a Conflict like any group, no longer the current version's winning. No extra Snapshot: the Undo's content is the combination.
- **Read-only Calendars** (decided 2026-11-21, reworded 2026-11-28): an Event in a Calendar marked read-only is left out of an Undo as one in a Conflict is, and the dialog names the Calendar; for a move into or out of one, see "A move with one side that can't be written". Ctrl+Z passes over a Snapshot of which every Event still in effect is in such a Calendar or a removed one, and the Calendar History shows it without "Undo" (decided 2026-11-22: an Undo that could do nothing offers no button). Incoming Syncs still take the server's changes in, and Unsent Changes made before the mark are still sent. A Calendar whose server refuses changes isn't read-only: undo works there and its changes wait (ADR 0019).
- **Events with guests** are undone and redone like any Event, although the user can't edit them, until the attendee features (ticket 126) decide how changes to them reach attendees (decided 2026-11-21).
- The Dangerous Undo goes, with its thresholds and its question.

## Considered Options

- **Undo per Event** (ADR 0009): an old import can be undone without touching what came after it in other Events, but it needs the hash check, the search for changes in between, the rule for undoing a Journal Transaction whole, and the Dangerous Undo.
- **Undo moving the User's Pointer back** (this ADR as first written, 2026-11-15): one write, nothing compared, and undo and redo never refused. But Ctrl+Z steps through syncs, so what it reaches depends on when the last Poll ran; taking back an older change takes back everything since, colleagues' changes included; the server's changes wait while redo is possible (Held during Undo, with its Status Mark, bar and "Continue"); the Server's Pointer moves backwards after an undo is sent; and redo has to ask at forks and between Calendars.
- **Swapping a Snapshot of the user with the sync Snapshot after it, then undoing** (noted on 2026-11-16 under "Left open" of the first form): Ctrl+Z over the user's own changes with the pointer moves kept, but a Snapshot's parents could change, which nothing else does, and a sync Snapshot would show a state the server never held. An Undo takes back a Snapshot from the middle without it.
- **Ctrl+Z over every Snapshot, syncs included**, with Undo as a Snapshot: one rule for all, but a stray Ctrl+Z after a Poll takes back a colleague's change. The Calendar History offers that, on purpose.
- **Refusing an Undo whole** (this ADR until 2026-11-28): no Undo leaves half a move or half an import, and no dialog asks, but one read-only or removed Calendar blocked a whole Snapshot, a Conflict on 3 of 50 imported Events blocked the other 47, and a removed Calendar needed a rule of its own (Alternative J of `.scratch/freecal-v1/critiques-2.md`). Taking back what can be taken back, the decision, was first rejected because it left half a move without a word; asking first answers that.
- **Taking back what can be taken back and reporting the rest afterwards**, in a toast: no dialog before, but a move would already be half taken back when the user reads of it, and an older change taken back by Ctrl+Z in place of a newer one.
- **Undos always whole** (until 2026-11-26): one shape of Undo, but taking back the server's part of one Event needed a Snapshot per Event merged or in Conflict (ADR 0019, Considered Options), and one Event of an import could only be taken back by editing it.
- **An Undo limited to one Event of an Incoming Sync Snapshot only**: Undos of the user's own Snapshots stay whole, but it is a second rule, with a trigger to enforce it, and the question why one Event of a sync can be undone but not one of an import.
- **Limited to Calendar and UID** instead of UID: one Event exactly, but it would split a move, which keeps its UID across two Calendars.
- **Ctrl+Z passing over a Snapshot with Events left out by a Conflict**, silently, or by a button "Skip to the change before" in the dialog, or silently once the user had been asked (2026-11-28): Ctrl+Z could go further back while keeping the Events changed since, but it would take back an older change while a newer one that could still be undone stays; the button would make Ctrl+Z's dialog differ from the Calendar History's, and remembering the answer would make what Ctrl+Z reaches depend on a stored past question. Stopping leaves the choice to the user, and the Calendar History reaches older changes. Passing over a Snapshot left only in read-only or removed Calendars costs no choice, as nothing there can be undone.
- **Undo for one Calendar, and taking a Calendar back to before a Snapshot** (the first form): useful after a mistake in one Calendar, but it leaves one UID in two Calendars after a move; the combined Calendar History undoes any one Snapshot instead.
- **Asking before undoing a change from a server**: a guard for the Calendar History's undo of a sync, but a dialog where the toast's "Redo" already puts it back, and redo now survives syncs.
- **"Stop waiting and mark read-only" as a merge**, with the server's Snapshot as second parent (2026-11-21, while merges ended Conflicts): one origin less, but a merge would no longer only end Conflicts. It has an origin of its own; merges went on 2026-11-22.
- **Counting only the Undo of an import not yet sent**, as the import itself isn't counted: no question for undoing an import the user just made, but undoing one already sent deletes on the server what others may have seen. Every Undo is counted.
- **Ctrl+Z taking back only the Events in Conflict at a merge with two parents** (2026-11-21, while the user ended Conflicts by a merge, which also took in the server's other changes): it needed the Events in Conflict stored on the merge or read from its parents. With a Server Event Replacement per Event, the user's restore is an Undo limited to that Event (since 2026-11-26), and Ctrl+Z passes over the Incoming Sync Snapshot as over any Snapshot FreeCal made for the server.
- **"Reverting Undo"** as the name (the critique's proposal): it told the Undo from the pointer move, which is gone; "Undo" is enough.
- **Refusing to undo a Snapshot that changes an Event with guests**: no undo writes a meeting, but in a busy work Calendar almost every change from the server touches one.
- **The current version's Unimplemented Fields winning where an Undo and a later change both changed them** (this ADR until 2026-11-22): an Undo "takes back what I did and keeps the rest", but it was a second rule beside sync's, where the server's won, and no reason for the difference was written down (point 3 of `.scratch/freecal-v1/critiques-2.md`).

## Consequences

- An Undo can leave Events out: those of which a field group it would take back has changed since, or the times against another group, and those in a Calendar marked read-only or removed. It then asks first, so Ctrl+Z can open a dialog.
- Where a later change touched other groups, an Undo combines without a word about it, so the user is told less often of a colleague's change than when every later change refused it. "Undo all over the later changes" goes further back on the Events concerned.
- Ctrl+Z never takes back someone else's change. The Calendar History can, without asking; the toast names it and offers "Redo".
- Undos and redos are Snapshots and stay in the Calendar History, which is written only by adding.
- An import or a restore can be partly in effect, after "Undo this Event" on some of its Events or "Undo the others"; the Calendar History shows the Undos beside it. A later Undo of the whole Snapshot takes back the rest.
- An Undo limited to one UID takes back that UID in every Calendar the Snapshot spans, so two unrelated Events sharing a UID in two Calendars changed by one Snapshot are taken back together.
- An undo compares the Events the Snapshot changed, where the first form moved a pointer.
- Ctrl+Z stops at a Snapshot with Events left out by a Conflict, and asks at each press until the user takes them back or the later changes go; older changes can still be undone from the Calendar History. Events left out because their Calendar is read-only are taken back by the next Ctrl+Z reaching their Snapshot after the mark goes.
- After asking, an Undo can split a move: the Event restored in its origin and still in a read-only target, one UID in two Calendars, or deleted from the target when its origin is gone.
- A removed Calendar's part of the Calendar History is gone with it (ADR 0018); an Undo can't name that Calendar, only say that it no longer exists.
- Until ticket 126, undo can move a meeting on the server; on a CalDAV server that schedules (RFC 6638), where the user organises the meeting, that can notify its attendees.
- An Event's History shows versions but offers no way to restore one.
