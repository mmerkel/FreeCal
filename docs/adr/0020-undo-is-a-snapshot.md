# Undo is a Snapshot that takes back an earlier one

With ADR 0018 this supersedes ADR 0009, and reverses its choice of undo per Event. It comes from the grilling of 2026-11-15 (see ADR 0017); the code follows with later tickets. Rewritten after the grilling of 2026-11-21 on the first point of `.scratch/freecal-v1/critiques.md`: as first written, undo moved a Calendar's User's Pointer back to the parent Snapshot (see "Considered Options"). The prototype `core/prototypes/calendar-history.PROTOTYPE.html` plays the rules below through.

Undo per Event had to work out which later changes stood in the way, undo those first, check hashes, and classify the result as benign or dangerous. Moving the User's Pointer back was one write, but it made Ctrl+Z step through syncs, so that a stray Ctrl+Z took back a colleague's change on the server, and taking back one's own change of two hours ago took back every sync since. It also made the server's changes wait while redo was possible, moved the Server's Pointer backwards, and made redo ask at forks and between Calendars. An undo that is a Snapshot of its own uses the comparison of the two sides that sync already has (ADR 0019), and both pointers only ever move forwards.

- **An Undo** is a Snapshot on the user's side whose origin names the one earlier Snapshot it takes back, written once. In each Calendar it spans, its only parent is the User's Pointer's Snapshot. Its content is the outcome of the comparison of the two sides (ADR 0019), per Occurrence: the Snapshot taken back is what both are compared with, the User's Pointer's Snapshot is one side, and the taken-back Snapshot's parent the other. It spans the Calendars that Snapshot spans and is made in one Database Transaction, then sent like any change. The Snapshot taken back is an ancestor of the User's Pointer, which the Store Check asks, and never a Calendar's first one (ADR 0018). An import or a restore doesn't create Calendars (ADR 0018), so it is taken back whole.
- **Refused whole.** If the comparison finds a Conflict in any Calendar, which is when something the Snapshot changed has changed since, nothing is written, and a toast says why, naming the later change: `Couldn't undo "Move Standup": Standup was changed on the server since`, or `… by "Resize Standup"` when the later change is the user's own. It offers "Open Standup" and "Undo both changes", which makes the Undo with the taken-back Snapshot's parent winning in every Occurrence. An Undo that would change nothing is refused too.
- **Ctrl+Z** takes back the newest of the user's own Snapshots that is in effect, across all Calendars, by when each was made. The user's own are those of an action of the user (create, edit, move, delete), an import, a Backup restore, a merge and "Stop waiting and mark read-only" (ADR 0019). A First Sync, an Incoming Sync's Snapshot and a Join are not, and Ctrl+Z passes over them. A Snapshot is in effect while no Undo in effect takes it back. Ctrl+Z also passes over Undos and over Snapshots that changed nothing on the user's side. A restart doesn't reset it.
- **At a merge**, which only ending a Conflict makes (ADR 0019), Ctrl+Z takes back what the user chose against the merge's parent on the user's side. Where the user kept their own version, the merge changed nothing on that side, and Ctrl+Z passes over it to the change before. It takes back only the Events that were in Conflict: a merge also takes in the server's changes that weren't, and Ctrl+Z doesn't take back a colleague's change. Those Events are known when the merge is taken back, stored on it or read by comparing both parents with their last common Snapshot while it is kept; ticket 134 settles which (decided 2026-11-21, to be discussed again there).
- **Redo** (Ctrl+Shift+Z, Ctrl+Y) takes back the newest Undo in effect, however it was made (Ctrl+Z, the Calendar History, "Undo both changes"), by the same rule: a Snapshot whose origin names that Undo. It is offered until the user makes a change of their own; syncs don't end it, and nothing is dropped when it ends. A redo is refused like an Undo; its toast offers "Redo over the server's change" instead of "Undo both changes". As a redo is itself an Undo, the change it brings back is in effect again, and the next Ctrl+Z takes it back once more.
- **The Calendar History** window lists the Snapshots of all Calendars together, newest first, with filters for one Calendar and for the user's own changes. Any Snapshot on the user's side can be undone from there, whole, in all Calendars it spans, an Incoming Sync's or a Join included. There is no undo for one Calendar alone and no taking a Calendar back to before a Snapshot: both would leave half a move.
- **No undo asks first** (decided 2026-11-21, here and for ADR 0019's Join): the toast after an Undo says what was undone, a change on the server too, and offers "Redo"; the toast after a redo says what was redone. The Mass-Change Guard counts every Undo at the Outgoing Sync that follows, an import's too (ADR 0019).
- **While a Calendar has a Conflict**, Undo and redo work as anywhere else and send nothing until it ends; the two sides are compared again after each, and the Conflict ends if they agree (ADR 0019).
- **Read-only Calendars** (decided 2026-11-21): Ctrl+Z and the Calendar History leave out the Snapshots of Calendars marked read-only. An Undo of a Snapshot spanning one, such as a move into it, is refused whole, saying which Calendar is read-only, without "Undo both changes". Incoming Syncs still take the server's changes in, and Unsent Changes made before the mark are still sent. A Calendar whose server refuses changes isn't read-only: undo works there and its changes wait (ADR 0019).
- **Events with guests** are undone and redone like any Event, although the user can't edit them, until the attendee features (ticket 126) decide how changes to them reach attendees (decided 2026-11-21).
- The Dangerous Undo goes, with its thresholds and its question.

## Considered Options

- **Undo per Event** (ADR 0009): an old import can be undone without touching what came after it in other Events, but it needs the hash check, the search for changes in between, the rule for undoing a Journal Transaction whole, and the Dangerous Undo.
- **Undo moving the User's Pointer back** (this ADR as first written, 2026-11-15): one write, nothing compared, and undo and redo never refused. But Ctrl+Z steps through syncs, so what it reaches depends on when the last Poll ran; taking back an older change takes back everything since, colleagues' changes included; the server's changes wait while redo is possible (Held during Undo, with its Status Mark, bar and "Continue"); the Server's Pointer moves backwards after an undo is sent; and redo has to ask at forks and between Calendars.
- **Swapping a Snapshot of the user with the sync Snapshot after it, then undoing** (noted on 2026-11-16 under "Left open" of the first form): Ctrl+Z over the user's own changes with the pointer moves kept, but a Snapshot's parents could change, which nothing else does, and a sync Snapshot would show a state the server never held. An Undo takes back a Snapshot from the middle without it.
- **Ctrl+Z over every Snapshot, syncs included**, with Undo as a Snapshot: one rule for all, but a stray Ctrl+Z after a Poll takes back a colleague's change. The Calendar History offers that, on purpose.
- **Taking back what can be taken back and leaving the rest**: an Undo is never refused, but it leaves half a move or half an import, and the toast has to say which half.
- **Stopping Ctrl+Z at a refusal versus skipping to the change before**: skipping would quietly take back an older change while the newer one stays; a refusal with "Undo both changes" leaves the choice to the user.
- **Undo for one Calendar, and taking a Calendar back to before a Snapshot** (the first form): useful after a mistake in one Calendar, but it leaves one UID in two Calendars after a move; the combined Calendar History undoes any one Snapshot instead.
- **Asking before undoing a change from a server**: a guard for the Calendar History's undo of a sync, but a dialog where the toast's "Redo" already puts it back, and redo now survives syncs.
- **"Stop waiting and mark read-only" as a merge**, with the server's Snapshot as second parent, as it ends a Conflict too: one origin less, but a merge would no longer only end Conflicts, and Ctrl+Z's rule for merges would need a case for it. It has an origin of its own.
- **Counting only the Undo of an import not yet sent**, as the import itself isn't counted: no question for undoing an import the user just made, but undoing one already sent deletes on the server what others may have seen. Every Undo is counted.
- **Ctrl+Z passing over merges**, only the Calendar History taking them back: nothing to know about the merge beyond its parents, but Ctrl+Z can't take back a wrong choice in a Conflict.
- **Taking a merge back whole against its parent on the user's side**: simplest, but Ctrl+Z would take back the server's changes that weren't in Conflict, a colleague's among them.
- **"Reverting Undo"** as the name (the critique's proposal): it told the Undo from the pointer move, which is gone; "Undo" is enough.
- **Refusing to undo a Snapshot that changes an Event with guests**: no undo writes a meeting, but in a busy work Calendar almost every change from the server touches one.

## Consequences

- An undo can be refused: whenever something it would take back has changed since, in any Calendar it spans. "Undo both changes" goes further back on the Events concerned; a refused redo stays refused until the user chooses "Redo over the server's change".
- Ctrl+Z never takes back someone else's change. The Calendar History can, without asking; the toast names it and offers "Redo".
- Undos and redos are Snapshots and stay in the Calendar History, which is written only by adding.
- An undo compares the Events the Snapshot changed, where the first form moved a pointer.
- Ctrl+Z stops at a Snapshot spanning a Calendar marked read-only until the mark goes; older changes can still be undone from the Calendar History.
- Until ticket 126, undo can move a meeting on the server; on a CalDAV server that schedules (RFC 6638), where the user organises the meeting, that can notify its attendees.
- An Event's History shows versions but offers no way to restore one.
