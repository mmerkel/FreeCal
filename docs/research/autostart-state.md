# Start at login: store the choice, or check the autostart entry?

Researched 2026-11-10 for ticket 13: should FreeCal keep the user's "start at login" choice in its own settings (`Settings::start_at_login`), or look at the autostart entry each time the Settings dialog shows the switch? FreeCal must run unchanged as a Flatpak at 1.0. Source links point at the commit cloned that day. "Unknown" means no primary source was found.

## Summary

- The Background portal has two methods, `RequestBackground` and `SetStatus`, and one property, `version`. **Nothing reports whether autostart is on** ([Background.xml#L18-L93](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/data/org.freedesktop.portal.Background.xml#L18-L93)).
- The `autostart` result says what *this request* did. When the user has refused background running, the portal returns `autostart` false **without touching an existing file** ([background.c#L907-L971](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/background.c#L907-L971)).
- The portal writes `$XDG_CONFIG_HOME/autostart/<app-id>.desktop` on the host. With `autostart` false it deletes that file. With `autostart` true it rewrites the whole file from scratch ([background.c#L802-L866](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/background.c#L802-L866)).
- A Flatpak app can't see that file unless it holds a static filesystem permission. Flathub's rules say a portal must be used instead of static permissions where one covers the use case ([requirements.md#L473-L485](https://github.com/flathub-infra/documentation/blob/105b2703dcdde88360cfa65018276aae13ae8a36/docs/02-for-app-authors/02-requirements.md#L473-L485)).

What apps do:

|---|---|---|---|
| Nextcloud desktop | Writes `~/.config/autostart/<name>.desktop` itself | Same code; no portal | **Checks the file** ([utility_unix.cpp#L73-L77](https://github.com/nextcloud/desktop/blob/8f30467ea0f9703389bc884397bbfbf4bca5c318/src/common/utility_unix.cpp#L73-L77)) |
| KeePassXC | Writes the file itself | Background portal | Outside: **checks the file**. In Flatpak: **stores the portal's answer** in its config ([NixUtils.cpp#L140-L146](https://github.com/keepassxreboot/keepassxc/blob/6bcb901aefdd6c7a525466d7dfe099c5ebc13c0e/src/gui/osutils/nixutils/NixUtils.cpp#L140-L146)) |
| Telegram Desktop | Writes the file itself | Background portal | **Stores** `cAutoStart` ([settings_advanced.cpp#L681-L705](https://github.com/telegramdesktop/tdesktop/blob/c4bd064bcc84a359179e191fa6dfd216acda504f/Telegram/SourceFiles/settings/sections/settings_advanced.cpp#L681-L705)) |
| Geary | Copies an installed autostart file | Background portal | **Stores** a GSettings key, `run-in-background` ([gschema.xml#L76-L80](https://gitlab.gnome.org/GNOME/geary/-/blob/86732800d5c09acc1cedcb3e4a876290201b5056/desktop/org.gnome.Geary.gschema.xml#L76-L80)) |

So every app that uses the portal inside Flatpak stores the choice (or derives it). The apps that check the file write the file themselves and don't use the portal.

## 1. The Background portal

### Interface

[org.freedesktop.portal.Background.xml](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/data/org.freedesktop.portal.Background.xml) describes version 2 ([#L16](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/data/org.freedesktop.portal.Background.xml#L16)). Rendered: [Background docs](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Background.html).

- `RequestBackground(s parent_window, a{sv} options) -> o handle` ([#L63-L68](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/data/org.freedesktop.portal.Background.xml#L63-L68)). Options: `handle_token`, `reason`, `autostart` ("true if the app also wants to be started automatically at login"), `commandline` ("If this is not specified, the `Exec` key from the desktop file will be used") and `dbus-activatable` ([#L27-L51](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/data/org.freedesktop.portal.Background.xml#L27-L51)). The Response carries `background` ("true if the application is allowed to run in the background") and `autostart` ("true if the application will be autostarted") ([#L53-L61](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/data/org.freedesktop.portal.Background.xml#L53-L61)).
- `SetStatus(a{sv} options)`, added in version 2, only sets a status `message` ([#L70-L90](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/data/org.freedesktop.portal.Background.xml#L70-L90)).
- Property `version` ([#L92](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/data/org.freedesktop.portal.Background.xml#L92)).

No method or property reports the autostart state. The portal's permission store keeps only yes/no/ask for *running in the background* per app, not autostart ([background.c#L26-L51](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/background.c#L26-L51), [#L104-L177](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/background.c#L104-L177)).

### What RequestBackground does (xdg-desktop-portal 1.22.x, main at faab6c7)

From `handle_request_background_in_thread_func` ([background.c#L871-L1012](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/background.c#L871-L1012)):

- A missing `autostart` option counts as false: `autostart_requested` starts as FALSE and `g_variant_lookup` leaves it alone ([#L894](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/background.c#L894)). Every *allowed* request then calls `enable_autostart_sync` with that value ([#L973-L997](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/background.c#L973-L997)). So a request for background permission alone **deletes** an existing autostart entry. teams-for-linux hit this and now always sends `autostart` ([issue #2936](https://github.com/IsmaelMartinez/teams-for-linux/issues/2936), [index.js#L124-L133](https://github.com/IsmaelMartinez/teams-for-linux/blob/40bc953f09ea032d5f7268381336eef36f4faf5c/app/backgroundPortal/index.js#L124-L133)).
- Host (unsandboxed) apps always count as allowed. Sandboxed apps are looked up in the permission store; "unset" becomes "yes" without a dialog, and "ask" shows a dialog ([#L900-L971](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/background.c#L900-L971)).
- If the user refuses (the stored permission is "no", or the dialog is refused), `enable_autostart_sync` is **not called**. The response says `autostart` false, but an autostart file already on disk stays ([#L907-L971](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/background.c#L907-L971)).
- **Meaning of the `autostart` result**: true means the file was just written. False means one of three things: it was just deleted, it was never touched because background running is refused, or writing failed ([#L973-L1010](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/background.c#L973-L1010)). In the last case the response code is "other" (2).
- libportal's `xdp_portal_request_background_finish` returns the `autostart` result when autostart was requested, otherwise the `background` result ([libportal background.c#L188-L196](https://github.com/flatpak/libportal/blob/cc398d79eb6718f2f27ae92a73d32ece9e5dcadb/libportal/background.c#L188-L196)).

### The file it writes

`enable_autostart_sync` ([background.c#L778-L867](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/background.c#L778-L867)):

- **Path**: `g_get_user_config_dir()/autostart/<app-id>.desktop`, computed in the portal process on the host. That is the host's `$XDG_CONFIG_HOME` (normally `~/.config/autostart/`), the same for Flatpak and host apps ([#L802-L804](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/background.c#L802-L804)).
- **No app ID**: an empty app ID fails with "Autostart not supported (no AppId detected)" ([#L795-L800](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/background.c#L795-L800)). The caller then gets response code 2 with `background` false and `autostart` false ([#L978-L1007](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/background.c#L978-L1007)). NEWS for 1.21.0: "Require a valid AppID from apps in `RequestBackground` to enable autostart (#1793)" ([NEWS.md#L133-L134](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/NEWS.md#L133-L134)).
- **autostart=false**: `unlink(path)`; a missing file is fine ([#L806-L816](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/background.c#L806-L816)).
- **autostart=true**: a new key file with `Type=Application`, `Name=` (from the app's desktop file, or else the app ID) and `X-XDP-Autostart=<app-id>`. It gets `Exec=` from `commandline` joined with spaces, and `DBusActivatable=true` when `dbus-activatable` is set ([#L825-L857](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/background.c#L825-L857)). The file is saved over any existing one ([#L863](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/background.c#L863)). So a `Hidden=true` the user set in their desktop's autostart settings is dropped when the app requests autostart again.
- **Flatpak apps**: `validate_autostart` replaces `Exec` with `flatpak run <app-id>`, or `flatpak run --command=<commandline[0]> <app-id> <rest>` when a commandline was given, and adds `X-Flatpak=<app-id>` ([xdp-app-info-flatpak.c#L230-L273](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/shared/xdp-app-info-flatpak.c#L230-L273), [#L324-L353](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/shared/xdp-app-info-flatpak.c#L324-L353)). So `commandline` must be the command *inside* the sandbox (e.g. `["freecal", "--hidden"]`), never `flatpak run …`.
- **Host apps**: `validate_autostart` does nothing ([xdp-app-info-host.c#L39-L46](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/shared/xdp-app-info-host.c#L39-L46)). Without `commandline` (and without `dbus-activatable`) the file gets **no `Exec` line at all**. I found no code that fills in the `Exec` from the app's desktop file, as the interface doc promises. Read from the code; not tested.
- **Older portals**: in 1.18.x the frontend didn't write the file. It called the desktop backend's `org.freedesktop.impl.portal.Background.EnableAutostart(app_id, enable, commandline, flags)` with `allowed && autostart_requested` ([1.18.4 background.c#L790-L808](https://github.com/flatpak/xdg-desktop-portal/blob/11c8a96b147aeae70e3f770313f93b367d53fedd/src/background.c#L790-L808), [impl XML#L83-L103](https://github.com/flatpak/xdg-desktop-portal/blob/11c8a96b147aeae70e3f770313f93b367d53fedd/data/org.freedesktop.impl.portal.Background.xml#L83-L103)). The frontend's own `enable_autostart_sync` is there from 1.19.0 on ([1.19.0 background.c#L691](https://github.com/flatpak/xdg-desktop-portal/blob/ab3ff7eb2a67a1638c509d9f1b63e641c250a04b/src/background.c#L691)). What each 1.18 backend (gnome, gtk, kde) wrote was not checked.

### App ID of host apps

- **Automatic**: `get_app_from_pid` reads the caller's systemd user unit. It parses `app[-<launcher>]-<AppID>-<RANDOM>.scope|.slice` or `app[-<launcher>]-<AppID>[@<RANDOM>].service` (the [systemd desktop-environment convention](https://systemd.io/DESKTOP_ENVIRONMENTS/)). It accepts the ID only if `<AppID>.desktop` is an installed desktop file ([xdp-app-info-host.c#L100-L187](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/shared/xdp-app-info-host.c#L100-L187)). Otherwise the app ID is `""` ([#L242-L281](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/shared/xdp-app-info-host.c#L242-L281)). This needs a build with libsystemd; without it there is always no ID ([#L184-L187](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/shared/xdp-app-info-host.c#L184-L187)). An app started from a terminal or a script gets no app ID, so autostart fails for it.
- **org.freedesktop.host.portal.Registry** (new in 1.19.4, released 2025-02-15; [NEWS.md#L199-L209](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/NEWS.md#L199-L209)) has `Register(s app_id, a{sv} options)`. Its documented rules: the ID must match the basename of a .desktop file; register at most once; register before any other portal call; re-register when the portal restarts ([Registry.xml#L8-L48](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/data/org.freedesktop.host.portal.Registry.xml#L8-L48)). The code refuses sandboxed callers ("Can't manually register a %s application"). It builds the app info with `REQUIRE_GAPPINFO`, so an ID with no installed desktop file is refused ([registry.c#L64-L140](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/desktop-portal/registry.c#L64-L140), [xdp-app-info-host.c#L210-L234](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/shared/xdp-app-info-host.c#L210-L234), [xdp-app-info.c#L92-L97](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/shared/xdp-app-info.c#L92-L97)). The API reference warns that the registry "is expected to eventually be deprecated and may be removed"; launchers should use the cgroup naming instead ([api-reference.rst#L14-L30](https://github.com/flatpak/xdg-desktop-portal/blob/faab6c7fd2c0f40183e542ba52454bc35a4e9a25/doc/api-reference.rst#L14-L30)).
- Rust: ashpd has `register_host_app` ([registry.rs#L44-L48](https://github.com/bilelmoussaoui/ashpd/blob/ce5c18a27def524cc0ccb8134e1f277c667c01e1/client/src/registry.rs#L44-L48)). Its Background module still says "This portal only works for sandboxed applications" ([background.rs#L4](https://github.com/bilelmoussaoui/ashpd/blob/ce5c18a27def524cc0ccb8134e1f277c667c01e1/client/src/desktop/background.rs#L4)). The portal code above contradicts this for host apps with an app ID.

### Who else edits the file

- The [XDG Autostart spec](https://specifications.freedesktop.org/autostart/latest/) (0.5): a file with `Hidden=true` "MUST be ignored".
- KDE Plasma's Autostart settings toggle an entry by writing or removing `Hidden=true`, and can delete the file ([autostartmodel.cpp#L494-L528](https://invent.kde.org/plasma/plasma-workspace/-/blob/2ff46cec0682729ed8285a2934e58bb608ceedf7/kcms/autostart/autostartmodel.cpp#L494-L528)).
- GNOME Settings' Apps panel (main, 2026-11-10) shows only the portal's "background" permission, not autostart ([cc-applications-panel.c#L461-L485](https://gitlab.gnome.org/GNOME/gnome-control-center/-/blob/599e508302753720c9a0a8d04bb83764170a2474/panels/applications/cc-applications-panel.c#L461-L485)). Merge request [!3221](https://gitlab.gnome.org/GNOME/gnome-control-center/-/merge_requests/3221) ("Support controlling the autostart flag on applications", built on `X-XDP-Autostart`) exists; its state is unknown because the page didn't load.

So the user can change the entry outside FreeCal (Plasma, or by deleting the file). Revoking background permission in GNOME Settings doesn't delete the file.

## 2. Apps

- **Nextcloud desktop**: on Linux, `hasLaunchOnStartup` is `QFile::exists(<ConfigLocation>/autostart/<appName>.desktop)`, and `setLaunchOnStartup` writes or removes the file ([utility_unix.cpp#L58-L134](https://github.com/nextcloud/desktop/blob/8f30467ea0f9703389bc884397bbfbf4bca5c318/src/common/utility_unix.cpp#L58-L134)). The checkbox is initialised from the file ([generalsettings.cpp#L55-L63](https://github.com/nextcloud/desktop/blob/8f30467ea0f9703389bc884397bbfbf4bca5c318/src/gui/generalsettings.cpp#L55-L63)). After a toggle it reads the file again and *also* stores the result as `launchOnSystemStartup` ([#L160-L175](https://github.com/nextcloud/desktop/blob/8f30467ea0f9703389bc884397bbfbf4bca5c318/src/gui/generalsettings.cpp#L160-L175)). That stored value is only used to re-apply the setting after a migration ([configfile.cpp#L1588-L1593](https://github.com/nextcloud/desktop/blob/8f30467ea0f9703389bc884397bbfbf4bca5c318/src/libsync/configfile.cpp#L1588-L1593)). There is no portal code. The Flathub build has `--filesystem=host:rw` and patches only the D-Bus service path ([manifest](https://github.com/flathub/com.nextcloud.desktopclient.nextcloud/blob/f267084b348d063429c6783a62986c8ef097d69c/com.nextcloud.desktopclient.nextcloud.yml)). Inside Flatpak, `XDG_CONFIG_HOME` is `~/.var/app/<id>/config` ([flatpak-docs conventions.rst#L374-L390](https://github.com/flatpak/flatpak-docs/blob/1017976c15fe847c48603de9301d873aeb77b197/docs/conventions.rst#L374-L390)). So the Flatpak build presumably writes and checks an autostart file that the session never reads. That is an inference; not tested.
- **Telegram Desktop**: in Flatpak (`KSandbox::isFlatpak()`), `AutostartToggle` calls the Background portal with `autostart`, `commandline = [<exe>, -autostart]` and `dbus-activatable` false. Outside Flatpak it writes or removes `<GenericConfigLocation>/autostart/<desktopFileName>.desktop` itself ([specific_linux.cpp#L57-L215](https://github.com/telegramdesktop/tdesktop/blob/c4bd064bcc84a359179e191fa6dfd216acda504f/Telegram/SourceFiles/platform/linux/specific_linux.cpp#L57-L215), [#L646-L678](https://github.com/telegramdesktop/tdesktop/blob/c4bd064bcc84a359179e191fa6dfd216acda504f/Telegram/SourceFiles/platform/linux/specific_linux.cpp#L646-L678)). The checkbox shows the stored setting `cAutoStart()`. On toggle it stores the new value, calls the platform, sets the checkbox to the outcome and writes settings ([settings_advanced.cpp#L681-L720](https://github.com/telegramdesktop/tdesktop/blob/c4bd064bcc84a359179e191fa6dfd216acda504f/Telegram/SourceFiles/settings/sections/settings_advanced.cpp#L681-L720)). After an update from ≤ 5.14.3 it re-applies the stored setting ([specific_linux.cpp#L859-L861](https://github.com/telegramdesktop/tdesktop/blob/c4bd064bcc84a359179e191fa6dfd216acda504f/Telegram/SourceFiles/platform/linux/specific_linux.cpp#L859-L861)). It never reads the file.
- **Geary** (direct D-Bus, not libportal): one GSettings key, `run-in-background`, means "run in background on logon and when closed" ([gschema.xml#L76-L80](https://gitlab.gnome.org/GNOME/geary/-/blob/86732800d5c09acc1cedcb3e4a876290201b5056/desktop/org.gnome.Geary.gschema.xml#L76-L80)). When the key changes, a Flatpak build calls `RequestBackground` with `autostart` and `commandline = ["geary", "--gapplication-service"]`; a host build copies or deletes `geary-autostart.desktop` ([application-startup-manager.vala#L66-L143](https://gitlab.gnome.org/GNOME/geary/-/blob/86732800d5c09acc1cedcb3e4a876290201b5056/src/client/application/application-startup-manager.vala#L66-L143)). It ignores the portal's result.
- **libportal callers**: GNOME Boxes calls `request_background` with `NONE` flags, i.e. without autostart ([resources-page.vala#L156](https://gitlab.gnome.org/GNOME/gnome-boxes/-/blob/78cd19e85b70e796aa17ca26fde611e9bd31608a/src/preferences/resources-page.vala#L156)). On current portals that removes any autostart entry, as described above. I found no GNOME/GTK app that calls `xdp_portal_request_background` with `XDP_BACKGROUND_FLAG_AUTOSTART`. Polari, Fractal, Dialect, Tuba, Mousai, Extension Manager and GNOME Calendar have no autostart portal call.
- **KeePassXC** (Qt): outside Flatpak, `isLaunchAtStartupEnabled` is "the file exists". In a Flatpak build (`KEEPASSXC_DIST_FLATPAK`) it is the stored `GUI_LaunchAtStartup`, which is set from the portal response's `autostart` ([NixUtils.cpp#L140-L225](https://github.com/keepassxreboot/keepassxc/blob/6bcb901aefdd6c7a525466d7dfe099c5ebc13c0e/src/gui/osutils/nixutils/NixUtils.cpp#L140-L225)). This is the clearest case of an app switching approach by packaging.
- **KDE**: KClock's daemon has no switch. In Flatpak it requests autostart (`dbus-activatable`, `commandline = ["kclockd"]`) whenever alarms or timers are active, and turns it off otherwise. It does this at every daemon start and on every change ([xdgportal.cpp#L23-L66](https://invent.kde.org/utilities/kclock/-/blob/4e87b9ae6b983b2a4b189fc0199b632885fd9d4b/src/kclockd/xdgportal.cpp#L23-L66), [main.cpp#L85-L96](https://invent.kde.org/utilities/kclock/-/blob/4e87b9ae6b983b2a4b189fc0199b632885fd9d4b/src/kclockd/main.cpp#L85-L96)). KDE Connect installs a system-wide autostart file ([daemon/CMakeLists.txt#L30](https://invent.kde.org/network/kdeconnect-kde/-/blob/7e0f7cecf00190309316ca69d5b9a6c75b147ed2/daemon/CMakeLists.txt#L30)). NeoChat, Tokodon, Kasts and Merkuro have no autostart code.
- **Electron**: `getLoginItemSettings`/`setLoginItemSettings` are documented `_macOS_ _Windows_` ([app.md#L1680](https://github.com/electron/electron/blob/0a31c405cb33b8bd5af7bd16d2ea79242a16d9a9/docs/api/app.md#L1680), [#L1712](https://github.com/electron/electron/blob/0a31c405cb33b8bd5af7bd16d2ea79242a16d9a9/docs/api/app.md#L1712)). On Linux, `SetLoginItemSettings` is empty and `GetLoginItemSettings` returns defaults ([browser_linux.cc#L265-L271](https://github.com/electron/electron/blob/0a31c405cb33b8bd5af7bd16d2ea79242a16d9a9/shell/browser/browser_linux.cc#L265-L271)). Portal support is an open feature request ([electron#32388](https://github.com/electron/electron/issues/32388)). Electron apps use the `auto-launch` npm package instead, whose Linux `isEnabled` is "`~/.config/autostart/<name>.desktop` exists" ([autoLaunchAPILinux.js#L59-L73](https://github.com/Teamwork/node-auto-launch/blob/c332f546f5594262adcb17f909030c21890ee80d/src/library/autoLaunchAPI/autoLaunchAPILinux.js#L59-L73)), or talk to the portal over D-Bus directly. teams-for-linux does the latter in Flatpak only ([index.js#L1-L24](https://github.com/IsmaelMartinez/teams-for-linux/blob/40bc953f09ea032d5f7268381336eef36f4faf5c/app/backgroundPortal/index.js#L1-L24)). To avoid the deletion bug it reads `~/.config/autostart/<FLATPAK_ID>.desktop`, counting `Hidden=true` or `X-GNOME-Autostart-enabled=false` as off, and passes that state back ([#L39-L44](https://github.com/IsmaelMartinez/teams-for-linux/blob/40bc953f09ea032d5f7268381336eef36f4faf5c/app/backgroundPortal/index.js#L39-L44), [#L144-L184](https://github.com/IsmaelMartinez/teams-for-linux/blob/40bc953f09ea032d5f7268381336eef36f4faf5c/app/backgroundPortal/index.js#L144-L184)). That read only works because its Flathub manifest has `--filesystem=home` ([manifest#L16](https://github.com/flathub/com.github.IsmaelMartinez.teams_for_linux/blob/677e78aa52a9ed77da932a9c2c4637e0f71bec5f/com.github.IsmaelMartinez.teams_for_linux.yml#L16)).
- **Tauri** (relevant to FreeCal's stack): `tauri-plugin-autostart` uses `auto-launch` 0.6 ([Cargo.toml#L34](https://github.com/tauri-apps/plugins-workspace/blob/9aa4f717152cdeceed4bada9c849ad68a9dc402c/plugins/autostart/Cargo.toml#L34)). That crate hard-codes `$HOME/.config/autostart` (ignoring `XDG_CONFIG_HOME`) and has `is_enabled` = "the file exists" ([linux.rs#L185-L190](https://github.com/zzzgydi/auto-launch/blob/e2feaffbdb6d8992bf1ddc8d5ec99e915ebbe1ed/src/linux.rs#L185-L190), [#L289-L294](https://github.com/zzzgydi/auto-launch/blob/e2feaffbdb6d8992bf1ddc8d5ec99e915ebbe1ed/src/linux.rs#L289-L294)). There is no portal path. What it does inside a Flatpak without filesystem permission was not tested.

## 3. Flathub

- **Requirements**: "Static permissions must be kept to an absolute minimum. Applications should rely on XDG Portals". "When a suitable XDG portal exists, is supported across the ecosystem, and covers the application's use case … using the portal becomes mandatory instead of static permissions." Exceptions are case by case ([requirements.md#L473-L485](https://github.com/flathub-infra/documentation/blob/105b2703dcdde88360cfa65018276aae13ae8a36/docs/02-for-app-authors/02-requirements.md#L473-L485)). The docs never name autostart or the Background portal.
- **Linter**: has no autostart-specific check. It errors on the whole of `xdg-config` (`finish-args-arbitrary-xdg-config-*-access`) and on the whole of `~/.config` (`finish-args-full-home-config-access`), but not on a subdirectory such as `xdg-config/autostart` or `home/.config/autostart` ([finish_args.py#L16-L22](https://github.com/flathub-infra/flatpak-builder-lint/blob/d7d3f5714d11ce8c5dbde70465331b166d7c5c67/flatpak_builder_lint/checks/finish_args.py#L16-L22), [#L152-L163](https://github.com/flathub-infra/flatpak-builder-lint/blob/d7d3f5714d11ce8c5dbde70465331b166d7c5c67/flatpak_builder_lint/checks/finish_args.py#L152-L163), [#L195-L203](https://github.com/flathub-infra/flatpak-builder-lint/blob/d7d3f5714d11ce8c5dbde70465331b166d7c5c67/flatpak_builder_lint/checks/finish_args.py#L195-L203); [linter.md#L847-L852](https://github.com/flathub-infra/documentation/blob/105b2703dcdde88360cfa65018276aae13ae8a36/docs/02-for-app-authors/12-linter.md#L847-L852), [#L969-L981](https://github.com/flathub-infra/documentation/blob/105b2703dcdde88360cfa65018276aae13ae8a36/docs/02-for-app-authors/12-linter.md#L969-L981)). So `--filesystem=xdg-config/autostart:ro` passes the linter. It would still be a static permission that human review can refuse under the rule above. No Flathub statement forbids or allows it specifically.
- **How it would map**: `xdg-config/<path>` bind-mounts the host path into the sandbox's `$XDG_CONFIG_HOME/<path>` ([sandbox-permissions.rst#L192](https://github.com/flatpak/flatpak-docs/blob/1017976c15fe847c48603de9301d873aeb77b197/docs/sandbox-permissions.rst#L192), [#L583-L590](https://github.com/flatpak/flatpak-docs/blob/1017976c15fe847c48603de9301d873aeb77b197/docs/sandbox-permissions.rst#L583-L590)).

## What this means for FreeCal

- **Check the entry**: the portal can't answer the question, so in Flatpak "check" means reading the host's `~/.config/autostart/<app-id>.desktop`. That needs `--filesystem=xdg-config/autostart:ro`, a static permission that only exists to work around the portal. It passes the linter, but it goes against Flathub's "portal is mandatory" rule, and so against US-116 ("works without loss of function" through portals). It would also have to read `Hidden=true` (Plasma) and `X-GNOME-Autostart-enabled=false` as off, as teams-for-linux does. Strongest pro: the switch never lies when the user disables or deletes the entry outside FreeCal. Strongest con: it needs a permission FreeCal can't count on in the Flatpak, so there would be two code paths, which is what KeePassXC ended up with.
- **Store the choice** (what ticket 13 already does with `Settings::start_at_login`): one rule for host and Flatpak. It matches Telegram, Geary, KeePassXC-in-Flatpak and KClock, i.e. every portal user found. Strongest con, as the ticket says: the switch can show on after the user removed or hid the entry outside FreeCal. A related con: re-asserting `autostart=true` at FreeCal's start would silently undo a Plasma "disable", because the portal rewrites the file without `Hidden`.
- **Portal pitfalls that apply whichever way is chosen**:
  - Every `RequestBackground` call must send `autostart` explicitly, set to the stored choice. Leaving it out deletes the entry.
  - Treat the response's `autostart` false as "not on now", not as "no file exists". When background permission is refused, an old file stays.
  - `commandline` is the command inside the sandbox; the portal adds `flatpak run`.
  - Unsandboxed, the portal works only if it can find FreeCal's app ID. The launcher must start FreeCal in an `app-<id>-….scope` with an installed `<id>.desktop`, or FreeCal calls `Registry.Register` (portal ≥ 1.19.4, possibly removed later). Otherwise it fails with "no AppId detected". So the planned XDG-file fallback is needed for a host build started from a terminal, and for portals < 1.19 (where host-app autostart went through each desktop backend, not checked here).
- **Recommendation**: store the choice, and only call the portal when the user flips the switch, never at start-up. Then FreeCal never overwrites an outside change, and the stored value is "what the user last asked FreeCal for". Strongest con: an outside change shows only as a stale switch until the user flips it twice.
