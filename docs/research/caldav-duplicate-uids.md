## 1. What the RFCs say

[RFC 4791 §4.1](https://www.rfc-editor.org/rfc/rfc4791#section-4.1):

> The UID property value of the calendar components contained in a calendar object resource MUST be unique in the scope of the calendar collection in which they are stored.
>
> Calendar components in a calendar collection that have different UID property values MUST be stored in separate calendar object resources.
>
> Calendar components with the same UID property value, in a given calendar collection, MUST be contained in the same calendar object resource. This ensures that all components in a recurrence "set" are contained in the same calendar object resource. It is possible for a calendar object resource to just contain components that represent "overridden" instances (ones that modify the behavior of a regular instance, and thus include a RECURRENCE-ID property) without also including the "master" recurring component (the one that defines the recurrence "set" and does not contain any RECURRENCE-ID property).

[RFC 4791 §5.3.2.1](https://www.rfc-editor.org/rfc/rfc4791#section-5.3.2.1), a precondition for PUT, COPY and MOVE:

> (CALDAV:no-uid-conflict): The resource submitted in the PUT request, or targeted by a COPY or MOVE request, MUST NOT specify an iCalendar UID property value already in use in the targeted calendar collection or overwrite an existing calendar object resource with one that has a different UID property value. Servers SHOULD report the URL of the resource that is already making use of the same UID property value in the DAV:href element;

So the RFC requires Exceptions to sit in the same resource as their Recurring Event. A resource may hold only Exceptions, but there can't be a second one for that UID.

[RFC 6638 §3.2.4.1](https://www.rfc-editor.org/rfc/rfc6638#section-3.2.4.1) (CALDAV:unique-scheduling-object-resource) extends this optionally to the owner's other calendars:

> Servers MAY reject requests to create a scheduling object resource with an iCalendar "UID" property value already in use by another scheduling object resource owned by the same user in other calendar collections.

[RFC 6638 §4.1](https://www.rfc-editor.org/rfc/rfc6638#section-4.1): for an incoming iTIP message the server "first tries to locate a corresponding scheduling object resource belonging to the 'Attendee'. If no matching scheduling object resource exists, the server treats the scheduling message as a new message; otherwise, it is treated as an update." An invitation to one Occurrence is therefore merged into the existing resource, not stored next to it. SabreDAV does this: it looks the UID up in the home and runs the iTIP broker on the existing object ([Schedule/Plugin.php#L477-L488](https://github.com/sabre-io/dav/blob/be1d58d6bce7ca33313b02909f9088c93c35db02/lib/CalDAV/Schedule/Plugin.php#L477-L488)). §3.2.2.3 likewise talks of an Attendee who "adds an overridden component" to the existing resource.

[RFC 5545 §3.8.4.4](https://www.rfc-editor.org/rfc/rfc5545#section-3.8.4.4): RECURRENCE-ID "is used in conjunction with the "UID" and "SEQUENCE" properties to identify a specific instance of a recurring" component. RFC 5545 itself says nothing about resources.

## 2. Servers in detail

- **SabreDAV core**: `createCalendarObject` inserts without looking at the UID ([PDO.php#L528-L571](https://github.com/sabre-io/dav/blob/be1d58d6bce7ca33313b02909f9088c93c35db02/lib/CalDAV/Backend/PDO.php#L528-L571)). The only unique index is (calendarid, uri) ([pgsql.calendars.sql#L18-L19](https://github.com/sabre-io/dav/blob/be1d58d6bce7ca33313b02909f9088c93c35db02/examples/sql/pgsql.calendars.sql#L18-L19)). Several UIDs in one resource are refused by sabre/vobject's CalDAV profile: "A calendar object on a CalDAV server may only have components with the same UID." ([VCalendar.php#L481](https://github.com/sabre-io/vobject/blob/5e2f338811916c03927398bb24e527989de63194/lib/Component/VCalendar.php#L481), called from [Plugin.php#L824-L831](https://github.com/sabre-io/dav/blob/be1d58d6bce7ca33313b02909f9088c93c35db02/lib/CalDAV/Plugin.php#L824-L831)). **Baïkal** uses this backend unchanged ([Server.php#L147](https://github.com/sabre-io/Baikal/blob/0b46a92cf7fdf5943542421d440791a4ebaac86c/Core/Frameworks/Baikal/Core/Server.php#L147)), so a Baïkal collection can hold one UID twice.
- **Nextcloud**: `createCalendarObject` throws `UidConflict` with the existing href ([#L1557-L1562](https://github.com/nextcloud/server/blob/cb2a66ea4ec7a10b74fc2a02e606824c7282743f/apps/dav/lib/CalDAV/CalDavBackend.php#L1557-L1562)), and so does a move ([#L1720-L1723](https://github.com/nextcloud/server/blob/cb2a66ea4ec7a10b74fc2a02e606824c7282743f/apps/dav/lib/CalDAV/CalDavBackend.php#L1720-L1723)). `updateCalendarObject` doesn't check ([#L1631-L1650](https://github.com/nextcloud/server/blob/cb2a66ea4ec7a10b74fc2a02e606824c7282743f/apps/dav/lib/CalDAV/CalDavBackend.php#L1631-L1650)), and neither does SabreDAV. ## 3. Exceptions as separate resources; duplicates in the wild

- No server was found that stores an Exception as a resource separate from its Recurring Event in one collection. Every enforcing server above refuses the second resource outright, so it can't do so. SabreDAV and the RFC 6638 servers merge an iTIP message for one Occurrence into the existing resource (§1). DavMail rebuilds Exchange's modified Occurrences into the master's VCALENDAR ([EwsExchangeSession.java#L2415-L2420](https://github.com/mguessan/davmail/blob/8ae78a405bd3374e4b2a37a0e2754c55e8cbc601/src/java/davmail/exchange/ews/EwsExchangeSession.java#L2415-L2420)).
- **Google**: the REST API's per-instance events don't show up as separate CalDAV resources in any primary source found. Unknown, and worth a live test before relying on it.
- **Resources holding only Exceptions** are legal (RFC 4791 §4.1). DAVx5 handles them: its main VEVENT is nullable ([CalendarUidSplitter.kt#L40-L43](https://github.com/bitfireAT/synctools/blob/cb4f75fd5d71c1960c9a59e1b873aea5433bcbeb/lib/src/main/kotlin/at/bitfire/synctools/icalendar/CalendarUidSplitter.kt#L40-L43)). One typically appears when someone is invited to a single Occurrence.
- **Duplicates seen in the wild**:
  - DAViCal 1.1.5 with CalDavZAP 0.13.1, where "duplicating" an event left two resources with the same UID ([davclients list, 2017](https://lists.inf-it.com/hyperkitty/list/davclients@lists.inf-it.com/message/RX4WESQBC7PLDJM2VCSRT3RQS5NBNFG2), a mailing-list report and the only evidence for it). This is a different case from the 2014 multi-UID one in ADR 0013.
  - Exchange through DavMail (above).
  - Nextcloud's error reports ([#12754](https://github.com/nextcloud/server/issues/12754)) show clients trying to create duplicates, e.g. after imports or birthday-calendar sync, and being refused.
  - The existence of vdirsyncer's `repair` command and Radicale's storage verification suggests both projects meet duplicates. That is an inference.

## 4. Clients

- **DAVx5**: each resource becomes one Android event keyed by its file name (`syncId = fileName`), so two hrefs with one UID give two events. A resource whose components hold not exactly one UID is skipped with "Received iCalendar with not exactly one UID; ignoring" ([CalendarSyncManager.kt#L152-L179](https://github.com/bitfireAT/davx5-ose/blob/e002a1e34b5fa718b3555ec5c6997d2aa4ecc97c/core/src/main/kotlin/at/bitfire/davdroid/sync/CalendarSyncManager.kt#L152-L179)). Within one resource, components with the same UID and RECURRENCE-ID are reduced to the one with the highest SEQUENCE ([CalendarUidSplitter.kt#L29-L65](https://github.com/bitfireAT/synctools/blob/cb4f75fd5d71c1960c9a59e1b873aea5433bcbeb/lib/src/main/kotlin/at/bitfire/synctools/icalendar/CalendarUidSplitter.kt#L29-L65)).
- **Thunderbird**: uses only `items[0]` of a resource ("with CalDAV there really should only be one item here", [#l965-l976](https://hg.mozilla.org/comm-central/file/7ea06a52233e9964dedcc840087855089cbc2c98/calendar/providers/caldav/CalDavCalendar.sys.mjs#l965)). The item cache is keyed by `item.id` (the UID). A second href with that UID turns into a MODIFY of the same item, and its `locationPath` replaces the first href's ([#l1001-l1022](https://hg.mozilla.org/comm-central/file/7ea06a52233e9964dedcc840087855089cbc2c98/calendar/providers/caldav/CalDavCalendar.sys.mjs#l1001)). So one is shown, the last one fetched, and edits go to that href. This matches the 2017 report that the event "disappears in Lightning".
- **Apple Calendar**: closed source. The same 2017 report says the event disappeared in Apple iCal too (mailing-list evidence only).
- **Evolution / GNOME Calendar**: GNOME Calendar uses EDS ([meson.build#L173](https://gitlab.gnome.org/GNOME/gnome-calendar/-/blob/17b370f5794d12da3dc4807a2da9d6981d5a1ffd/meson.build#L173)). The EDS CalDAV backend takes a resource's UID from its first component ([e-cal-backend-caldav.c#L432-L456](https://gitlab.gnome.org/GNOME/evolution-data-server/-/blob/15755335e9c99b24f11139b1c65db76ba385ea94/src/calendar/backends/caldav/e-cal-backend-caldav.c#L432-L456)). The cache key is UID plus RECURRENCE-ID ([e-cal-cache.c#L456-L465](https://gitlab.gnome.org/GNOME/evolution-data-server/-/blob/15755335e9c99b24f11139b1c65db76ba385ea94/src/calendar/libedata-cal/e-cal-cache.c#L456-L465)), written with `e_cache_put` ([#L2565](https://gitlab.gnome.org/GNOME/evolution-data-server/-/blob/15755335e9c99b24f11139b1c65db76ba385ea94/src/calendar/libedata-cal/e-cal-cache.c#L2565)). From reading the code, two hrefs collapse into one cache entry and the later one replaces the earlier. This was not tested.
- **vdirsyncer**: a second item with the same UID raises `IdentConflict` ([sync/__init__.py#L46-L53](https://github.com/pimutils/vdirsyncer/blob/ceee70d1a15bab19b9691beff86d23bf072ea7dc/vdirsyncer/sync/__init__.py#L46-L53)). It then "will now abort the synchronization of this collection" and suggests `vdirsyncer repair` ([cli/utils.py#L104-L113](https://github.com/pimutils/vdirsyncer/blob/ceee70d1a15bab19b9691beff86d23bf072ea7dc/vdirsyncer/cli/utils.py#L104-L113)).
- **khal**: its events table's primary key is (href, calendar), so both are shown ([backend.py#L147-L154](https://github.com/pimutils/khal/blob/3ba0fcef06d5244a4a7330869a8d5f18a0342ce9/khal/khalendar/backend.py#L147-L154)). A file with several UIDs is skipped with a warning ([#L227-L235](https://github.com/pimutils/khal/blob/3ba0fcef06d5244a4a7330869a8d5f18a0342ce9/khal/khalendar/backend.py#L227-L235)).

So clients split three ways: keep both (DAVx5, khal), keep one (Thunderbird, EDS, reportedly Apple), stop with an error (vdirsyncer). None merges the two.

## What this means for FreeCal

- **Dropped Exceptions**: on the servers checked, ignoring a second resource with a held UID never drops Exceptions the server keeps apart on purpose. RFC 4791 puts a whole recurrence set in one resource, and no server found stores Exceptions separately. Google CalDAV is the one unverified case. It has its own Provider (ticket 26), but test it if it is ever reached through CalDAV.
- **Where duplicates come from**: the servers that allow them are SabreDAV core/Baïkal, DAViCal, DavMail/Exchange, and Nextcloud when an update changes the UID. There they come from buggy clients, imports and Exchange data. Each such case is two independent copies of an Event, not a Recurring Event and its Exceptions. Showing one of them is what Thunderbird and EDS already do. Logging the other matches nobody exactly but is closest to vdirsyncer's "report, don't guess".
- **"Winner removed, loser left"**: the Corresponding Server Object (the resource FreeCal mirrored) is deleted on the server while the ignored resource with the same UID stays. This needs a duplicate to exist first, so it can only happen on the permissive servers above. There it is plausible: a user who sees two copies in a keep-both client such as DAVx5 or khal and deletes one has a 50% chance of deleting FreeCal's. ADR 0011's rule that the other resource "becomes the Corresponding Server Object … when the first one goes" covers this case. Under ticket 102 that only works if the ignored resource is fetched again and taken up, so the Log line shouldn't be the only trace of it.
- **Which copy wins**: rules that pick by fetch order differ between clients. Thunderbird shows the last href fetched, so FreeCal and Thunderbird can show different copies. ADR 0011's "the one holding the Recurring Event, otherwise the first one mirrored" is deterministic for FreeCal, which is more than the RFC asks.
- **ADR 0013's server list**: re-checked. SabreDAV (via sabre/vobject), Radicale, CCS, Cyrus and Stalwart refuse resources holding several UIDs. On the separate question of one UID in two resources, SabreDAV core and Baïkal do **not** refuse; Nextcloud's own backend does on create only. Don't cite "SabreDAV refuses" for duplicate UIDs.
